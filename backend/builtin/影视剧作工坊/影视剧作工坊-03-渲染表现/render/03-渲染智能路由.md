# 渲染智能路由（执行层）
（把视觉意图变成一份可交付的渲染档案）

## 固定链

```
视觉意图 → 渲染智能 → 渲染器 / 模型执行 → 语义转换（12）
```

本层负责链的前两段：读取意图 → 产出 `SHOT_RENDER_PROFILE`。第三段交给 **12 技术语言转换**（UE5 / Arnold 通道），它把渲染器技术词翻译成模型能执行的画面语言。

## 渲染智能内部能力（15 项）

渲染风格 / 渲染质量 / 材质响应 / 灯光响应 / 阴影 / 反射 / 折射 / 体积 / 曝光 / 景深 / 运动模糊 / 镜头特性 / 照片级真实感 QC / 渲染器选择 / 渲染器翻译。

前 12 项是**画面属性**，最后 3 项是**工程属性**。12 的心法（"模型看不见渲染管线，只看见画面效果"）在这里就成立：前 12 项最终都要落成可观察的画面描述，后 3 项在交付前由 12 剥离。

# 一、处理顺序（九步）

1. **读取 Human Visual Lock** —— 取用户明确锁定的视觉字段；没有明确锁定的部分记为待推导，不冒充锁定。
2. **解析视觉生产体系**（A 维）。
3. **解析写实度**（B 维）。
4. **解析渲染策略**（C 维）。
5. **解析渲染器**（D 维，若用户指定）。
6. **生成 `SHOT_RENDER_PROFILE`**。
7. **调用视觉知识库、电影摄影知识库与风格能力库** —— 即 `render/05`–`render/09` 的 DNA 库与 02 的调色资产。
8. **经语义转换，变为模型可执行的可观察结果语言**（12 承接）。
9. **语义与生成结果验证** —— 回到视觉意图核对：生成结果是否仍落在第 1 步的锁定范围内。

## SHOT_RENDER_PROFILE（本层交付契约）

下游（12、13）按此结构取字段，字段名与 `render/13-视觉风格调用接口.md` 的 `visual_style` 对齐：

```yaml
render_profile:
  medium: ""            # 载体（九轴之一）
  art_direction: ""     # NEXT_GEN / GUOMAN / ANIME_COMIC
  realism: ""           # HYPERREAL / REALISTIC / SEMI_REALISTIC / STYLIZED
  photographic_cue: ""  # 是否启用 PHOTOGRAPHIC_REALISM
  render_strategy: ""   # REALTIME / HIGH_QUALITY_REALTIME / OFFLINE_CINEMA
  renderer: ""          # UE5 / ARNOLD / OCTANE / 未指定
  locked_fields: []     # Human Lock：用户明确指定的轴
  derived_fields: []    # 推导值：本层补齐的轴，必须标注
  material_response: "" # 材质响应：反射 / 折射 / 次表面 / 粗糙度表现
  light_response: ""    # 灯光响应：硬光 / 柔光 / 遮蔽 / 反弹
  optics: ""            # 曝光 / 景深 / 运动模糊 / 镜头特性
  qc_gate: ""           # 照片级真实感验收点
```

**`locked_fields` 与 `derived_fields` 必须分开写。**混在一起会让下游无法判断哪些可以推翻——这是返修（11）时最容易扯皮的地方。

# 二、禁止反向污染

> **渲染器只能实现目标，不能重新定义目标。**

- 用户指定"次世代半写实"，**即使走了 Arnold，也不得擅自变成超写实**。
- 同样地，**选了 UE5 也不得擅自降成游戏预览质感**。
- 判断依据始终是第 1 步的 Human Visual Lock；渲染器改变的是实现成本与部分渲染特性，不是写实度。

## 六维视觉 DNA 与四维正交轴的关系

- 生产体系 / 写实度 / 渲染策略 / 渲染器**四维保持正交定义**，不互相吸收。
- 六维视觉 DNA（构图与镜头、色彩与光影、质感与氛围、经典场景、角色与动作、色调细节，见 `render/05`）是**更上层的视觉决策描述层**。
- **不把 DNA 维度改造回渲染器轴或载体轴**——DNA 描述"画面给人的整体决定"，四维描述"用什么做"。两者单向使用：DNA → 四维，不可倒推。
