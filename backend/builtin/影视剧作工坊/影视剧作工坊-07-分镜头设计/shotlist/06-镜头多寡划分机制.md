01 总览：镜头多寡是怎么定下来的（决策链全景）
────────────────────────────────────────────────────────────────────────

该技能不采用"每 X 秒切一个镜头"之类的机械配额，而是把镜头数量作为
导演决策的【结果】，由以下五层机制共同收敛出来：

    剧本/意图
        ↓  ①拆节拍（Beat Map）→ ②信息释放 → ③判断每个节拍是否需要镜头
    镜头必要性筛选
        ↓  ④无目的镜头 → Shot Kill Gate 淘汰
    镜头链（Coverage）
        ↓  ⑤主镜头 + 反应 + 关系 + 必要补 coverage
    覆盖预算收敛
        ↓  ⑥Coverage Budget = 固定时长（HARD）× 生成风险
    生成单元切分
        ↓  ⑦Shot ≠ Generation Unit ≠ Edit Unit；自然边界切分
    交付
        ↓  ⑧每个镜头按 shot_id 输出 ①～⑩ + 逐秒精细化说明

一句话概括：
    多寡 = 节拍和信息释放说了算（每个镜头必须有目的），
    上限被固定时长和生成风险卡死（Coverage Budget），
    单元边界由动作/状态/空间切换切分，
    无目的镜头会被 Shot Kill Gate 淘汰，
    用户明确指定的镜头方案拥有最高优先级。

02 第一原则：剧本决定镜头，没有数量公式
────────────────────────────────────────────────────────────────────────

出处：CORE/UNIFIED_DIRECTOR_ARCHITECTURE.md（总原则）
      FUSED_CORE/rules/01_DECISION_STORY_BEAT.md（Hard rules）

原文引述：
    「剧本决定镜头；模式只改变表达倾向。」
    「导演决定需要什么素材；生成模型负责执行；剪辑系统负责最终剪辑。」
    「每个镜头必须有叙事/信息/情绪目的；没有目的的镜头进入 Shot Kill Gate。」

含义拆解：
  · 镜头数量不由时长机械推导（不是"30 秒 = 3 个 10 秒镜头"），
    而由剧本内容反推：这段戏要释放什么信息、什么情绪、什么调度。
  · 文生视频（T2V）/ 图生视频（I2V）等"模式"只改变表达方式，
    不改变镜头数量本身。
  · 三方分工明确：导演只决定需要哪些镜头素材；生成模型负责执行
    每个镜头；最终剪辑取舍归剪辑系统，导演不越权。

03 决策顺序：从场景目的到镜头必要性
────────────────────────────────────────────────────────────────────────

出处：FUSED_CORE/rules/01_DECISION_STORY_BEAT.md（Canonical order）

固定决策顺序（不可跳步）：
    目标解析 → 任务分类 → 场景目的 → Beat Map → 信息释放
    → POV/信息控制 → 时间域 → 镜头必要性 → Coverage → 接受标准

镜头数量在这个链条中的位置：
  a) 先把场景目的拆成 Beat Map（节拍图）；
  b) 每个节拍标注信息释放（这一拍观众得知什么）；
  c) 由信息释放推导"镜头必要性"——需要新信息量/新视点/新情绪
     的节拍才值得一个新镜头；
  d) 汇总必要镜头 → 形成 Coverage 方案；
  e) 最后对照"接受标准"验收。

配套的时间域规则（决定镜头时长的分配方式）：
  三时间域分别处理，不能混为一个时钟：
    · 故事时间（剧情内经过的时间）
    · 表演/动作时间（动作实际耗时）
    · 生成/执行时间（模型生成条片的时长）

另一条硬规则：导演只决定所需素材，不替编辑决定最终剪辑——
即使规划了 N 个镜头，最终用几个由剪辑侧决定。

04 镜头链结构：主镜头 / 反应 / 关系 / 补 coverage
────────────────────────────────────────────────────────────────────────

出处：FUSED_CORE/rules/04_SHOT_CAMERA_COVERAGE.md（Coverage 节）

原文引述：
    「建立镜头链、主镜头、反应、关系镜头、必要补 coverage；
      Coverage Budget 受固定时长与生成风险约束。」
    「景别 = 信息量；机位 = 心理暗示；运动 = 调度情绪。
      镜头必须服务 Scene Purpose / Beat / Information Release。」

镜头链的典型构成（数量由此结构生长）：
    · 主镜头（Master）：承载场景主干信息的基准镜头
    · 反应镜头（Reaction）：承接情绪信息
    · 关系镜头（Relationship）：交代人物空间/权力关系
    · 补 coverage（Pickup/Insert）：只补必要缺口，不额外加戏

镜头分配的三条语义轴：
    · 景别 → 决定每个镜头携带的【信息量】
    · 机位 → 决定每个镜头施加的【心理暗示】
    · 运动 → 决定每个镜头调度的【情绪】
  一个镜头若在这三轴上都无增益，即不必要。

────────────────────────────────────────────────────────────────────────
05 Coverage Budget：覆盖预算的两大约束（固定时长 + 生成风险）
────────────────────────────────────────────────────────────────────────

出处：FUSED_CORE/rules/04_SHOT_CAMERA_COVERAGE.md；
      CORE/UNIFIED_DIRECTOR_ARCHITECTURE.md（时长节）

原文引述：
    「Coverage Budget 受固定时长与生成风险约束。」
    「固定时长是 HARD。导演在固定时间内重新分配 coverage、beat、
      镜头材料，不偷偷增加总时长。」

两个约束因子的含义：
  约束一：固定时长
    · 项目/镜头总时长是硬闸，镜头再多，总和不得超出。
    · 镜头多寡因此是"时长内分配问题"：加一个镜头 = 从别的
      镜头/节拍那里挪时长，而不是延长总时长。

  约束二：生成风险
    · AI 视频生成的现实约束：镜头切得越多，跨镜连续性崩坏
      （人物换脸、道具漂移、光线跳变）的累计风险越大。
    · 因此技能倾向"少而稳"：单镜承载主要动点（尤其 I2V），
      动静分离，把高风险变化集中到尽量少的生成单元里。

────────────────────────────────────────────────────────────────────────
06 固定时长硬约束：只许内部腾挪，不许扩时
────────────────────────────────────────────────────────────────────────

出处：SKILL.md（核心硬锁第 2 条）；
      ORCHESTRATION/MASTER_ORCHESTRATOR.md（核心规则 9）；
      LOCKED_CONTRACTS/FINAL_DELIVERY_TRUTH.md（硬锁）

原文引述：
    「固定时长为 HARD CONSTRAINT，超过项目时长直接 BLOCK。」
    「固定时长为 HARD；编排只优化固定时长内的素材结构，不自行扩时。」
    「固定时长为 HARD CONSTRAINT；不得自行扩时。」

执行机制：
  · 时长超限不是"警告"而是 BLOCK——直接阻断交付闸门。
  · 编排器（Orchestrator）的一切优化（并行、复用、重排）
    都只在固定时长内进行素材结构调整。

07 Shot ≠ Generation Unit ≠ Edit Unit：镜头数不等于生成条数
────────────────────────────────────────────────────────────────────────

出处：CORE/UNIFIED_DIRECTOR_ARCHITECTURE.md（总原则）；
      FUSED_CORE/rules/04_SHOT_CAMERA_COVERAGE.md（Generation Unit 节）；
      ORCHESTRATION/MASTER_ORCHESTRATOR.md（核心规则 8）

原文引述：
    「Shot ≠ Generation Unit ≠ Edit Unit。」
    「自然边界由动作完成、状态完成、空间切换、生成风险和连续性决定。」
    「编排器不替编辑器决定最终剪辑。」

三个概念的区别：
    Shot（镜头）      —— 导演叙事单位，"我要一个什么画面"
    Generation Unit
    （生成单元）      —— 喂给视频模型的一次生成任务，
                         边界按"自然边界"切：
                           · 动作完成处
                           · 状态完成处
                           · 空间切换处
                           · 生成风险点
                           · 连续性需求点
    Edit Unit（剪辑单位）—— 最终成片里的剪辑切点，归剪辑系统

对"镜头多寡"的实际影响：
  · 规划了 3 个镜头 ≠ 生成 3 条视频：连续的静态对话镜头可合并为
    一个生成单元，高风险动作镜头也可能拆出多个生成单元。
  · 一个生成单元内部还可以携带 first_frame_state（首帧状态）：
    起始空间 / 起始人物位置 / 起始身体方向 / 起始视线 /
    起始动作状态 / 起始道具状态（出处：FUSED_CORE/
    VIDEO_DIRECTOR_ENHANCEMENT/RULES.md 第 3 节）。
  · 动作时序上，每个视频单元拆成可观察节拍：
    动作起点 → 动作发展 → 结果/反应（同文件第 4 节）。

08 代码实现：shotlist_director() 的默认划分行为
────────────────────────────────────────────────────────────────────────

出处：FUSED_CORE/engines/higgsfield_director_core.py（shotlist_director 函数）

代码要点（摘录）：
    def shotlist_director(sequence):
        ...
        for s in shots:
            s.setdefault("generation_unit", s.get("shot_id"))
            s.setdefault("one_job", True)
        return {
            ...
            "shots": shots,
            "envelope_s": 15,
            "sequence_tempo": ...,
            "edit_once": True,
        }

解读：
  · generation_unit 默认 = shot_id：每个镜头默认对应一个生成任务，
    one_job = True（一次生成完成，不做内部分批）。
  · envelope_s = 15：序列包络默认 15 秒——即默认按 15 秒量级的
    序列组织 shotlist，超出则自然形成多个序列/镜头组。
  · edit_once = True：剪辑动作只做一次，导演层不反复改剪。
  · 注意这是"默认值"而非硬锁——上游导演决策可覆盖。

基准测试参照（BENCHMARK/cases/011.json）：
    测试用例主题为「10秒单镜头」，要求在 30 秒以内严格遵守
    用户视觉锁、角色连续性、对白绑定和最终交付规范。
  → 说明技能把"10 秒单镜头"作为单镜头场景的标准校验样例，
    单镜方案是该技能支持且重点保障的最小划分。

09 Shot Kill Gate：无目的镜头的淘汰闸门
────────────────────────────────────────────────────────────────────────

出处：CORE/UNIFIED_DIRECTOR_ARCHITECTURE.md（决策层 19 号节点）；
      FUSED_CORE/rules/01_DECISION_STORY_BEAT.md（Hard rules）

原文引述：
    「每个镜头必须有叙事/信息/情绪目的；没有目的的镜头进入
      Shot Kill Gate。」

运行位置：
  Shot Kill Gate 是 24 层决策架构中的第 19 层
  （19 Validation / Shot Kill Gate），位于生成执行（18）之后、
  修复再生（20）之前——即验证阶段统一淘汰不合格镜头。

淘汰后走向：
  被杀掉的镜头不是简单丢弃，进入 20 Repair / Regeneration
  （修复/再生成）或回滚重规划；不满足目的的镜头材料不允许
  带病进入交付。

对镜头多寡的意义：
  这是数量收敛的"下限闸门"——宁可少，不可无目的。

10 优先级链：用户指定的镜头拥有最高决定权
────────────────────────────────────────────────────────────────────────

出处：SKILL.md（核心硬锁第 1 条）；
      CORE/UNIFIED_DIRECTOR_ARCHITECTURE.md（优先级节）；
      FUSED_CORE/rules/05_VISUAL_RENDER.md（Human lock 节）

原文引述：
    「Human Visual Lock > Scene Lock > Shot Override > Director Decision
      > Model Default。」

镜头多寡语境下的含义：
  · 用户明确说"10 秒单镜头"“三个机位拍完”→ 属于 SHOT OVERRIDE，
    压过导演自己的 coverage 判断。
  · 导演只能在用户未指定的层级上补齐，且补齐值必须标记为推导值，
    不得伪装成 Human Lock（出处：VISUAL/VISUAL_INTENT_ONTOLOGY.md 约束节）。
  · 模型默认值永远排在最后。

11 I2V / 图生视频的单镜控制规则
────────────────────────────────────────────────────────────────────────

出处：FUSED_CORE/rules/04_SHOT_CAMERA_COVERAGE.md（I2V 节）；
      SKILL.md（I2V 输出模式）

原文引述：
    「外观不确定时 still-first；参考图负责身份/构图锚定，
      文本负责动作/镜头/环境变化；动静分离，控制单镜主要动点。」

对镜头多寡的影响：
  · I2V 模式下镜头划分更保守：参考图锚定静态身份与构图，
    文本只描述新增变化。
  · "控制单镜主要动点"= 每个生成镜头只承载一个主要运动焦点，
    人物动作、镜头运动、环境动态三者可分别描述、按时间统一
    （VIDEO_DIRECTOR_ENHANCEMENT/RULES.md 第 4 节），但单镜内
    不堆多个主要动点——这直接把 I2V 的单镜复杂度压低，
    客观上鼓励"多镜头、轻镜头"而非"少镜头、重镜头"。
  · 首尾帧场景：图1 → 变化过程 → 图2 的首尾帧协议也在
    生成单元层面约束了镜头起止状态。

12 交付层落地：shot_id + ①～⑩ + 逐秒精细化说明
────────────────────────────────────────────────────────────────────────

出处：LOCKED_CONTRACTS/FINAL_DELIVERY_TRUTH.md（锁死交付文件格式）

原文引述（每个镜头的交付结构）：
    id="<shot_id>"
    ①渲染规格
    ②画幅画质
    ③环境场景
    ④人物外观状态
    ⑤人物动作
    ⑥镜头运镜构图
    ⑦光影色彩
    ⑧对白
    ⑨背景音
    ⑩BGM
    —— 全局尾部：负面规避词表 + 逐秒精细化说明

与镜头多寡相关的硬锁：
    · 固定时长为 HARD CONSTRAINT；不得自行扩时。
    · 每个镜头独立持有 id，逐秒精细化说明按镜头落到秒级。
    · 数值锚与完整自然台词冲突时，保留准确台词，调整数值锚。

含义：镜头数量的最终体现就是交付文件里 shot_id 的个数；
每个 shot_id 内部再按秒细化，时长约束在秒级被最终校验。

13 典型场景推演（单镜头 vs 多镜头怎么选）
────────────────────────────────────────────────────────────────────────

场景A：10 秒单镜头（基准用例 011 的形态）
    剧本只有一个信息节拍 → Beat Map 只有一拍 → 镜头必要性 = 1
    → 无需反应/关系镜头 → Coverage = 主镜头 1 个
    → 生成单元 1 个（one_job）→ 逐秒说明覆盖 10 秒。
    选择依据：信息量单拍即可释放完毕，切镜无增益。

场景B：一场对话戏（约 15 秒包络内）
    Beat Map 多拍：陈述 → 反应 → 关系变化
    → 镜头链 = 主镜头 + 反应镜头 + 关系镜头（3 个左右）
    → Coverage Budget 检查：15 秒内分配三个镜头，每镜 4~6 秒；
       生成风险：对话镜头动作轻，风险低 → 通过
    → 生成单元可按自然边界合并或保持 3 个。

场景C：高动作戏（同一固定时长）
    动作节拍多、动点密集 → 镜头必要性高
    → 但生成风险约束生效：单镜只放一个主要动点
    → 结果是"镜头变多变短"，每个生成单元负担轻，
      连续性靠场尾状态记录（人物位置/朝向/动作结果/道具状态/
      信息状态/视觉灯光状态/声音状态，见 VIDEO_DIRECTOR_ENHANCEMENT
      RULES.md 第 8 节）在镜头间传递。

场景D：用户指定方案
    用户直接给出"两个机位、每机位 5 秒" → SHOT OVERRIDE 生效
    → 导演不再自行推导数量，只在未指定维度（景别、运镜细节等）
      补齐推导值并显式标记。

A.1 FUSED_CORE/rules/01_DECISION_STORY_BEAT.md（全文）
────────────────────────────────────────────────


来源融合：Global Decision Engine、Director Intent Engine、script-interpreter、information-pov-engine、three-time-domains、sequence-memory、Director Brain、Orchestrator。

## Canonical order
目标解析 → 任务分类 → 场景目的 → Beat Map → 信息释放 → POV/信息控制 → 时间域 → 镜头必要性 → Coverage → 接受标准。

## Hard rules
- 剧本决定镜头，模式只改变表达倾向。
- 每个镜头必须有叙事/信息/情绪目的；没有目的的镜头进入 Shot Kill Gate。
- 三时间域分别处理故事时间、表演/动作时间、生成/执行时间，不能混为一个时钟。
- 固定时长 HARD；覆盖量在时长内重新分配。
- 导演只决定所需素材，不替编辑决定最终剪辑。

## Decision record
每次重大导演选择都保留：intent / alternatives / chosen / reason / constraints / downstream impact。

A.2 FUSED_CORE/rules/04_SHOT_CAMERA_COVERAGE.md（全文）
────────────────────────────────────────────────


来源融合：Shot Architecture、Storyboard Engine、Camera & Lens、Composition Physics、Coverage Budget、Generation Unit、Sequence Editor/Memory。

## Shot logic
景别 = 信息量；机位 = 心理暗示；运动 = 调度情绪。镜头必须服务 Scene Purpose / Beat / Information Release。

## Coverage
建立镜头链、主镜头、反应、关系镜头、必要补 coverage；Coverage Budget 受固定时长与生成风险约束。

## Generation Unit
Shot ≠ Generation Unit ≠ Edit Unit。自然边界由动作完成、状态完成、空间切换、生成风险和连续性决定。

## Camera
焦距、景别、机位、运动、景深、Filmback、视线和空间透视先形成摄影语义，再由 D-CG 转成模型可理解语言。

## I2V
外观不确定时 still-first；参考图负责身份/构图锚定，文本负责动作/镜头/环境变化；动静分离，控制单镜主要动点。

def shotlist_director(sequence: Dict[str, Any]) -> Dict[str, Any]:
    q = deepcopy(sequence or {})
    shots = deepcopy(q.get("shots") or [])
    for s in shots:
        s.setdefault("generation_unit", s.get("shot_id"))
        s.setdefault("one_job", True)
    return {
        "global_style_anchor": deepcopy(q.get("global_style_anchor") or {}),
        "asset_glossary": deepcopy(q.get("asset_glossary") or []),
        "shots": shots,
        "envelope_s": 15,
        "sequence_tempo": deepcopy(q.get("sequence_tempo") or {}),
        "edit_once": True,
    }
