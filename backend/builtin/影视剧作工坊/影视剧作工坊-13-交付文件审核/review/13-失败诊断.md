**总纲：诊断先于修复。**

1. **先分岔，再动手**——大多数失败是方差，不是提示词坏了。系统性失败（每次都同一种失败）走单变量迭代；随机性失败（失败方式五花八门、偶尔接近命中）走批量抽卡。分岔流程见《提示词结构·纯技术文档》§迭代纪律。
2. **失败发生在哪一层，决定修什么**——过滤器拒稿修语气，渲染失败修密度，参考失败修输入，系统性重复修提示词，随机性单次失败什么都不修。
3. **绝不在诊断之前原样重发**——同样的文本会绊响同一个分类器、踩中同一处渲染边界；重发不是诊断。

# 一、第一步：失败发生在哪一层

## 1.1 即时失败 vs 延迟失败

| 失败时机 | 含义 | 该做什么 |
|---------|------|---------|
| **< 10 秒**（即时） | 内容过滤器拒稿——提示词根本没到渲染层 | 按语气重写 + 移除风险词。绝不绝不绝不原样重新生成。 |
| **> 30 秒**（延迟） | 基础设施、超时或复杂度——提示词过了过滤器但渲染失败 | 简化动作密度、缩短时长、再试 |

循环出现的即时失败是过滤器问题，绝不是渲染能力问题——在重写完成之前，先拦住重新生成的手。

## 1.2 过滤器模型

过滤器不是关键词黑名单，而是一个把整条提示词当作一场戏来读的语言模型："读起来像电影人在描述一个镜头"倾向于通过；"读起来像写给朋友的便条"倾向于失败。孤立看敏感的词可以安然待在结构良好的电影化提示词里；没有画面可读的提示词（没有场景、没有视觉目的、没有叙事逻辑）让过滤器无从下手、宁可保守。**提示词必须描述一个场景，而不是一个主体——先修语气，再修用词。**

# 二、常见问题速修表

| 症状 | 根因 | 修复 |
|------|------|------|
| **角色面部不一致或变形** | 没有角色参考；提示词里有互相冲突的外貌描述 | 建立角色参考并全程使用；删除互相矛盾的外貌描述；图生视频时不重新描述面部——让输入图承载它 |
| **镜头运动不生效 / 过于泛泛** | 镜头描述含糊，没用确切预设名 | 用准确预设名替换泛述；镜头指令单独成行；指名控制项而非散文描述 |
| **提示词被无视 / 输出不匹配** | 过长、指令冲突、过度指定 | 短句体制删减到目标区间；删除矛盾元素；最重要的元素放开头；复杂场景拆成多次生成 |
| **视觉风格不对 / 千篇一律** | 没指定风格或描述含糊 | 点名风格；加具体调色描述；指定画幅；加灯光语言 |
| **运动预设效果看不出来** | 预设没点名，或场景语境不支撑 | 按预设库原样写明；指令放提示词末尾并清晰标注；确认语境支撑（变形预设需要一个逻辑上能变形的主体） |
| **图生视频几乎不动 / 静止** | 提示词在重新描述静止元素 | 只描述会变化会运动的内容；加明确镜头运动；指明运动类型；加氛围运动（尘埃上浮、灯光闪烁、蒸汽升起） |
| **特效预设太假 / 卡通化** | 预设配错模型，或风格与效果冲突 | 写实系预设配写实引擎；风格化预设配风格化引擎；提示词加"照片级真实、物理准确" |
| **产品镜头显廉价 / 打光过度** | 没有灯光规格，背景平淡 | 指明背景表面（素混凝土、暖木纹、黑丝绒）；加具体灯光；加质感线索（表面在边缘吃光） |
| **恐怖 / 暗黑内容被拦截** | 平台安全过滤器被露骨内容触发 | 描述后果而非露骨行为（"事后余波""紧张""恐惧弥漫"）；用氛围语言（"令人不安""有什么不对"）；恐怖效果用运动预设实现，不用露骨描述 |

# 三、动作迁移失败速查

动作迁移（把参考片段的动作迁移到新角色）生成结果不对时，原因几乎总在提示词上游——动作参考、角色图、或朝向/场景设置：

| 症状 | 根因 | 修复 |
|------|------|------|
| 输出在片段中途跳切或顿挫 | 动作参考里含有隐藏的剪切、叠化或硬转场 | 把参考重新修剪成单一连续镜头；源片段清理不干净就重拍或另选参考 |
| 输出比参考片段短 | 源动作太快太密，无法干净迁移 | 放慢源片段（50–75% 变速）、用更从容的节奏重拍，或另选动作更简单的参考 |
| 面部在片段中漂移或扭曲 | 角色图的面部不可读——构图差、光暗、脸太小 | 用更近景别、均匀光照、中性表情重拍角色图 |
| 身体动作正确但面部呆滞 | 朝向模式用错——该用视频朝向的镜头用了图像朝向（或反之） | 全身运动（舞蹈、动作戏）用视频朝向；镜头驱动、身体基本静止的镜头用图像朝向 |
| 角色与环境脱节 | 场景来源设置错误——拉了错误的背景 | 判断环境应来自动作视频还是角色图，相应设置 |
| 动作迁移成功但身份漂移 | 角色图不完整——头部或身体被裁掉 | 重传一张头脚完整入镜的角色图——元素绑定靠它让面部在运动中保持稳定 |

**音频两症**（完整对白/口型纪律见《负面约束预防总表》时序部分）：

- **口型不同步**——头部运动 token 与口型引擎互相抢占、格式不对、片段过长 → 删掉所有头/脸运动 token；对白片段剪到 3–8 秒；每个镜头只有一张脸；镜头锁静态或慢速推近。
- **背景音乐压过上传的对白**——环境/音乐 token 招来生成式音频引擎替换上传音频 → 加时间戳锚定（"音频 @Audio1 从 0 秒到结尾严格按上传内容播放"）；删掉所有环境音/音效/音乐 token。

# 四、失败模式图谱

（本文档收录未进入其他专题文档的失败模式。多运动过载、帧率漂移、动作被截断见《运镜·纯技术文档》§十；空间感知、无主肢体、走路、打斗接缝见《空间约束·纯技术文档》§四；序列与续接失败图谱见《镜头组接·纯技术文档》§七。）

## 4.1 逐帧审查是强制性的

**症状：**一条片段全速播放看着没问题，内里一帧坏帧毁掉剪辑——闪了一下的手、扭曲的脸、错位的物品，只有按暂停的眼睛抓得住。

**机理：**输出是生成的，不是拍摄的。实拍素材里镜头光学约束着每一帧；生成片段的逐帧状态是独立的，可以在毫无预兆下单帧漂移。一条 24 帧的片段就是 24 次被串在一起的独立生成。

**对策：**审查之前把每条片段当作不可信的——逐帧步进梳理；一帧坏帧就足以否决整条。把逐帧审查时间规划进预算（10 秒片段每遍约 30–60 秒）。

## 4.2 失败生成的抢救

**症状：**一次生成在条次级别被退回——运镜不对、动作垮塌、构图中途散架。第一反应是丢弃重生成。

**机理：**一次"失败"很少在全部时长上都失败——模型常在被丢弃的片段内产出 1–3 秒可用素材：运镜漂移前的干净开头、动作垮塌前的干净中段、临近结尾的可用插入。

**对策：**丢弃之前，用入点/出点标记可用段落，剪出来存进素材库。幸存的 2 秒插入镜头常能塞进另一个场景当衔接，或撑住一个反应节拍。抢救出的秒数在整个项目层面复利累积——某部 90 分钟剧情长片的正片里，抢救剪辑贡献了可观的时长。

## 4.3 NSFW 误判（供应商侧）

**症状：**不含任何敏感内容的提示词被当作敏感内容退回；其他检查通过，只有这一个分类器触发。

**机理：**分类器同时运行在提示词文本和中间生成 token 上；身体细节、某些服装词汇、感性但干净的措辞都可能绊响它。分类器是概率性的且偏保守——误判是其运行画像的一部分。

**对策（改写提示词）：**

1. 移除或泛化解剖细节（"她裸露的肩膀"→"她的肩膀"；"紧身连衣裙"→"合身连衣裙"）。
2. 用中性等价词替换感性语域形容词（"妩媚"→"沉静"；"挑逗"→"直接"）。
3. 改写稿过一遍发送前自查，抓剩余风险词。

绝不绝不原样重发——同样文本绊响同一分类器。

## 4.4 关键帧一致性迫使凭空发明

**症状：**提示词要求某元素出现或移动（"从冰箱上扯下一张拍立得"），但源关键帧里没有那个元素——模型照样生成动作，凭空发明元素的位置，常与场景几何矛盾。

**机理：**模型把源关键帧当作"这个世界包含什么"的强锚点。要求关键帧没展示的元素时，它必须同时制造元素**和**位置，而位置漂到它在不覆盖其他参考的前提下能塞下的任何地方。

**对策：**显式声明"不存在"，让模型知道这是"添加"而非"匹配"：`拍立得在参考图的冰箱上并不可见；在本镜头中，当角色的手从画框下方抬起时，它才出现。`这条显式的"参考与输出在此元素上刻意不一致"从句，把发明从兜底随手一放变成有意图的摆放。

## 4.5 物理状态锚

**症状：**一个物体在相邻物体移动时行为出错——扯下拍立得时磁贴跟着飞走；端起碟子时杯子翻了；转头时帽子跟着抬起。

**机理：**没有强制的物理模拟。两个物体在源画面中视觉相邻时，模型可能把其一的运动解读为两者的运动——快速运镜或密集动作下尤甚。

**对策：**显式写出不变量——点名什么保持不动：`磁贴全程吸附在冰箱表面。只有拍立得在动。`物理锚是软约束不是硬保证，但不变量被点名后相邻漂移明显下降。

## 4.6 动作回摆填充

**症状：**被提示的动作在最初几秒完成，片段其余部分把它倒着重放一遍——向前走然后退回起点，倾身靠近然后拉开，伸手然后收回。运镜版本：没有声明目的地的运镜到达后原路漂回。

**机理：**短动作在片段结束前就完成了，模型手里还剩几秒时间线要填；没有进一步指令时，与场景一致的最廉价延续就是把已渲染的运动倒着再跑。（此处未经系统验证——模型无关的图生视频行为，非特定引擎规范。）

**对策：**给运动足够的素材让整条片段朝一个方向花掉——沿同一矢量串联 2–3 个相连动作（走到窗边，拉开窗帘，凑近玻璃）。剧情真要"去了又回"，那是两个镜头不是一条提示词。运镜点名终点——声明运动结束时画面展示什么。

## 4.7 短台词上的填充嘟囔

**症状：**单人镜头里一句很短的台词返回时被包在发明的嘟囔里——词前词后有含混的伪语音，或台词被念了两遍。

**机理：**音频分支会填充死空气——与动作回摆填充花掉剩余运动时间是同一机制。远早于片段结束就收尾的台词留下一扇静默窗口，最廉价的延续是同一个嗓音里更多语音形状的声音。（实测：4 秒镜头里 ≤6 词的台词每条都中招；8 词与 12 词干净返回——风险方向是*短*台词。）

**对策：给死空气安排工作，并为每张可见的脸声明嘴部状态：**

1. **填满窗口**——4 秒镜头里把台词扩到约 8 词以上，或把镜头剪短到台词长度。
2. **把静默写进脚本**——台词必须很短时，写下窗口其余部分被什么占据：一个具名的停顿节拍、一个环境声事件、覆盖台词前后空隙的动作散文。
3. **一个说话者，一句台词，只说一次**——说话的角色只说那句台词；承载想法而非台词的节拍标注为内心独白，完全不进入嘴里。
4. **每张其他可见的脸获得一条肯定式的静息嘴部事实**——画面里一张未标注的嘴就是模型可能判定为正在说话的嘴。表述为*确实为真*的事："双唇静息""下颌闭合，呼吸抬起胸口""目光落在说话者身上，嘴部安静"——绝不用否定式（"听着不说话"携带"不"字，绊响同一条法则）。

示例（4 秒双人镜头，一句台词）：

- ❌ `音频——MIRA（干涩、短促）："没了。"`——窗口大部分没写，第二张脸没有嘴部状态。
- ✅ `音频——只有剧情内声：雨点打在天窗上，3.4s 处一声门闩。MIRA（干涩、短促）的台词只说一次："没了，它把账本也一起带走了。"DEV 的目光一直落在她身上——双唇静息，下颌闭合，呼吸抬起他的胸口。`

（台词改写是实测的一半；第二张脸的静息嘴部事实是未实测的一半——它是当第二张脸无法排除出画面时的提示词侧处理。）

# 五、诊断树与预检清单

## 5.1 快速诊断表

| 症状 | 可能原因 | 修复 |
|------|----------|------|
| 输出模糊、抖动或变形 | 过度指定——过长过细 | 短提示词删减到 30–100 词、用参考图替代 50 词以上的描述；块脚手架简报不缩短——收紧结构 |
| 镜头混乱、旋转或抖动 | 违反单动规则 | 每镜头一个主运动；或拆成多镜头；或用视频参考迁移运镜 |
| 角色与参考不符 | 提示词在重新描述外貌 | 删除全部外貌描述，只留动作与情绪——身份由参考承载 |
| 动作僵硬或没有冲击力 | 缺意图/物理语言 | 加程度副词与物理后果（尘土炸起、火花飞溅、布料撕裂） |
| 输出"不是我想要的"（说不清） | 含糊、主观语言 | 跑反空话自查：把"美丽""惊艳""史诗感"换成可观察可度量的细节 |
| 音画不匹配 | 音频与视觉冲突，或上传音频被覆盖 | 时间戳锚定上传音频；删除环境音 token |

## 5.2 诊断流程图

```
输出不好？
├─ 模糊/变形 → 短提示词超过 100 词？
│   ├─ 是 → 删减，改用参考图（块脚手架：收紧结构，绝不截断）
│   └─ 否 → 动作节拍太多？（每 5 秒超过 2 个）→ 拆成多镜头
├─ 镜头不对 → 指定了几个镜头运动？
│   ├─ 多个 → 减到一个（单动规则）
│   └─ 一个 → 改试智能模式，或用视频参考迁移运镜
├─ 角色不对 → 提示词有没有描述外貌？
│   ├─ 有 → 删除外貌，只留动作/情绪
│   └─ 没有 → 换更好的参考（正面 + 3/4 侧 + 侧面）
├─ 动作无力 → 有没有物理语言？
│   ├─ 没有 → 加程度副词 + 物理后果
│   └─ 有 → 降低节拍密度（每 5 秒 1–2 个节拍）
└─ 就是不行 → 反空话自查
    ├─ 发现空话 → 换成具体的可观察细节
    └─ 干净 → 换个题材设定，或补参考
```

成功率背景：约九成产出可用；多次尝试*持续*不佳时，问题几乎肯定在提示词而不在模型。

## 5.3 生成前检查清单

生成前逐项确认：

- [ ] 主体描述清晰（谁/什么）
- [ ] 动作描述具体（发生什么）
- [ ] 镜头用准确预设名指名
- [ ] 视觉风格已指定
- [ ] 提到调色或灯光
- [ ] 包含画幅
- [ ] 已选定模型
- [ ] 提示词在体制字数内（块脚手架跳过此项）
- [ ] 没有互相冲突的指令
- [ ] 需要角色一致性时已挂参考
- [ ] 运动预设在结尾点名
- [ ] 身份块与运动块已分离

## 5.4 交付前自我修复清单

发送前把对策整合成一遍预防，让常见失败在构建时被抓住：

- [ ] 帧率写在提示词正文中（不只元数据头）？（→ 帧率漂移）
- [ ] 身体/感性语域 token 已清理？（→ 敏感误判）
- [ ] 首次出现的元素已标记"不在源关键帧中"？（→ 凭空发明）
- [ ] 相邻物体不变量已点名（"X 保持吸附""Y 不移动"）？（→ 物理状态锚）
- [ ] 运动把整条片段花在一个方向上？短动作串成 2–3 个同向节拍？运镜有具名终点？（→ 动作回摆）
- [ ] 对白窗口被完整写出？短台词扩长或静默写进脚本？每张可见的脸都带嘴部状态？（→ 填充嘟囔）
- [ ] 每镜头一个主导运镜？复合运镜拆成先后相位或分开的剪切？（→ 多运动过载）
- [ ] 几何用空间布局块锁定——主体多于一个或易发空间失败的镜头？（→ 空间感知失败）
- [ ] 为最终条次预留了逐帧审查时间？（→ 逐帧审查）

这份清单每条提示词花 60–90 秒，在烧额度之前抓住大多数可预防的失败。

# 六、镜头裁定——交付镜头的五种裁定

修复章节处理的是彻底失败。大多数真实交付落在中间地带——**部分可用**——而最烧钱的坏习惯是把每个瑕疵都当成重新生成的理由。任何东西重新触发之前，每条交付镜头必须拿到五种裁定之一：

| 裁定 | 适用情形 | 下一步 |
|------|----------|--------|
| **保留（Keep）** | 镜头使命已交付，无致命伤 | 锁定、记录、继续。次要细节的完美是后期的工作 |
| **后期修复** | 瑕疵属于剪辑师的领域：调色、画面文字、混音、修剪、首尾帧不稳 | 绝不为几分钟就能剪好的事烧掉好几条 |
| **编辑而非重生成** | 构图与时机都对，恰好只有一层错了，且有编辑手段 | 只修出错的那一层——"当编辑而非当重跑器" |
| **重掷（Re-roll）** | 提示词是对的，只是采样运气不好 | 同一提示词原样再来——每次投掷都是全新采样（没有种子参数）。历史足够多时分岔判定决定单发还是批量 |
| **重写（Rewrite）** | 同一瑕疵出现在两条镜头上 | 是系统问题不是运气——**两条镜头同一瑕疵 = 按规则重写**。先诊断，再改提示词 |

**重写绊线是双向的**：同一瑕疵出现两次 → 停止往同一堵墙上重掷；每次都是*不同*瑕疵 → 失手是随机的，属于批量抽卡的领地而不是重写。

**每次重拍只改一个变量**——无论裁定改的是什么（一条从句、一个模式、一个参考），两次拍摄之间恰好只改一件事，让因果保持可读；拍摄日志记录每次改的是哪个变量。

**尝试预算——第一条镜头开拍前声明**（启发式）：

- 一个**条数预算**数字；
- 一条**写下来的"够好"标准**——主要目标已交付、次要瑕疵可后期。不写下来，这个标准会悄悄变成"完美"，而任何预算都扛不住"完美"。

预算过半而同一瑕疵毫无进展时，停止迭代并改变策略：换模式、拆镜头、或走重试阶梯末级的具名选项（接受最好的一条 / 重新界定 / 推迟 / 占位标记——阶梯全文见《镜头组接·纯技术文档》§重试阶梯）。没有停止条件的迭代，就是一个便宜镜头变贵的方式。

**拍摄日志**：每条镜头一行——改了什么、结果如何。两行共享同一瑕疵，重写绊线就可审计——重读日志强过重蹈覆辙。

# 七、视觉锚定诊断

凭记忆记录淘汰原因就是道听途说（"我觉得脸漂了"）。能真正看到被否决的输出时，从画面本身分类——**视觉提议，人做确认**。

**适用范围**：仅静帧——一张图或从视频挑出的一帧代表帧。整段运动失败（帧率漂移、时序去重、多运动）不在其列，需要逐帧审看。

**流程链：**

1. **取帧**——把静帧拿到手（本地图直接读取；网页链接走导入控件，绝不喂原始链接）。
2. **对照枚举分类**——用一行字写下你看到的东西。
3. **找不到干净归类 → 归入"其他"+ 证据备注**——绝不硬套近似值。
4. **确认，然后记录**——抛出提议（"视觉判定为物理违规——左手扭曲，画面中央；确认还是纠正？"），人确认后落账。

**视觉所见 → 淘汰原因映射：**

| 视觉所见 | 淘汰原因 |
|---|---|
| 面部/身份相对参考变化 | 身份漂移 |
| 服装或颜色相对参考偏移 | 服装污染 |
| 多出剪切/不想要的场景断裂 | 多余剪辑 |
| 场面调度或走位被破坏 | 走位破坏 |
| 表演平淡/错误 | 表演 |
| 镜头运动不对 | 运镜错误 |
| 物理或解剖违规（含手部扭曲） | 物理违规 |
| 画面文字乱码 | 文字渲染 |
| 被内容过滤器拦截 | 过滤器拦截 |
| 取景/构图糟糕 | 构图 |
| 帧率漂移、时序去重，或无干净归类 | 其他 + 证据备注 |

**先度量，再信任。**视觉提议与最终裁定的一致率高于闸门的类别才可转为自动可信；在此之前每一条都人工确认。

# 八、记录结果——永远要记

不落记录的排障等于让下一个会话把排障重来一遍。任何确认有效的修复都落进项目记忆：

- **过滤器绕行已确认**（改写后的提示词在真实生成中通过）——记下通过的那条提示词本身；
- **质量修复已确认**（运动/身份/走位/音频被改进的提示词修好）——记下原始提示词、失败描述与改进后提示词，验证通过后标记改善；
- **事后才得知结果**（针对已有条目）——更新其最终状态（已修复 / 已绕行 / 仍被拦截）；
- **项目专属教训**单独归档，不污染全局记忆。

排障之前也先查记忆——那是上一轮会话留下的现成答案。
