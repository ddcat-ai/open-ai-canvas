## I — 方法论骨架 (Interpretation)

本 skill 管"渲染层"——解决"不喜欢线条风能不能换成别的"这个高频痛点。核心是**身份与画风两份独立配置**：

- 风格文件只声明"继承身份 + 改变渲染表面"：如毛毡风格 = 继承角色档案，只改变毛毡材质+手工轮廓+色彩质感，保持年龄感+发型+眼镜+服装+配饰。
- 反过来，同一毛毡风格可服务不同 IP，不能谁用了毛毡就长成同一个人。
- 可切换的远不止毛毡：极简线稿/纸张拼贴/松弛手绘/高冲击撞色/艺术版画/精致编辑卡通，都可在不改角色档案下单独替换。

**回归测试（解耦后的质保）**：同一"怀疑检查"动作分别生成线稿/毛毡/拼贴/版画/编辑卡通版，必须保持同一个人+同表情+同视线——把"感觉不像了"变成可复查工程条件。

**小互补充——招牌画风纪律**：能守住一种招牌风就别每篇换；辨识度来自统一不是多样，每篇换皮肤会稀释辨识度；真要偶尔换，传张锚点图让 AI 临时"现转"即可，不用囤一堆皮肤。

## A1 — 书中的应用 (Past Application)

### 案例 1：毛毡风格继承身份
- **问题**：角色最初极简线稿，替换成自己 IP 后仍只能沿用线稿，想改毛毡角色就变脸。
- **方法论的使用**：把角色档案与风格档案拆开；毛毡文件声明继承身份、只改材质，年龄感/发型/眼镜/服装不变。
- **结论**：变化的是画面材质，留下来的才是 IP。
- **结果**：线稿↔毛毡切换，人物仍是同一个人。

### 案例 2：风格一致性回归测试
- **问题**：换了几版画风，靠印象争论"像不像了"。
- **方法论的使用**：同动作跨 5 种画风生成，强制保持同一人+同表情+同视线，作为回归用例。
- **结论**：一致性变成可复查条件。
- **结果**：换风格不换身份有了验收准绳。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 想给同一 IP 换画风（毛毡/拼贴/版画）却怕角色变脸。
2. 想新增一个风格皮肤，不想重写角色档案或整套流程。
3. 要验收"同动作跨画风是否还是同一个人"（回归测试）。
4. 纠结该守一种招牌风还是每篇换。

### 语言信号（用户的话里出现这些就应激活）

- "身份与画风解耦 / 换画风角色变脸"
- "招牌画风 / 风格皮肤 / 同动作跨画风保持一致"
- "style decoupling / swap art style / signature style"

### 与相邻 skill 的区分

- 与 `ip-character-bible` 的区别：本 skill 管"渲染表面"（画风），ip-character-bible 管"身份"（她是谁）；换风格不动身份档案。
- 与 `dof-focus-cinematography`（视频侧）的区别：dof 管镜头景深渲染，本 skill 管配图画风渲染，同属"渲染层"但媒介不同。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **拆分身份/风格两份配置**
   - 完成标准：确认角色档案独立存在，风格文件显式声明"继承身份+仅改渲染表面"。

2. **新增风格而非改写人物**
   - 完成标准：加风格皮肤时只写材质/色彩/轮廓变化，不动年龄感/发型/眼镜/服装/配饰。

3. **跑回归测试**
   - 完成标准：同动作跨 ≥2 画风生成，校验同一人+同表情+同视线；不符即回炉。

4. **守招牌风纪律**
   - 完成标准：默认守一种招牌风；偶尔换用锚点图临时转，不囤皮肤。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 建角色身份系统（走 ip-character-bible）。
- 设计动作/表情（走 ip-action-library / ip-performance-faces）。
- 视频镜头景深渲染（走 dof-focus-cinematography）。

### 作者在书中警告的失败模式

- **身份画风绑死**：现成 Skill 把身份与画风绑死，一换风角色就变脸——根因是没分清"身份 vs 渲染"。
- **招牌风稀释**：为了多变每篇换皮肤，反而把辨识度稀释掉——辨识度来自统一不是多样。

### 作者的盲点 / 时代局限

- 回归测试依赖人工/规则比对，未工程化自动比对（如相似度模型）。

### 容易混淆的邻近方法论

- 与"单纯换滤镜"混淆：本 skill 是身份-渲染解耦的架构原则，不是后期滤镜。
