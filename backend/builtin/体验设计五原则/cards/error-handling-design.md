## I — 方法论骨架 (Interpretation)

交互设计很大篇幅在处理"用户错误"。应对分三层,优先级递减:

1. **设计成不可能犯错(最优)**: 从物理/逻辑上杜绝错误发生。例: 自动挡汽车"除非挂 P 档否则不能启动",根除了"非 P 档启动损坏变速箱/溜车"的错误。
2. **使错误难以发生**: 通过约束(如只允许合法输入、步骤引导)降低出错概率。
3. **帮用户找出并纠正**: 错误仍会发生时,给清晰错误信息与自我解释界面,引导改正。

**慎用自动改正**: 软件"善意"替用户改错常惹人烦(作者以 Word 过度纠错为例——常需关掉"改正"才能工作)。默认不替用户做主,而是呈现清晰错误让其自行修正。

## A1 — 书中的应用 (Past Application)

### 案例 1: 自动挡防错
- **问题**: 非 P 档启动会损坏变速箱、甚至溜车伤人。
- **方法论的使用**: 作者以自动挡"必须挂 P 档才能启动"为"设计成不可能犯错"的绝佳范例。
- **结论**: 防错设计优于事后纠错。
- **结果**: 成为全书的错误处理范本(c05)。

### 案例 2: Word 善意纠错的烦扰
- **问题**: 软件自动改正常规错误。
- **方法论的使用**: 作者指出这类"善意改正"常让用户不得不关掉功能才能工作。
- **结论**: 自动改正需极谨慎。
- **结果**: 说明第三层"帮纠正"不等于"替用户改"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
1. 表单/流程用户总填错、报错看不懂。
2. 设计输入校验、确认步骤、撤销机制。
3. 复盘"用户老在某步卡住/误操作"。
4. 争论"系统要不要自动帮用户改"。

### 语言信号
- "用户总填错怎么办?"
- "报错提示怎么写?"
- "怎么防止误操作"
- "error handling / 防错"

### 与相邻 skill 的区分
- 与 `conceptual-model-consistency` 的区别: 概念模型是"组件如何被理解"; 本 skill 是"出错时系统如何响应",属交互设计另一面。
- 与 `interface-design-defaults` 的区别: interface 关注"最常见行为的顺畅"; 本 skill 关注"错误路径的防护"。

## E — 可执行步骤 (Execution)

1. **优先设计成不可能犯错**
   - 完成标准: 识别高风险错误,用约束/强制步骤从结构上杜绝(如必填校验、禁用非法提交)。
2. **降发生概率**
   - 完成标准: 对非结构性错误加实时校验/引导,减少发生。
   - 判停条件: 若自动改正会替用户做主,改为"清晰提示+用户自改"。
3. **清晰纠错反馈**
   - 完成标准: 错误发生给出具体、可自我解释的信息,指明如何修正,不责怪用户。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill
- 纯内容展示无用户输入,无错误处理场景。
- 不要为"防错"而过度限制正常用户(如禁用所有自由输入)——防错不等于锁死。

### 作者在书中警告的失败模式
- 善意自动改正惹人烦: Word 式过度纠错让用户关功能才能工作。
- 只做"报错"不做"防错": 事后纠错成本高于事前杜绝。

### 作者的盲点 / 时代局限
- 例多为桌面/表单; 今天语音/对话式 UI 的"错误"含误解意图,防错逻辑更复杂(需确认而非强制)。

### 容易混淆的邻近方法论
- 不要与"异常监控/日志"混淆: 本 skill 是面向用户的交互防错,非系统异常捕获。
