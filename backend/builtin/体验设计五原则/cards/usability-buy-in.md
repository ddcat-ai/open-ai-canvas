## I — 方法论骨架 (Interpretation)

问题的标准形态是："我明白可用性重要，可我怎么说服老板——还有他的老板——
让他们重视用户，并允许我花时间做这件事？"

**通行的两条建议，作者都判为次优：**

- **演示 ROI**：收集数据证明某项改进带来了成本节约或收入增长
  （"改这个按钮文案提升了 0.25% 销售额"）。问题是——证明因果**极难**，
  条件不极端严格的话，总会有人跳出来说增量是别的因素带来的。
- **说他们的语言**：改用痛点、触点、KPI、CSI 这类管理热词讲同一件事。
  问题是——学商业语言本身是个挑战，"毕竟那是人们去拿 MBA 学位的原因"。

两条都值得试，但都不是主路径。作者的主路径是**换掉说服的介质**：
不用论证，用**亲历**。

**为什么亲历有效，而报告无效？** 因为差距不在信息量，在体验强度——
"现场看球赛 vs 看晚间新闻集锦"。管理者脑子里有一个想象中的用户
（聪明、有耐心、看得懂我们的措辞），这个想象受论证保护，因为论证只调用同一套认知系统。
而**看着一个真人在自己公司的产品上卡住、皱眉、说出"这是什么意思"**，
直接摧毁那个想象。作者的经验证据很朴素：本来说好露个面待几分钟的高管，
通常会留下来看完——因为"这是他们第一次亲眼看到有人在用公司的网站，
而且画面通常不像他们想象中那么美好"。

**四个动作按获取难度递降排列，可任选一个作为起点：**

1. **请老板及其老板到场**（最高杠杆）。邀请话术不是"来学习"，
   而是"你能来露个面待几分钟，会极大鼓舞团队士气"——把门槛降到最低。
2. **到不了 → 发 3 分钟以内的视频片段**。放内网，配一句有意思的描述和链接，
   邮件发过去。"即使是执行总裁们，也喜欢观看短视频。"
3. **用自己的时间做第一次测试**，不申请许可、不花钱、找志愿者。
   关键是**选目标的策略**：挑一个你**已经知道存在严重可用性问题、
   而且这个问题很好修、修它不需要把很多人牵扯进来讨论或同意**的地方
   （例如重命名一个词不达意的按钮）。然后测试 → 修复 → 公开宣传。
   如果能顺手测量改善（如客服来电量下降），就测。
4. **测竞品**，办成午餐活动。这一招组织阻力最低：**任何人都想了解竞争对手，
   而且测的不是自家东西，不涉及内部任何人的个人利益**，没人需要防守。

**还有两条姿态层面的告诫，比技巧更重要：**

- **理解管理层。** 作者的反转很关键：同理心是可用性工作的**职业条件**，
  但从业者常常只把它给用户，不给老板。他要求把这份同理心分一点过去——
  **不是"我怎么找到办法激发他们、好让他们做我想做的事"**（那是操纵），
  而是真正去理解他们的处境，给予情感上的关注。
- **摆正自己的位置。** 商业社会里每个人都是大齿轮组里的小齿轮。
  抱着"向普罗大众宣扬真理"的态度——不论在可用性还是别的事情上——
  效果都很难保证。**你的主要角色是分享知识，而不是告诉别人该怎么做。**

最后是一条职业边界：可用性工作是"为用户呐喊"。若有人要求你用这些方法
去**操控**用户而非服务用户，那不在你的职责范围内。

## A1 — 书中的应用 (Past Application)

### 案例 1: 只想露个面的高管留了下来
- **问题**：如何让掌握资源的人真正改变对用户体验的看法。
- **方法论的使用**：邀请高管来观察一次测试，明说"待几分钟就行，会鼓舞团队士气"。
- **结论**：改变立场的不是论证，是认知冲击——第一次亲眼看到真人使用自家产品，
  且画面比想象中糟。
- **结果**：高管超时停留，成为作者眼中"效果最好的策略"。

### 案例 2: 用自己的时间挑一个"必赢"的目标
- **问题**：没有预算、没有许可、没有信任，第一步从哪迈。
- **方法论的使用**：不申请许可，不花钱，非正式地找志愿者；**目标选择上刻意做局**——
  挑一个已知有严重问题、修起来容易、且不需要多方同意的点（如改一个词不达意的按钮名）。
  测试 → 修复 → 公开宣传，能测量就测量（客服来电减少）。
- **结论**：第一次尝试必须产出**可见的改善**，否则不会有第二次。
- **结果**：用一次小胜换取继续做的空间。

### 案例 3: 把测竞品办成午餐活动
- **问题**：团队对"被测试自己的作品"有天然防御。
- **方法论的使用**：改测竞争对手——人人想看，且不触及任何人的利益。
- **结论**：绕开利益防御是启动阻力最低的路径。
- **结果**：既普及了方法，又收获了竞品洞察，还成为团队活动。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. "老板/客户/业务方根本不在乎用户体验，只看功能上线和排期。"
2. 申请不到做研究/测试的时间、预算、人力。
3. 团队里只有自己一个人在意这件事（"one-person UX team"）。
4. 有人要求先给出 ROI 测算才批准。
5. 决策者坚持自己就是典型用户，用自己的偏好定方案。
6. 做过一次测试，报告发出去了，没有任何反应。
7. 想推动的不是可用性，而是任何**需要决策者亲历才能相信**的事
   （客服一线轮岗、跟车配送、去店里排一次队、自己走一遍报销流程）。

### 语言信号（用户的话里出现这些就应激活）

- "老板不重视 / 领导不认 / 说服不了业务方"
- "怎么申请预算 / 排不进需求 / 没人给我时间"
- "要不要先算 ROI / 他们要看数据"
- "只有我一个人在乎 / 团队里唯一的 UX / 孤军奋战"
- "报告发了没人看 / 讲了很多遍还是没用"
- "stakeholder buy-in / get management support / 向上管理"

### 与相邻 skill 的区分

- 与 `nih-co-creation-buyin` 的区别：那个的机制是**共创**——让对方参与产出，
  以消除"非我发明"的排斥；本 skill 的机制是**亲历**——让对方目睹现实，
  以摧毁其想象中的用户。选型判据：对方**已有一个竞争方案且抵触你的**→ 那个；
  对方**根本不认为存在问题** → 本 skill。两者可串联：先亲历建立问题共识，再共创出方案。
- 与 `foot-in-the-door` 的区别：那个是通过小承诺逐步升级到大承诺（承诺一致性机制）；
  本 skill 的第 1 步"来露个面待几分钟"表面上很像，但目的不是**积累承诺**，
  而是**制造一次不可逆的认知冲击**。冲击一次就够，不需要阶梯。
- 与 `average-user-fallacy` 的区别：那个处理**团队内部关于用户偏好的争论**
  （谁说了算），本 skill 处理**根本没人愿意投入**（要不要做）。
  常见顺序：先本 skill 拿到支持，再用那个裁决争论。
- 与 `diy-usability-test` 的区别：那个是**怎么把测试跑起来**（方法），
  本 skill 是**怎么让测试有人看、有资源、有下文**（组织）。
  本 skill 的每个动作都依赖那个作为载体。
- 与 `flaw-first-credibility` 的区别：那个通过主动暴露缺点建立可信度（说话的技巧）；
  本 skill 干脆不靠说，靠让对方自己看见。

## E — 可执行步骤 (Execution)

1. **先判断阻力类型（不要走错路）**
   - 若对方**不认为存在问题**（"我们的产品挺好用的"）→ 走本 skill 的亲历路径。
   - 若对方**认为有问题但有别的方案** → 转 `nih-co-creation-buyin`。
   - 若对方**已支持但排不上期** → 转 `usability-debrief-triage` 谈取舍，不必再说服。
   - 完成标准：写下一句"阻力是 ___ 型"，并据此选定路径。

2. **动作 A：请他到场（首选，尽一切可能达成）**
   - 邀请话术压低门槛：**"我们下周三上午做几场测试，你能过来露个面待几分钟吗？
     对团队会是很大的鼓舞。"** 不说"来学习"，不说"来听结论"。
   - 邀请对象包括老板**和他的老板**。
   - 安排：观察室独立、屏幕共享清晰、给他准备一张纸让他自己记"最严重的三条"。
   - 完成标准：他到场了，并且看到了至少一位真实用户在真实卡顿。

3. **动作 B：到不了 → 3 分钟视频**
   - 剪一段**不超过 3 分钟**的关键片段（用户卡住、说出困惑的原话那一段最有效）。
   - 放内网/共享盘，邮件或消息里配**一句有意思的描述** + 链接。不要附长报告。
   - 完成标准：视频≤3 分钟，一句话描述，一个链接，无附件。

4. **动作 C：自费自办第一次测试，挑必赢的目标**
   - 不申请许可、不申请预算，找志愿者，非正式进行。
   - **目标选择三条件同时满足**：① 你已经知道这里有严重可用性问题
     ② 这个问题很容易修 ③ 修它不需要牵扯很多人讨论或同意。
   - 顺序：测试 → 修复 → **公开宣传**。
   - 若能低成本测量改善（客服来电量、工单数、放弃率），就测出来。
   - 完成标准：产生了一个**可见、可归因、可讲述**的改善。

5. **动作 D：测竞品，办成午餐活动**
   - 选一个大家都好奇的竞争对手，公开邀请，提供午餐。
   - 优势：无人利益受损，人人想看，顺带普及了方法本身。
   - 完成标准：非本团队的人也来了，且事后有人问"我们自己什么时候测"。

6. **姿态校准（每次沟通前自检两句）**
   - **"我是在理解他的处境，还是在找办法让他做我想做的事？"**
     后者会被识别为操纵，且效果不佳。真正关心他面对的约束（预算、排期、上级要求）。
   - **"我是在分享知识，还是在宣讲真理？"** 传教式姿态在任何议题上都难以奏效。
   - 完成标准：能说出对方当前最头疼的三件事，且你的提议至少与其中一件有关。

7. **ROI 与黑话作为补充手段（不作为主路径）**
   - 若组织文化强制要求数字，用动作 C 里那个**可测量的小胜**作为证据，
     而不是从头构建一套 ROI 模型。
   - 明确风险：因果归因几乎必然被质疑，不要把全部筹码押在这里。
   - 完成标准：数字是"亲历"的补充证据，不是唯一论据。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **说服对象是用户/客户而不是内部决策者**：本 skill 全部动作都基于
  "让决策者目睹自家产品的真实使用"，对外不成立。
- **对方已经支持，只是资源冲突**：这是排期问题不是认知问题，转
  `usability-debrief-triage` 或直接谈取舍。
- **对方抵触的是你这个人/你这个方案，而非议题本身**：转 `nih-co-creation-buyin`，
  让他参与产出。
- **组织的问题是激励结构而非认知**：若产品经理的考核只看上线数量、
  客服的考核只看接通时长，那么看多少场测试都不会改变行为。
  此时要动的是考核口径，不是认知（见下方"作者的盲点"）。

### 作者在书中警告的失败模式

- **押注 ROI 论证**：因果证明难度高，"总会有人跳出来说这些增加的价值是别的因素带来的"。
- **靠学管理黑话取胜**：那是拿 MBA 的难度。
- **只发报告不给现场**：报告 vs 现场 = 晚间新闻集锦 vs 现场看球。
- **传教姿态**：抱着"向普罗大众宣扬真理"的态度，"效果总是很难保证"。
- **只对用户有同理心，对老板没有**：作者点名这是从业者的常见盲区。
- **第一次尝试没做出可见改善**：会直接终结后续机会，所以目标必须精心挑选。

### 作者的盲点 / 时代局限

- **假设"看见即相信"**。当决策者的行为由**激励结构**决定时（考核只看 GMV、
  上线数、需求吞吐量），亲历只能改变态度，改变不了行为——他会说
  "确实做得不好，但这季度先上功能"。**本 skill 缺少对激励结构的处理**，
  遇到这种情况需要另找杠杆（改考核口径、把体验指标写进 OKR、
  或借客诉与舆情事件推动）。
- **假设组织允许你自作主张**。动作 C（不申请许可、用自己的时间做测试）
  在管控严格、合规要求高、或员工与客户接触受限的组织里可能违规。
  在这类环境需先取得最小许可。
- **假设你能约到高管**。层级深、外包制、甲乙方关系中，
  "请他老板来看一上午"往往不可行。此时动作 B（3 分钟视频）与动作 D（测竞品）
  是更现实的入口。
- **样本是作者的咨询经历**，即甲方已经付费请他来了——起点上就存在一定的
  组织意愿。完全零支持的环境下，效果会打折。
- **时代局限**：第 3 版正文写于 2013 年。章中关于职业名称的讨论
  （可用性/信息架构 → UX/UXD 的更名之争）**已完全过时**；
  当年的"现场观察 + 内网视频"在今天有更低成本的等价实现
  （远程会议旁听、录屏切片、异步回放、无人值守远程测试平台）。
  **具体形式需在当代远程/混合办公语境下重新检验；
  "亲历胜过论证"的核心机制不受影响，甚至因视频获取更容易而更好实施。**
- **诊断非生成**：本 skill 解决"如何拿到支持"，不解决"拿到支持后做什么"。
- 作者对"故意不重视用户是理性商业选择"的情形（低竞争、垄断、
  一次性交易、账号迁移成本极高）未作讨论——在这些场景里，
  可用性投入的回报确实可能很低，说服失败未必是方法问题。

### 容易混淆的邻近方法论

- **Tomer Sharon《It's Our Research》**：作者推荐书目，专门讲用户研究的
  stakeholder buy-in，比本章系统得多。
- **Leah Buley《The UX Team of One》**：写给组织里唯一的 UX 从业者，
  第 3、4 章有大量可用资源。
- **变革管理（Kotter 八步）**：更宏观的组织变革框架；本 skill 相当于
  其中"制造紧迫感"一步的一个极低成本实现。
- **同理心地图 / 客户旅程共创工作坊**：也能建立共识，但需要更多组织资源与协调，
  且更偏共创机制（转 `nih-co-creation-buyin`）。
