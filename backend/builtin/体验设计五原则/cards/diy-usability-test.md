## I — 方法论骨架 (Interpretation)

大多数团队不做可用性测试，不是因为不信它有用，而是因为脑子里的"可用性测试"是一个
需要实验室、单向玻璃、专业研究员、几万块预算和三周周期的项目。Krug 干的事情，
是把这个项目**降级成一件例行公事**：每月一个上午，三个人，一顿午饭，结束。

几个反直觉但关键的设定：

**为什么是三个人？** 因为目标不是"证明"什么，也不是穷举所有问题，而是发现并修掉
**最严重的那几个**。而且现实是：你永远修不完你发现的问题。测八个人只会让待修清单更长，
不会让修复速度变快。

**为什么每月一次？** 因为要能**坚持**。一个上午是多数团队能持续挤出的最大额度。
一旦流程复杂或耗时，忙起来第一个被砍的就是它。节奏优先于严谨。

**为什么先定日期？** 先在日历上锁死"每月某个上午"，再决定那天测什么。反过来
（等做好了再约测试）永远约不上。

**为什么可以宽松招募？** 因为大部分可用性问题与领域知识无关，一个聪明的外行照样会
在你的命名和布局上卡住。（这条有重要例外，见 B 段。）

**为什么"边做边说"（thinking out loud）？** 因为你需要的不是"他有没有做到"，
而是"他为什么这么做、卡在哪一刻、当时在想什么"。这是录屏和埋点给不了的东西。

**主持人的核心纪律是不帮忙。** 用户一卡住，所有人的本能都是提示。一旦提示，
这次观察就作废了。标准话术只有几句："你在想什么？""如果我不在这儿，你会怎么做？"

还有一条动机层的判断，重要到必须单列：**测一位用户比不做测试好一倍**，
早期粗糙测试的价值远高于后期精致测试。所以不要因为"样本太小""还没做完""不够严谨"
而推迟——可以测草图，测纸面原型，测竞品。

## A1 — 书中的应用 (Past Application)

### 案例 1: Janice 测 eLance 的完整实录
- **问题**：如何让没做过测试的人知道一场测试具体长什么样。
- **方法论的使用**：Krug 给出一整场逐字实录——开场白（"我们不是在测试你，我们是在测试网站。
  没有什么正确或错误的答案"）、主页巡览（只看不点，说印象）、任务执行、
  参与者卡住时主持人如何忍住不帮。
- **结论**：测试的门槛远比想象的低，脚本可以复用。
- **结果**：读者可以照着实录直接跑第一场。

### 案例 2: 每月一个上午的节奏设计
- **问题**：团队做过一两次测试后就再也没做过。
- **方法论的使用**：作者把节奏简化到极致，并明确理由——"这样能保持测试简单，
  所以你们能坚持进行。每个月一个上午是很多团队能为测试留出的最大时间了。"
- **结论**：可持续性是第一约束，严谨性排第二。
- **结果**：测试从项目变成习惯。

### 案例 3: 用竞品作为起点
- **问题**：产品还没做出来，或不想让团队在自己的作品上被批评。
- **方法论的使用**：先测竞争对手——任何人都想了解竞品，而且不涉及内部任何人的利益。
- **结论**：测竞品既能获得洞察，又能降低组织阻力。
- **结果**：成为团队第一次测试的最佳切入点。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 团队为某个体验问题争论不下，需要真实证据来裁决（通常由 `average-user-fallacy` 转来）。
2. 想知道用户实际怎么用某个页面/流程/表单/文档，但没有预算和研究资源。
3. 有人问"要不要请专业用研机构""这样的样本量有意义吗"。
4. 改版前想先摸清现状，或改版后想验证有没有变好。
5. 要测的不是软件：一份合同、一张表单、一门课件、一套内部流程、一个申请指南。
6. 团队从来没做过测试，想知道第一场怎么起步。
7. 想通过测试竞品来低成本获得洞察。

### 语言信号（用户的话里出现这些就应激活）

- "做个用户测试 / 找几个人试试 / 拉几个同事来点点"
- "用户到底怎么用的 / 我们得看看真实用户"
- "没预算 / 要不要请专业机构 / 三个人够吗"
- "怎么招募 / 测试脚本怎么写 / 要不要付钱给参与者"
- "usability test / user testing / think aloud / moderated test / recruit participants"

### 与相邻 skill 的区分

- 与 `average-user-fallacy` 的区别：那个负责**把问题问对**（识别信仰之争、改写命题）；
  本 skill 负责**把测试跑起来**。理想顺序是先那个后这个。
- 与 `usability-debrief-triage` 的区别：本 skill 到"拿到观察记录"为止；
  那个处理观察之后的排序、取舍与修复决策。两者是同一天上下午的关系。
- 与 `dont-make-me-think-audit` 的区别：那个是**不用真人**的专家式自查（快、便宜、
  但受作者视角污染）；本 skill 是**用真人**的实测（慢一点、更可信）。
  常见组合：先自查列假设，再实测验证。
- 与 `habit-testing` 的区别：那个是用数据衡量产品有没有形成使用习惯（留存/队列分析）；
  本 skill 是定性观察单次任务能否完成。

## E — 可执行步骤 (Execution)

1. **先定日期，再定测什么**
   - 在日历上锁死"每月某个固定上午"，作为团队例行事项发出邀请。
   - 完成标准：下一次测试的日期已进日历且团队可见。

2. **确定测什么与测试命题**
   - 明确 1–3 个要回答的具体命题（不是"看看好不好用"，而是
     "新用户能否在无提示下完成 X"）。
   - 可测对象包括：线上产品、原型、纸面草图、竞品、文档、表单、流程。
   - 完成标准：命题写成可判定的句子。

3. **招募 3 名参与者**
   - 默认宽松招募（朋友、同事的朋友、附近的人、社群里报名的人），付酬。
   - **例外检查**：若产品有强领域门槛（医疗、金融风控、开发者工具、专业后台、
     多角色审批流）→ 必须严格招募真实角色，否则结论会误导（见 B 段）。
   - 完成标准：3 人已确认时间；招募标准已写明并说明理由。

4. **写任务脚本与开场白**
   - 任务 3–4 个，用**用户的目标**表述（"你要给孩子买一双雨鞋，预算 200 以内"），
     不要用界面词汇（"点击类目筛选"）。
   - 开场白固定包含：不是测你、是测网站；没有对错；请边做边说；卡住了也没关系；
     我不能帮你但事后可以回答；全程录屏，仅内部使用。
   - 完成标准：脚本可被另一个人照着念。

5. **执行（每人约 1 小时）**
   - 顺序：开场白 → 主页/首屏巡览（**只看不点**，说出印象与预期）→ 任务逐个执行 →
     结束提问。
   - 主持人纪律：**不提示、不解释、不辩护**。允许的话术只有——
     "你现在在想什么？""你觉得会发生什么？""如果我不在这儿，你会怎么做？"
   - 旁观：团队在另一间屋子看屏幕共享，各自记录"最严重的三条"。
   - 完成标准：3 场完成，每个旁观者都交了自己的三条。

6. **移交总结**
   - 当天午餐会合并清单，转 `usability-debrief-triage` 执行排序与决策。
   - 完成标准：总结会已开始，且团队当场产出下月要修的清单。

7. **降级方案（时间/人力极度受限时）**
   - 找 1 个人、测 20 分钟、只测一个任务。依据："测一位用户比不做测试好一倍。"
   - 完成标准：哪怕降级，也真的做了一次而不是又推迟。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **要回答"用户想不想要这个"**。作者本人明确警告：这不是可用性测试适合衡量的方面，
  那是市场研究的问题。用测试来论证"用户想要"，是把工具用错。
- **要证明改版带来了多少收益**。三人定性测试没有统计效力，不能用于汇报"提升了 X%"。
  那需要 A/B 测试与埋点。
- **只需要分析已有的问题清单**：直接转 `usability-debrief-triage`。
- **要验证概念、价值主张、是否有需求**：那是焦点小组/深访/市场研究的射程
  （见下方"容易混淆"）。
- **成熟且已多轮打磨的产品**：前 3 人可能发现不了新问题，此时需要更大样本、
  更细分人群或转向定量。

### 作者在书中警告的失败模式

- **主持人忍不住帮忙**。一旦提示，这次观察作废。
- **把可用性测试和焦点小组混为一谈**。焦点小组是**一群人说想法**，适合项目最早期
  验证概念与价值主张；可用性测试是**一个人做任务**，适合验证具体实现，贯穿全程。
  用焦点小组定界面，收集到的是群体压力下的臆想。
- **因为"不够严谨/不够完整"而推迟测试**。作者的反驳是：测一位用户比不测好一倍，
  早期粗糙测试的价值远高于后期精致测试。
- **测得太多修不完**。发现问题的速度永远快于修复速度，这正是只测 3 人的理由。

### 作者的盲点 / 时代局限

- **"宽松招募"在强领域知识产品中不成立**。作者主张"几乎任何人都能测"，
  但在医疗、金融风控、开发者工具、B 端多角色系统里，非目标用户暴露的问题
  （看不懂术语、不知业务流程）与真实用户的问题（字段难找、状态机不清、缺批量操作）
  几乎不重叠，会误导修复优先级。这类产品必须严格招募。
- **"3 人足够"是经验判断而非证明**，作者自己承认。其前提是"存在少数高频严重问题"，
  对打磨成熟的产品边际收益显著下降。
- **时代局限**：第 3 版正文写于 2013 年，书中的工具选型（GoToMeeting、WebEx、
  Camtasia、AmCap、自制摄像装置）**已全部换代**；书中说"移动屏幕录制/共享工具还没上市"，
  而今天 iOS/Android 均内置录屏，远程无人值守测试平台也已成熟。
  **凡涉及具体工具与设备的操作细节，需在当代语境下重新检验；流程与纪律部分仍然成立。**
- **本方法只能做局部优化**。一个每月虔诚做三人测试的团队，可以把一个方向错误的产品
  打磨得极其顺滑。可用性是必要条件不是充分条件——它不回答"这个产品该不该存在"。
- 作者对定量方法基本回避，未给出定性与定量的分工方案。

### 容易混淆的邻近方法论

- **焦点小组**：人数（群体 vs 单人）、行为（说 vs 做）、时机（最早期 vs 全程）
  三方面都不同。选型判据：你的问题是"该不该做/值不值得"→ 焦点小组或市场研究；
  是"做出来能不能用"→ 本 skill。
- **用户访谈 / 深访**：了解动机、场景、痛点；不观察操作。
- **A/B 测试**：能裁决哪个数字更高，不能告诉你为什么。与本 skill 互补：
  定量选方向，定性找原因。
- **无人值守远程测试**：规模更大、成本更低，但失去了追问与观察表情/犹豫的能力。
