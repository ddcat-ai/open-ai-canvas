## I — 方法论骨架 (Interpretation)

这是一个**元认知工具**：它不修界面，它修你脑子里那个"用户"。

做东西的人默认脑中住着一个理想用户——会读、会比较、会弄懂。这个假设一旦成立，
很多决策就自动跟着来了：写长说明、设计精细的选项体系、做用户培训、在争论里说
"用户应该先看一下这段"。这些决策全部建立在一个不存在的人身上。

真实的人是这样的：

**① 扫描（scan）**。不逐字读，只快速扫视，寻找与当下任务相关的词和视觉线索。
原因很朴素：赶时间；知道页面上大部分内容与自己无关；而且已经习惯扫描了。
推论：你写的绝大多数字根本不会被读到。关键词不在开头，就等于不存在。

**② 满意即可（satisfice）**。选"第一个看起来合理的"，不选最优。原因：猜错的代价很低
（点回退就行）、等待权衡的代价很高、把所有选项比一遍不划算、而且猜错还挺有意思。
推论：把 8 个选项打磨到同样精致是浪费，用户只会看前两三个；真正要做的是让
"第一个看起来合理的"恰好是对的。

**③ 勉强应付（muddle through）**。用户不理解系统的真实工作机制也照样用下去，
而且长期不去弄明白。Krug 的狠话是：所谓专家，只是在更高层次上勉强应付。
推论："让用户理解我们的模型"这个目标基本不可达；更现实也更值钱的目标是
"让勉强应付也能顺利完成任务"。

三条都不是缺陷，不能靠教育、培训、说明文档修正。它们是**必须被接受的设计约束**。
本 skill 的用法就是：把当前决策里那条隐藏的用户假设拎出来，逐条对照，
然后把决策改写成"接受约束"的版本。

## A1 — 书中的应用 (Past Application)

### 案例 1: 为什么加说明没用
- **问题**：团队发现某处用户老出错，第一反应是加一段说明文字。
- **方法论的使用**：Krug 用"扫描"这条事实反推——说明文字位于用户扫描路径之外，
  且与当下任务无关，因此不会被读到。
- **结论**：说明不会被读，加了等于没加。
- **结果**：正确动作变成重做那个元素，而不是给它配一段解释。

### 案例 2: 用户为什么不找最优路径
- **问题**：设计者精心设计了层级分类，希望用户逐层比较后选到最合适的入口。
- **方法论的使用**：用"满意即可"解释——用户猜错的成本只是点一下回退，
  而认真比较的成本是持续的注意力投入，收益比不划算。
- **结论**：用户会点第一个看着差不多的，不会比较。
- **结果**：设计目标从"让选项体系严谨完备"改为"让最可能正确的那个第一眼就显眼"。

### 案例 3: 专家也在勉强应付
- **问题**：团队假定重度用户会真正理解系统。
- **方法论的使用**：Krug 指出连专家也只是在更高层次上勉强应付，
  很少有人真的去搞清楚背后的机制。
- **结论**："用户会学会的"是一个不可依赖的假设。
- **结果**：不再把复杂度寄希望于用户的学习曲线。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 写了详细的说明/公告/引导，但用户还是不知道，团队想不通为什么。
2. 团队在争论"用户应该会看到/应该能理解/我们已经告诉他们了"。
3. 要做用户培训、写操作手册、录教程视频之前，先判断这条路可不可行。
4. 精心设计的分类/选项体系没人用，用户总走那一两条路。
5. 需要向老板/同事解释"为什么不能靠加提示解决"。
6. 写任何"别人要在赶时间的状态下读"的东西（周报、通知、错误消息、群公告）。

### 语言信号（用户的话里出现这些就应激活）

- "我明明写了 / 上面就有说明 / 公告里写了啊"
- "用户为什么不读 / 他们不看说明 / 得培训一下用户"
- "用户应该会理解 / 用户应该能找到"
- "为什么大家都走那条路，明明另一条更合适"
- "users don't read / nobody reads the instructions / scanning / satisficing"

### 与相邻 skill 的区分

- 与 `dont-make-me-think-audit` 的区别：本 skill 修的是**假设**（你脑中的用户是谁），
  那个 skill 修的是**具体界面**（哪里有问号）。本 skill 通常是它的上游。
- 与 `omit-needless-words` 的区别：那个给出删文字的具体动作；本 skill 给出为什么必须删
  的理由（扫描），以及"删了也不影响，因为本来就没被读"的依据。
- 与 `wysiati-evidence-audit`（卡尼曼 WYSIATI）的区别：那个查的是**你自己**的结论
  被有限证据牵着走；本 skill 查的是**你对别人**的行为假设失真。
- 与 `bmat-behavior-diagnosis` 的区别：B=MAT 处理"行为没发生"的归因；本 skill 处理
  "行为发生了但方式和你想的完全不同"。

## E — 可执行步骤 (Execution)

1. **把当前决策里隐藏的用户假设写成一句话**
   - 格式："我假设使用者会 ____。"
   - 完成标准：能写出至少一条形如"会读完这段/会比较这几个选项/会理解这个流程"的句子。

2. **逐条对照三事实，判定该假设是否成立**
   - 扫描：这段文字在扫描路径上吗？关键词在开头吗？（不在 → 假设不成立）
   - 满意即可：用户有动力比较全部选项吗？猜错成本高吗？（成本低 → 不会比较）
   - 勉强应付：用户需要理解机制才能完成任务吗？（需要 → 高风险）
   - 完成标准：每条假设都有"成立/不成立/需实测"的结论。

3. **对不成立的假设，改写为"接受约束"的版本**
   - 会读完 → 改为：关键信息前置到前 5 个字 + 视觉上独立成块。
   - 会比较 → 改为：让最可能正确的选项在第一眼位置且最显眼，其余折叠。
   - 会理解 → 改为：不要求理解，只要求勉强应付也能走通；出错时可低成本回退。
   - 完成标准：每条改写都是一个具体可执行的动作，不是原则复述。

4. **检查例外条件（防止过度套用）**
   - 若属高涉入决策（金额大、不可逆、涉及健康/法律）→ 标注"用户会真读"，
     本 skill 的结论减半使用，信息完整性优先。
   - 判停条件：若三条例外全部命中，直接终止并说明本 skill 不适用。

5. **输出一张对照表**
   - 列：原假设 / 三事实判定 / 改写后的动作 / 验证方式。
   - 完成标准：表中每行的"验证方式"可执行（通常指向 `diy-usability-test` 找 1–3 人实测）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **高涉入决策场景**：购房、保险、医疗方案、大额 B 端采购、法律条款、投资合同。
  这些场景里用户会非常仔细地逐字阅读并认真比较，"用户不读"的结论会直接导致
  信息披露不足与合规风险。三事实主要适用于**低涉入、低试错成本**的场景。
- **专家用户的高频工作流**：重度用户确实会为常用工具建立准确的心智模型和肌肉记忆，
  "勉强应付"对他们的解释力显著下降。
- **已经确定要出设计方案时**：本 skill 只负责纠正假设，不生成方案。

### 作者在书中警告的失败模式

- 把三事实当成"用户素质低"的抱怨，进而推导出"所以要教育用户"——这是完全相反的结论。
  作者的立场是：这三条是设计者必须适应的现实，不是待修正的缺陷。
- 用"我们已经写了/说了/公告了"来免责。信息发出 ≠ 信息到达。

### 作者的盲点 / 时代局限

- 本书第 3 版正文写于 2013 年，观察对象是英文桌面 Web 用户。**中文语境需要校准**：
  中文无空格分词，扫描的视觉锚点是词组块而非首字母，因此"关键词前置"在中文里更重要；
  中文单字信息密度高，删减尺度需要重新把握。
- 完全没有覆盖**信息流/短视频/算法推荐**这类无目的消费场景——那里的用户行为模型
  （无限滑动、被动接收）与三事实不同源。
- 三事实没有量化证据支撑，是作者长期观察得出的定性结论。

### 容易混淆的邻近方法论

- **Herbert Simon 的 satisficing**：原本是关于有限理性的一般理论，Krug 把它专门化到
  界面选择行为上。引用时不要把两者的适用范围混为一谈。
- **尼尔森"用户如何阅读网页"（F 型浏览）**：眼动研究给出的是扫描的**路径形状**，
  本 skill 给出的是扫描的**行为动机**，两者互补。
