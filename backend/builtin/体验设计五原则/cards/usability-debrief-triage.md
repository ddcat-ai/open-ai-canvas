## I — 方法论骨架 (Interpretation)

发现问题的速度永远快于修复问题的速度。所以总结会真正要解决的不是"我们发现了什么"，
而是**"在资源恒定不足的前提下，如何保证被修掉的是最严重的那几个"**。

Krug 观察到的失败机制很具体：团队天然会漂移向容易的问题。因为严重问题往往牵扯多人、
需要决策、要动结构；而"改个错别字、调个间距"能立刻打勾。于是每次复盘都很热闹，
每次都修了十几条，最严重的那条永远挂在那里，一年后还在。

对抗这个漂移的机制有四层：

**第一层：先写后说，禁止讨论。** 每人独立写下自己看到的"最严重三条"，先全部上墙，
过程中**不讨论**。讨论会引入锚定——嗓门大的人、职级高的人、最先发言的人会重塑其他人的判断。
而且必须是"观察到的"问题，不是"我觉得可能有问题"。

**第二层：投票 → 评级 → 排成有序列表。** 从多到少不叫排序，一到十的强制排名才叫排序。

**第三层：排满就停。** 从最上面开始，逐条写"下个月怎么修、谁负责、要什么资源"，
**当下个月的时间和资源被排满时立刻停下**，剩下的不管。这一步是整个方法的关键约束：
它把"问题清单"强行转换成"承诺清单"。一份没人认领、没有截止日、长度超过产能的清单，
等于没开这个会。

**第四层：修复标准是"移出前十"，不是"完美解决"。** 一个粗糙的调整只要让这个问题不再是
最严重的之一，就算完成。追求完美修复会让第一条就吃掉全部预算。

然后是四条**反直觉的过滤与决策规则**：

1. **抵制添加的冲动。** 看到用户困惑，第一反应是"加个说明/加个引导/加个 tooltip"。
   但困惑通常是**已有元素造成的**，加说明只是在噪声上再叠一层噪声。默认动作应该是
   "先找能拿掉什么"。
2. **忽略 Kayak（皮划艇）问题。** 用户短暂走岔、但没人帮忙就自己回到正轨的片段，
   不算问题。判据三条：他马上意识到偏了 / 不需要帮助就回来了 / 没有打乱他的节奏。
   "第二次猜对就已经可以了。"用篮球术语说：没有伤人，不算犯规。
3. **不要太看重用户要求的新功能。** "如果它能做 XX 就好了"多数是随口一说——追问细节时
   用户自己往往会说"仔细想想我可能不会用"。真正的好点子有个识别特征：
   你听完的第一反应是"为什么我们没早点想到？！"
4. **另立"够得着的果子"清单。** 不严重但极易修的问题单独一份。"极易"的定义很硬：
   一个人一小时内能做完，且不需要任何不在会议室里的人点头。

## A1 — 书中的应用 (Past Application)

### 案例 1: 大型高资金网站为何仍有严重可用性问题
- **问题**：钱和人都不缺，为什么严重问题长期不修。
- **方法论的使用**：Krug 归因于分诊机制缺失——"那个功能马上要改了，留到那时候再说"、
  "修一个难的不如修一堆简单的"，这两句话反复出现，构成系统性漂移。
- **结论**：不是能力问题，是排序纪律问题。
- **结果**：确立"最严重的问题最先修"作为独立原则。

### 案例 2: Kayak 问题的过滤
- **问题**：一场测试会产生大量"用户走错了一下"的片段，团队倾向于全部记下来。
- **方法论的使用**：作者给出明确的三条忽略判据，把这类噪声主动排除出清单。
- **结论**：保护有限的修复预算，比记录完整更重要。
- **结果**：清单变短，短到能被真正修完。

### 案例 3: "加个说明"的第一反应
- **问题**：测试中用户看不懂某个区域，团队立刻提议加注释。
- **方法论的使用**：作者反向要求——先问"能不能拿掉某个让人混淆的东西"。
- **结论**：困惑的成因通常是多余，而不是缺失。
- **结果**：形成"删除优先于添加"的默认动作，与「文字减半」同源。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 刚做完可用性测试/走查/内测，手上一堆观察记录，不知道从哪下手。
2. 问题清单越来越长，每次会议都在加，从来没变短过。
3. 团队争论"先修这个还是先修那个"，或倾向于挑软柿子捏。
4. 用户反馈、客诉、应用商店评论、评审意见堆积，需要分诊。
5. 有人提议"加个说明/加个新手引导"来解决困惑。
6. 用户提了一堆新功能诉求，不知道该不该接。
7. 复盘会开完了但没人认领任何事项。

### 语言信号（用户的话里出现这些就应激活）

- "测完了 / 收集了一堆问题 / 反馈太多了 / 修不完"
- "先修哪个 / 怎么排优先级 / 这个严重吗"
- "要不要加个说明 / 加个引导 / 加个提示"
- "用户说想要 XX 功能"
- "复盘会 / 总结会 / debrief / triage / prioritize issues / severity"

### 与相邻 skill 的区分

- 与 `diy-usability-test` 的区别：那个负责**产出观察记录**（上午）；本 skill 负责
  **把观察变成承诺**（午餐）。两者是同一天的上下半场，可连续调用。
- 与 `omit-needless-words` 的区别：那个在文案层面做删除；本 skill 是在**决策层面**
  把"删除"设为默认解法，作用于任何元素（功能、控件、步骤、说明）。
- 与 `dont-make-me-think-audit` 的区别：那个负责**发现**自明性问题；
  本 skill 负责**在一堆已发现的问题里做取舍**。
- 与 `premortem-doubt-injection` 的区别：那个是决策**前**注入怀疑防止群体过度自信；
  本 skill 是决策**后/观察后**做资源分配。机制与时点都不同。
- 与产品需求优先级方法（RICE / KANO / MoSCoW）的区别：那些排的是**要做什么新东西**、
  依据是价值与成本估算；本 skill 排的是**已经坏掉的东西**、依据是观察到的严重度，
  且带有硬性的产能截断规则。

## E — 可执行步骤 (Execution)

1. **收集：每人独立写"最严重的三条"**
   - 每位观察者按场次各写 3 条（3 场即 9 条），**全程不讨论**。
   - 硬约束：必须是**观察到发生过**的问题，不是推测的问题。
   - 全部贴/写到白板，重复项打勾计数。
   - 完成标准：所有人的条目都在墙上，且没有发生任何辩论。

2. **选出前 10**
   - 非正式投票，或直接从打勾数最多的开始。
   - 完成标准：候选池收敛到 10 条以内。

3. **强制评级 1–10**
   - 1 为最严重，重新誊写成有序新列表，条目之间留白（后面要写方案）。
   - 完成标准：不存在并列，每条都有唯一名次。

4. **自上而下写修复承诺，排满即停**
   - 逐条写：粗略方案 / 负责人 / 所需资源 / 截止日（下次测试之前）。
   - **当下个月的时间与资源排满，立刻停止**，下面的条目本轮不处理。
   - 修复标准是"把它挤出最严重列表"，不是"完美解决"。
   - 完成标准：每条被采纳的问题都有人名和日期；会议在"排满"处结束而非"排完"处结束。

5. **对每条应用"先删后加"检查**
   - 提问顺序固定：先问"能拿掉什么让它不再混淆？"，无解时才考虑添加。
   - 完成标准：所有"加说明/加引导"类方案，都记录了被否决的删除方案或说明为何删不掉。

6. **过滤 Kayak 问题**
   - 三条同时满足则剔除：马上自觉偏离 / 无需帮助自行回正 / 未打乱其活动。
   - 完成标准：清单里不含"用户点错一下又点回来了"这类条目。

7. **单列"够得着的果子"**
   - 标准：一人一小时内可完成，且不需要会议室外任何人同意。
   - 完成标准：这份清单与主清单物理分开，不占用主清单的名额与讨论时间。

8. **处理新功能诉求（单独归档）**
   - 默认不进本轮清单。真好点子的识别信号：团队第一反应是"为什么我们没早点想到"。
   - 完成标准：功能诉求进入独立 backlog，不与可用性缺陷混排。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **手上没有观察数据**。本方法处理的是"观察到的问题"，不处理臆测清单。
  没有数据先去 `diy-usability-test`。
- **要给产品路线图/新功能排优先级**。本 skill 的排序依据是"用户在任务中受阻的严重度"，
  不含商业价值、开发成本、市场时机维度。那属于 RICE / KANO / MoSCoW 的射程。
- **要处理的是安全、合规、数据丢失、资损类缺陷**。这些不参与"严重度投票"，
  应走独立的强制修复通道。
- **要判断某个设计该不该存在（伦理层面）**。转 `manipulation-matrix-ethics`。

### 作者在书中警告的失败模式

- **挑软柿子**：面临"一个难的 vs 一堆容易的"，团队几乎必然选后者。
- **"那块马上要改了，到时再说"**：最常见的严重问题逃逸话术。
- **清单只增不减**：没有产能截断，会议产出就退化成许愿池。
- **第一反应是"加个说明"**：把困惑当成信息不足，实际是干扰过多。
- **把参与者当设计师**：过度采纳测试中随口提出的功能诉求。

### 作者的盲点 / 时代局限

- **"严重度"缺乏客观定义**，完全依赖观察者投票。在利益不一致的团队里
  （例如某模块的负责人参会），投票会被政治污染。作者未给出对策——
  实践中建议由不承担该模块 KPI 的人主持并计票。
- **"下个月能修完"作为唯一截断线**，隐含"团队按月迭代且能自主排期"的假设。
  在双周迭代、外包交付、需求由业务方下发的组织中需要重新校准截断单位。
- **忽略 Kayak 问题在高频场景下不安全**。一次自我纠正无害，但若该抖动
  每天发生数万次（如支付、搜索），累计成本可能远超一个"严重问题"。
  **需补充频次维度：严重度 ≈ 受阻深度 × 发生频次。**
- **时代局限**：第 3 版正文写于 2013 年。书中默认"面对面白板总结会"，
  未涉及远程/异步团队；今天的等价实现（协作白板独立填写 → 匿名投票 → 排序）
  需在当代协作工具语境下重新检验，但"先写后说、禁止讨论"的反锚定纪律仍然成立。
- **诊断非生成**：本 skill 决定"修哪些、按什么顺序"，不提供具体的设计解法。

### 容易混淆的邻近方法论

- **严重度×优先级矩阵（Nielsen severity rating）**：更细的评分维度（频率/影响/持续性），
  但缺少"排满即停"的产能约束，容易再次退化成长清单。可作为本 skill 第 3 步的替代评级法。
- **RICE / KANO**：面向新功能取舍，不面向缺陷修复。
- **客诉分级 SLA**：按业务损失分级，是本 skill 在客服场景的近亲，
  但两者的"严重"含义不同（业务损失 vs 用户受阻）。
