## I — 方法论骨架 (Interpretation)

外部触发能把用户拉来一次，**内部触发才让用户自己回来**。
内部触发是一种情绪或情境与产品之间建立起的自动联结：
情绪一出现，用户不需要提醒就想到你。

三条不可让步的纪律：

**纪律一：优先找负面情绪。**
负面情绪出现频率远高于正面情绪，且自带"想立刻消除它"的驱动力。
正面情绪（愉悦、成就感）通常是**酬赏**，不是触发。
把"用户想要更好的体验"写进用户故事，等于什么都没写。

**纪律二：5 问法，每一问必须落在情绪上。**
从一个具体行为出发连问五次"为什么"。
若某一问的答案还是功能性的（"因为要买菜""因为要开会"），说明还没到底，继续问。
终点标志是出现一个**情绪词**，且这个情绪词在用户日常生活中会反复发作。

**纪律三：对象必须是一个具体的人。**
杰克·多西的要求是：写清楚"谁、在什么场景、做了什么、为什么"。
抽象人群（"25-35 岁白领女性"）会让追问退化为属性描述，
只有给这个人起个名字、写出她今天的一天，追问才有落点。

**产出格式（一句话）：**
> 当【某个具体的人】在【某个具体情境】感到【某种负面情绪】时，
> 她希望【某种即时的缓解】。

## A1 — 书中的应用 (Past Application)

### 案例 1: "茱莉"用户画像的五次追问
- **问题**: 要为一个社交/邮件类产品定位内部触发，团队只能说出"用户想和朋友联系"。
- **方法论的使用**: 给用户起名叫茱莉，写出她的具体处境（在小镇工作、朋友都在外地），
  然后连问五次为什么：为什么看邮件 → 怕漏信息 → 为什么怕漏 → 怕落在别人后面 →
  为什么怕落后 → **怕被冷落、怕被圈子抛下**。
- **结论**: 真正的内部触发是"怕被冷落"这种社交焦虑，不是"想联系朋友"这个功能描述。
- **结果**: 一旦锁定这个情绪，产品该在什么时刻提醒、该给什么酬赏（社交酬赏）全部有了依据。

### 案例 2: YouVersion《圣经》App 的内部触发
- **问题**: 网站版数据平平，团队原以为需求是"方便查经文"。
- **方法论的使用**: 观察真实用户后发现，人们读经文的时刻是排队、等车、临睡前——
  那些**孤独、焦虑、需要慰藉**的碎片时刻。
- **结论**: 内部触发不是"要查经文"（功能），而是"此刻心里不安"（情绪）。
- **结果**: 产品从桌面搬到手机，推送时间对齐这些情绪时刻，装机量过 2 亿。

### 案例 3: 电子邮件——最古老的习惯型产品
- **问题**: 为什么人们一天查看几十次邮箱？
- **方法论的使用**: 追问下去，答案不是"要处理工作"，而是"**怕错过重要信息**"的焦虑，
  以及"收件箱不清空就不舒服"的秩序焦虑。
- **结论**: 同一个产品可以挂在多个负面情绪上，情绪越常见，习惯越牢固。
- **结果**: 成为作者示范四阶段拆解的入门样本。

### 案例 4: Instagram 的"怕错过瞬间"
- **问题**: 拍照 App 一大堆，为什么这一个成了习惯？
- **方法论的使用**: 内部触发不是"想拍好看的照片"（功能/正面），
  而是"**怕这个值得留住的瞬间溜走**"的失落感 + FOMO。
- **结论**: 情绪指向"随时随地、立刻能拍能发"，直接决定了产品必须极简且移动优先。
- **结果**: 13 人团队、10 亿美元被收购。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **说不清用户为什么回来**——数据尚可但团队讲不出用户打开前 30 秒在想什么。
2. **要写用户画像 / 用户故事**，且希望它能真正指导设计而不是挂在墙上。
3. **留存差，且已排除"做不到"的可能**（流程已经很简单了，用户就是不回来）。
4. **要决定推送在什么时刻发**——时机必须对齐情绪，先得知道是什么情绪。
5. **要决定给什么酬赏**——酬赏必须缓解内部触发的那个情绪，否则是无效奖励。
6. **产品要立项 / 要判断切入点**，需要找到一个高频发作的心理痛点。

### 语言信号 (用户的话里出现这些就应激活)

- "用户为什么会用我们 / 为什么会回来"
- "找不到使用场景 / 说不清用户什么时候需要"
- "用户画像该怎么写 / 用户故事写不下去"
- "留存不行，但我们也不知道问题在哪"
- "该在什么时候推送"（时机问题的上游）
- "internal trigger" / "why would users come back" / "user emotion" / "jobs to be done"

### 与相邻 skill 的区分

- 与 `external-trigger-design` 的区别：那个解决"用什么渠道、在什么时刻提醒"，
  本 skill 解决"提醒要挂在哪个情绪上"。**顺序上本 skill 在前**——
  没有内部触发，外部触发就只是买流量（见 ce05）。
- 与 `bmat-behavior-diagnosis` 的区别：那个是行为不发生时的分诊；
  只有当分诊结论指向"动机/触发"时才转到本 skill。
  若结论是"能力"，去 `ability-simplification`。
- 与 `variable-reward-design` 的区别：本 skill 找的是**痛**，那个设计的是**止痛的方式**。
  两者必须成对使用——酬赏若不缓解本 skill 找到的情绪，就是 ce19 式的空积分。
- 与 `habit-zone-screening` 的区别：那个判断"值不值得做习惯"（频率×用途），
  本 skill 判断"挂在哪个情绪上"。若情绪一年才发作一次，回去做筛选。

## E — 可执行步骤 (Execution)

1. **选定一个真实的、有名有姓的人**
   - 不是"目标用户群"，是一个人：名字、职业、今天做了什么、手机里装了什么。
   - 完成标准：能写出这个人一天中的 3 个具体时刻。
   - 判停条件：如果只能写出年龄段和收入区间 → 材料不足，先去做用户访谈或找一个真实用户。

2. **写下一个具体的、可观测的行为**
   - 格式："她在【时刻】打开了【产品】做了【动作】。"
   - 完成标准：这个行为有时间、有地点、有动作。

3. **连问五次"为什么"，每次都往情绪方向压**
   - 每一轮记录答案，并标注它是**功能性**还是**情绪性**。
   - 完成标准：至少在第 3 问之后出现情绪词。
   - 判停条件：若五问结束仍是功能描述（"因为她需要 X"）→ 说明追问对象太抽象，回步骤 1。

4. **检查这个情绪的极性与频率**
   - 是负面情绪吗？（无聊/孤独/焦虑/沮丧/困惑/犹疑/怕错过/怕被落下/怕丢脸）
   - 一天/一周发作几次？
   - 完成标准：明确写出情绪名 + 估计发作频率。
   - 判停条件：若得到的是正面情绪 → 多半找到的是酬赏而非触发，回步骤 3 继续追问
     "她为什么需要这份愉悦"；若发作频率低于每周一次 → 转 `habit-zone-screening`。

5. **写出标准产出句，并做交叉验证**
   - 句式："当【人】在【情境】感到【情绪】时，她希望【即时缓解】。"
   - 交叉验证：用同样方法再做 1–2 个不同的人。若三个人指向同一情绪 → 高置信；
     若完全不同 → 说明存在多个用户段，需要分别设计或选择主段。
   - 完成标准：至少 1 句成型陈述，并注明置信度依据。

6. **向下游交付**
   - 交给 `external-trigger-design`：这个情绪在一天中的发作窗口 → 决定推送时机。
   - 交给 `variable-reward-design`：这个情绪需要什么样的缓解 → 决定酬赏类型。
   - 完成标准：明确写出这两条交付内容，而不是止步于一句画像。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **情绪发作频率极低的品类**（买房、报税、婚礼、遗嘱）——
  再准确的内部触发也撑不起习惯，先用 `habit-zone-screening` 判定（见 ce10）。
- **行为不发生的真实原因是能力**——用户其实很想用，只是做不到。
  挖情绪不会让流程变短，转 `ability-simplification`。
- **B 端强制流程**（合规审批、考勤打卡）——行为由制度驱动而非情绪驱动，
  内部触发挖掘的收益有限，重点应放在能力与触发时机。
- **产品本身没有可感知价值**——内部触发只能告诉你"用户什么时候难受"，
  不能替你造出解药（见 ce22）。

### 作者在书中警告的失败模式

- **ce06 — 内部触发只想到正面情绪**：用户故事里全是"想要更好的体验"，
  说不出用户上一次打开前 30 秒在想什么。
  警告信号：触发时刻描述抽象、不可观测；画像里只有褒义词。
- **ce05 — 只做外部触发，从不建立内部触发**：靠 push 和买量续命，停投即断崖。
  本 skill 就是这一失败的解药，但必须真的执行到情绪层，不能停在功能层。
- **ce18 — 触发时机与情绪脱节**：情绪没找对，时机自然也对不上，
  最终通知被关闭、外部触发通道永久损失。
- **ce19 — 说不清酬赏对应哪个内部触发**：这是本 skill 缺位的下游症状。

### 作者的盲点 / 时代局限

- 书中把内部触发几乎等同于情绪，但**情境线索**（在办公室/在地铁/刚开完会）
  同样能构成自动联结，且更易观测。实践中建议"情绪 + 情境"双锚，书中对后者着墨不足。
- 5 问法源自丰田的根因分析，用于心理归因时缺乏证伪机制：
  追问者很容易把自己的假设顺下去。缓解办法是同一行为由不同人独立追问后比对，
  书中未提供这一校验步骤。
- 书中未讨论**文化差异**：同一行为背后的情绪在不同文化里可能完全不同
  （如"怕丢脸"在东亚场景的权重远高于书中案例）。
- 强调负面情绪有其代价：长期只对准焦虑做设计，容易滑向 `manipulation-matrix-ethics`
  中的经销商象限。挖掘阶段就应记录"缓解之后用户是否真的更好"。

### 容易混淆的邻近方法论

- **JTBD（Jobs To Be Done）**：也追问"用户雇佣产品做什么"，但落点是**任务**；
  本 skill 落点强制是**情绪**。JTBD 允许"我要打一个洞"，本 skill 要求继续问到
  "我怕这个架子装不好被家人笑话"。
- **同理心地图 / 用户画像模板**：产出的是属性与描述；本 skill 产出的是
  一个可直接驱动"何时推送、给什么酬赏"的因果陈述。
- **马斯洛需求层次**：解释的是需求的普遍分层，不提供逐案挖掘的操作程序。
- **根因分析（5 Whys 原版）**：面向故障与流程缺陷，答案是机制；
  本 skill 面向人的动机，答案必须是情绪。
