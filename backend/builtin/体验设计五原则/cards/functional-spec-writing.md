## I — 方法论骨架 (Interpretation)

写需求/功能规格时,三条铁律让规格"可被实现、可被验收":

1. **乐观(positive)**: 描述系统**将要做什么去防止**坏情况,而非"系统不允许做什么"。例: 把"系统不允许用户买无线的风筝"改为"若用户想买无线的风筝,系统应引导至风筝线页"。前者是禁令,后者给出正向行为路径。
2. **具体(specific)**: 用可判定细节。反例"最受欢迎的视频要重点标注"漏洞百出(什么叫最受欢迎?如何标注?);正例"上周播放最多的视频显示在列表最前端"定义了标准与机制。
3. **避免主观(avoid subjective)**: 必须可验证。反例"网站风格要时尚闪耀"无法验证(每人定义不同);改用量化("支持1000并发")或既有参照("符合企业品牌指南文档")。

核心: **文档不解决问题,但"定义"可以**。不必包罗每处细节,只写设计/开发中易混淆的功能定义;不展望理想态,只记已确定的决议。

## A1 — 书中的应用 (Past Application)

### 案例 1: "最受欢迎视频"含糊 vs 具体
- **问题**: 需求写"最受欢迎的视频要重点标注"。
- **方法论的使用**: 作者指出其漏洞(评论最多?投票最多?如何标注?),改为"上周播放最多的显示在列表最前端"。
- **结论**: 具体细节定义了目标与机制,可判定实现。
- **结果**: 成为"具体"的正面教学。

### 案例 2: "时尚闪耀"不可验证
- **问题**: 需求写"网站风格要时尚、闪耀"。
- **方法论的使用**: 作者说明无法验证;可改"符合品牌指南文档"或用 Wayne 的时尚标准(仍偏主观,最好量化/参照)。
- **结论**: 主观词让验收靠感觉,等于没写。
- **结果**: 成为"避免主观/可验证"的反例(ce06)。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
1. 写/审 PRD、需求卡、验收标准,出现形容词或无判定标准。
2. 开发验收时"这算满足需求吗"扯皮。
3. 想建立需求撰写规范。
4. 把老板口头"要友好点"翻译成可落地规格。

### 语言信号
- "需求怎么写才清楚?"
- "这个需求算不算完成?"
- "系统要友好/时尚/好用"
- "spec / 功能规格 / 可验证需求"

### 与相邻 skill 的区分
- 与 `scope-definition-against-creep` 的区别: scope 决定"哪些需求进本期"; 本 skill 决定"单条需求怎么写清楚"。先定范围,再写规格。
- 与 `strategy-dual-axis` 的区别: strategy 是目标; 本 skill 是实现层的可验证描述。

## E — 可执行步骤 (Execution)

1. **改禁令为乐观正向**
   - 完成标准: 每条"不允许 X"改写为"当 X 时系统应做 Y 以防止"。
2. **补具体判定细节**
   - 完成标准: 删除"最受欢迎/便捷"等空词,填入可观测的定义与机制。
   - 判停条件: 若仍含无法判定的词,回到重写。
3. **替换为可验证标准**
   - 完成标准: 主观词改为量化指标或既有参照文档(品牌指南/技术阈值)。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill
- 纯艺术创作/品牌调性描述,主观即合理(但落地实现仍需可验证映射)。
- 不要为"可验证"而把每条都堆量化——只需覆盖易混淆处。

### 作者在书中警告的失败模式
- 主观不可验证规格: "时尚闪耀"各人定义不同,等于没写,验收靠拍板(ce06)。
- 功能规格"自我应验的预言": 写了没人读→强化"写它浪费时间"→更不写。解法是让撰写快速简便,不成独立项目。

### 作者的盲点 / 时代局限
- 书中偏传统 PRD; 今天用户故事/验收场景(Given-When-Then)是常见载体,三原则仍适用但表达形式可现代化。

### 容易混淆的邻近方法论
- 不要与"测试用例"混淆: 本 skill 写需求本身可验证; 测试是另一步验证它。
