## I — 方法论骨架 (Interpretation)

同一套五层,因产品类型不同,每层用的方法论不一样。这是作者用来**终结行业术语混乱**的钥匙:

| 层 | 功能型(任务导向) | 信息型(信息导向) |
|---|---|---|
| 范围 | 功能规格(functional spec) | 内容需求(content requirement) |
| 结构 | 交互设计(interaction design) | 信息架构(information architecture) |
| 框架 | 界面设计(interface design) | 导航设计(navigation design) |
| 战略 | 目标×需求(共享) | 目标×需求(共享) |
| 框架-信息设计 | 共享 | 共享 |
| 表现 | 感知体验(共享) | 感知体验(共享) |

- **功能型产品**: 把产品当"帮用户完成任务的工具",关注操作过程(如 App、SaaS)。
- **信息型产品**: 把产品当"提供信息的媒介",关注信息本身及其意义(如新闻站、文档库)。

很多真实产品是混合体(电商既有功能型下单,又有信息型商品展示)。识别主导类型,才能选对每层的方法——否则就会把"信息架构"和"界面设计"混为一谈。

## A1 — 书中的应用 (Past Application)

### 案例 1: 用双重性澄清术语混用
- **问题**: 行业里"信息设计""信息架构""界面设计"被随意互用,沟通受阻。
- **方法论的使用**: 作者把五层从中间切开,左边功能型、右边信息型,每层的真实归属一目了然。
- **结论**: 术语混乱源于没区分产品类型,双重性给出唯一对照表。
- **结果**: 成为全书统一词汇表的基础。

### 案例 2: 电商的双面性
- **问题**: 网上商店既卖货(功能)又展示商品信息(信息)。
- **方法论的使用**: 作者以"保存邮寄地址"功能属范围层(功能型)、商品照片属内容需求(信息型)示范拆分。
- **结论**: 同一产品不同部分走不同半。
- **结果**: 团队可分别用功能规格与内容需求两套语言。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
1. 讨论中"信息架构/交互设计/界面设计"被混用,需要厘清。
2. 定义产品范围,不确定写"功能规格"还是"内容需求"。
3. 设计一个混合产品(如带内容的工具),不知每层用哪套方法。
4. 招聘/分工时搞不清"信息架构师 vs 交互设计师"职责。

### 语言信号
- "信息架构和交互设计有什么区别?"
- "这是功能还是内容?"
- "我们到底是做工具还是做内容"
- "functional / informational / 双重性"

### 与相邻 skill 的区分
- 与 `five-planes-model` 的区别: 五层是纵向坐标; 本 skill 是每层内部的横向两半拆分。
- 与 `information-architecture-building` / `interaction` 类 skill 的区别: 本 skill 只做"类型判定与映射",具体怎么建 IA 或交互设计看对应 skill。

## E — 可执行步骤 (Execution)

1. **判定产品主导类型**
   - 完成标准: 回答"用户主要来'做事'还是'获取信息'?"给出功能型/信息型/混合。
2. **套用对照表映射每层要素**
   - 完成标准: 对战略/范围/结构/框架/表现逐层填出对应要素(功能规格 or 内容需求等)。
3. **混合产品分区域处理**
   - 完成标准: 若混合,标注哪些部分走功能型、哪些走信息型,各自用对应方法。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill
- 产品类型极其单纯(纯算法后台无用户面)无需区分。
- 不要为了"归边"而强行二选一——混合产品允许多区域各走各的。

### 作者在书中警告的失败模式
- 术语混用导致沟通障碍: 大家连基本名词都达不成一致,事情很难顺利进展(第2章)。

### 作者的盲点 / 时代局限
- 模型以 Web 为主; 今天 AI/对话式产品很难简单归为功能或信息型(对话既完成任务又给信息),需把"对话流"同时映射到两侧。

### 容易混淆的邻近方法论
- 不要与"技术栈选型"混淆: 双重性说的是产品与用户的关系类型,不是用什么技术实现。
