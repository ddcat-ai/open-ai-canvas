## I — 方法论骨架 (Interpretation)

范围层回答"我们要开发的是什么"(把战略变成功能/内容)。定义范围的动作同时产生**过程价值**和**产品价值**:

- **过程价值**: 在假设阶段就逼出潜在冲突、分清哪些现在解决、哪些迟点解决。
- **产品价值**: 给出团队共同参考点,明确全部工作,提供讨论的共同语言,避免"电话游戏"式走样(每人脑中不同版本)。

防蠕变的关键在"有意识地管理需求":
- 写文档记录需求,让每个想法都能被评估"是否服务战略目标"。
- 把当前难满足但好的想法**囤积为未来版本**,形成循环开发,而非当场塞进本期。
- 范围蠕变比喻: 雪球每滚一寸捎更多雪,最终失控——每个新增需求看似不多,汇总即爆。

作者亲历: 一个"永远 Beta"的 Web 应用,因无人定义需求、功能随灵感膨胀、无里程碑,永远完不了(见 A1)。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: 永远 Beta 的 Web 应用 (作者亲历)
- **问题**: 项目最大绊脚石是"没人有意愿定义需求"。
- **方法论的使用**: 功能随读到的新文章/灵感不断新增,有流程无日程无里程碑。
- **结论**: 因无人知范围,不知何时结束。
- **结果**: 成为"为何必须写需求文档"的最有力论据。

### 案例 2: 支持文档与产品规格的交叠
- **问题**: 早期讨论中两功能看似独立。
- **方法论的使用**: 定义为需求后,交叠变明显,同一小组可一并负担。
- **结论**: 明确范围让隐性联系浮现。
- **结果**: 提升协作效率与责任分配。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
1. 老板/客户每天加新需求,项目看不到终点。
2. 团队对"本期到底做哪些"理解不一。
3. 想建立需求文档/PRD 规范。
4. 复盘发现项目因需求膨胀而超支延期。

### 语言信号
- "又来个新需求,加不加?"
- "这个项目怎么一直做不完"
- "范围蠕变 / 需求蔓延"
- "scope / requirements / 范围层"

### 与相邻 skill 的区分
- 与 `functional-spec-writing` 的区别: 本 skill 是"是否/哪些需求进本期"(范围与防蠕变); functional-spec-writing 是"单条需求怎么写清楚"(规格撰写)。
- 与 `strategy-dual-axis` 的区别: strategy 定目标; 本 skill 把目标落成"做什么/不做什么"。

## E — 可执行步骤 (Execution)

1. **文档化本期需求清单**
   - 完成标准: 列出功能/内容需求,团队可共同查阅,责任清晰。
2. **每个新想法过战略筛**
   - 完成标准: 新需求先问"服务哪个战略目标?",不服务则拒或囤未来版。
   - 判停条件: 若某想法频繁出现且超出现有战略,触发重审战略(而非硬塞)。
3. **建立"未来版本"囤积池**
   - 完成标准: 当前不做但好的想法入池,形成循环开发,杜绝当场膨胀。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill
- 一行文案修改等微型改动,无需范围文档。
- 不要为文档而文档: 写正确级别即可,过少糊弄、过多降低生产力。

### 作者在书中警告的失败模式
- **范围蠕变**: 无意识纳入需求,雪球式膨胀,结束遥遥无期、预算崩盘(ce01)。
- "电话游戏": 不写文档,每人脑中不同产品版本,责任悬空。

### 作者的盲点 / 时代局限
- 强调"写文档"对极小团队/单人可能有形式负担; 本书也承认"文档不是目的",但实践中易滑向官僚。

### 容易混淆的邻近方法论
- 不要与"敏捷 backlog"混淆: backlog 也管理需求,但本 skill 强调"有意识地管+囤未来版防蠕变"这一具体纪律。
