## I — 方法论骨架 (Interpretation)

"三次点击原则"是一条流传极广、但选错了变量的规则。它假定成本随步数线性增长，
于是团队去合并步骤、压缩层级、把三个页面塞进一页。结果常常更糟：合并后的那一页
选项更多、更密、更难判断，用户在那一页上卡住的时间比原来三页加起来还长。

Krug 换了变量：成本不在**步数**，在每一步的**选择确定性**。

- 一次点击如果是"显而易见、明确无误"的，它的认知成本接近零。用户几乎感觉不到自己点了。
- 一次点击如果需要权衡（"这两个选项看起来都像""这词是什么意思""点错了会怎样"），
  它的成本是巨大的，而且会累积成焦虑。

所以正确的审查动作不是数步数，而是**逐步测量确定性**。每一步问三件事：
① 用户是否百分百确定该点哪个？② 选项名称是否互斥且穷尽（不会觉得"两个都像"或"都不像"）？
③ 万一点错，回来的成本是不是极低？

三问全通过 → 这一步不算成本，哪怕它是第八步。
任一问不通过 → 这一步就是漏斗真正漏水的地方，哪怕它是第一步。

配套的反向动作也很重要：当你打算**合并**步骤时，先检查合并是否会把两个原本清晰的
选择挤成一个模糊的选择。如果会，宁可多一步。把一个复杂表单拆成三个明确的小步，
通常比塞成一页更好用。

## A1 — 书中的应用 (Past Application)

### 案例 1: 三次点击原则的破产
- **问题**：很多站点规定"到达任何页面不超过 3/4/5 次点击"，并以此约束信息架构。
- **方法论的使用**：Krug 长期观察后发现，用户真正的挫折感与点击次数不相关，
  而与"这次该点哪个"的犹豫强相关。
- **结论**：点击次数是伪指标。
- **结果**：设计目标从"压缩层级"转为"让每层的选项一目了然"，
  信息架构可以更深，但每层必须更清楚。

### 案例 2: 无须思考的选择才是关键因素
- **问题**：团队想知道"什么才是网站容易使用的最重要因素"。
- **方法论的使用**：作者直接给出判断——无须思考是最重要的因素。
- **结论**：确定性 > 效率指标。
- **结果**：评审重心从"数步数"变成"逐步判断歧义"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 团队提出"要把流程控制在三步以内""能不能合并成一页""少一次跳转"。
2. 转化漏斗某一步流失异常高，要定位原因。
3. 设计注册/下单/结算/申请/审批/退款流程，或对现有流程改版。
4. 设计菜单层级、CLI 子命令树、客服 IVR 转接路径、后台导航层级。
5. 表单太长，在纠结"一次展示全部"还是"分步引导"。
6. 有人拿"点击次数少"当作方案更优的论据。

### 语言信号（用户的话里出现这些就应激活）

- "三次点击原则 / 步骤太多 / 太绕了 / 要几步才能到"
- "能不能合并成一页 / 减少一次跳转 / 精简流程"
- "这一步流失特别高 / 漏斗在这断了"
- "用户在这里犹豫 / 不知道该选哪个"
- "three-click rule / too many steps / reduce clicks / simplify the flow / funnel"

### 与相邻 skill 的区分

- 与 `ability-simplification` 的区别：那个 skill 的默认动作是**减少步骤、降低门槛**；
  本 skill 恰恰警告"减少步骤可能有害"，两者方向相反、互为制衡。用法：先用
  ability-simplification 找出所有可砍的门槛，再用本 skill 检查砍完之后每一步是否仍然明确。
- 与 `dont-make-me-think-audit` 的区别：那个审查**单个界面**上的问号；
  本 skill 审查**一条链路**上每一步的选择确定性，输出是链路图而非页面清单。
- 与 `bmat-behavior-diagnosis` 的区别：B=MAT 分诊动机/能力/触发；本 skill 只处理
  "能力—理解"这一支里的"选择歧义"子类。若用户是**不想做**而非**不知道选哪个**，
  本 skill 不适用。
- 与 `choice-set-decoy-design` 的区别：那个是用选项结构**引导用户选某一项**（说服）；
  本 skill 是让用户**自己想选的那项一眼可辨**（不歧义）。目的不同。

## E — 可执行步骤 (Execution)

1. **把链路画成一条步骤序列**
   - 从入口到目标，逐步列出：步骤名 / 该步用户要做的选择 / 全部可见选项。
   - 完成标准：步骤数、每步选项数都被明确写出。

2. **逐步做三问确定性测量**
   - ① 用户是否 100% 确定该点哪个？
   - ② 选项名称是否互斥且穷尽？（有没有"两个都像"或"一个都不像"）
   - ③ 点错后返回成本是否极低？（能不能一步退回、是否会丢数据）
   - 完成标准：每步得到"明确 / 有歧义 / 高风险"三档评级之一。

3. **标出真正的成本点，忽略无痛步骤**
   - 只有"有歧义"和"高风险"的步骤计入成本；"明确"的步骤即使很多也不计。
   - 完成标准：得到一张只含问题步骤的短清单（通常 1–3 步）。

4. **对合并类提案做反向检查**
   - 若有人提议合并步骤，模拟合并后的那一页，重跑三问。
   - 判停条件：若合并会把两个清晰选择挤成一个模糊选择 → 明确反对合并，
     并给出"宁可多一步"的理由。

5. **对有歧义的步骤给出消歧动作**
   - 优先级：改选项名（用用户的词）> 减少同层选项数 > 加一句极短的判别提示
     （形如"如果你想 X，选这个"）> 提供低成本回退（明显的返回、自动保存）。
   - 完成标准：每个问题步骤都有一条具体改法。

6. **输出链路评审表**
   - 列：步骤 / 三问评级 / 问题描述 / 改法 / 是否建议拆分或合并。
   - 附一句总结论：本链路真正的成本在第 N 步，而不是"步数太多"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **成本来自等待而非选择**：加载慢、审核要三天、物流要一周、需要线下盖章。
  这类步骤的痛苦与"确定性"无关，压缩耗时才是正解。第二定律不为它们辩护。
- **用户是"不想做"而不是"不知道选哪个"**：动机问题请转 `bmat-behavior-diagnosis`
  或动机类 skill。
- **单页视觉问题**：如果卡点是"看不见那个按钮"而非"不知道选哪个"，转 `billboard-scan-design`。
- **有意设置的摩擦**：删除确认、大额转账二次验证、风控问询——这些步骤的存在意义
  就是让人停下来想一想，不适用本定律。
- **需要减少的是真实操作负担**（输入 20 个字段、上传 5 份材料）：那是执行成本不是认知成本，
  转 `ability-simplification`。

### 作者在书中警告的失败模式

- **把"点击次数"写进规范并强制执行**。作者明确指出很多站点这么做，但这条准则
  "表面上看起来有用"，实际抓错了变量。
- **为了减少步数而把复杂度堆到某一页**。这是第二定律最常被误用的方向。

### 作者的盲点 / 时代局限

- 第 3 版正文写于 2013 年，语境是桌面 Web 的页面跳转。今天在**移动端与小程序**里，
  一次跳转还附带转场动画、页面加载、状态丢失风险，因此"步数完全不重要"需要打折——
  **具体判断需在当代移动端与 App 语境下重新检验**；但"确定性比步数重要"这一排序仍成立。
- 作者未讨论**多设备/多会话中断**场景（用户在手机上开始、在电脑上继续），
  长链路在这类场景下的断点成本确实随步数上升。
- 作者只给判据，不给消歧的设计方法（诊断非生成）。

### 容易混淆的邻近方法论

- **认知负荷理论（内在/外在/相关负荷）**：本 skill 处理的是"外在负荷"里的选择歧义子类。
- **漏斗分析（定量）**：能告诉你哪一步流失高，但不能告诉你为什么。
  本 skill 提供"为什么"的定性判据，两者配合使用：先看漏斗定位，再用三问定因，
  最后用 `diy-usability-test` 找 3 个人验证。
