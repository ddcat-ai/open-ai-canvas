## I — 方法论骨架 (Interpretation)

绝大多数团队不做可访问性，不是因为反对，而是因为**入口设计得让人放弃**。
标准建议是"用检查器跑一遍，保证符合 WCAG"。但检查器的表现更像语法检查器而不是
拼写检查器：它会找出少量明确错误（缺 alt 文本），同时吐出一长串"你**可能**做错了"的
模糊警告和"建议你检查但也许没问题"的条目。结果是新手得出结论：这事深不见底，
我做不了。于是一件都没做。

Krug 的策略是**把入口换掉**：不追求达标，先摘影响最大的那几件。他给出的四步有一个
清晰的递进逻辑——**先修共通问题 → 建立对真实使用方式的直觉 → 补系统知识 → 动代码**。

**#1 先修让所有人都困惑的普通可用性问题。**
这一步是全章最反直觉、也最容易被跳过的。流行说法是"提升可访问性会让所有人都受益"
（作者称之为"Tang 式说法"，即"航天科技带来了果珍"那种论调）。他指出**反过来说才是对的**：
让网站对普通人更好用，会让残障用户用得更好。理由很硬——
"他们不会因为残障而变得聪明许多"，而且更难从混乱中回过神来。
一个提交表单后弹出的费解错误提示，你看得见都难受；想象看不见时怎么解决。
**如果网站本身含混不清，无论多努力套用可访问性规则，残障人士还是用不了。**

**#2 读一篇文章（20 分钟）。**
理解一种使用方式的正确路径是观察真人。多数人没有条件观察屏幕阅读器用户，
所以借用已有的观察研究：Theofanos & Redish 观察 16 位盲人用户完成任务的报告。
其核心发现与本书第 2 章的扫描理论**完全同构**：盲人用户同样没有耐心，
同样不逐字听，而是"用耳朵扫描"——只听一行文本或一个链接的**前几个字**，
不相干就跳到下一个。很多人把语速调得极快。

这条洞察的可操作推论非常锋利：**关键词若不在开头，对读屏用户等于不存在。**
明眼人可以横向扫描整页捕捉关键词，读屏用户只能顺序听到开头。
所以"点击这里""了解更多""查看详情"这类链接文字，对他们是纯噪声。
这一条同时也是给所有人的文案规则（标题前置关键词、链接文字自解释）。

**#3 看一本书（一天或一个周末）。** 掌握大致轮廓即可，不需要全部吸收。

**#4 摘够得着的果子。** 到这一步才动代码，且只做七件确定有效的事。

另有一条需要正面拆除的心理障碍：**"可访问性必然导致设计折中"**。
作者用"背上捆着涂黄油面包的猫"来指代设计师的这种想象，并给出实体反例（见 A1 案例 1）。
判断句是：可访问性与美观不是零和，多数情况下只是**分层承载不同通道的信息**。

## A1 — 书中的应用 (Past Application)

### 案例 1: 芝加哥出租车的有机玻璃盲文标志
- **问题**：设计师担心"照顾残障用户 = 牺牲设计"。
- **方法论的使用**：作者展示座椅背后的标志——表面覆一层有机玻璃，
  盲文凸印在透明层上。常规做法是文字与盲文各占一半、双双缩小；
  这个设计让两类读者**各自获得全尺寸的最优体验**。
- **结论**：可访问性不必然是折中，透明叠加式思路可以让两个通道互不挤占。
- **结果**：破除"奶油面包猫"式的折中恐惧，是启动这项工作的心理前提。

### 案例 2: Theofanos & Redish 的 16 位盲人用户观察
- **问题**：团队对"读屏用户如何使用网页"完全没有直觉，只能凭规则条文猜。
- **方法论的使用**：借用一篇 20 分钟可读完的观察报告，直接获得使用模型——
  用耳朵扫描、只听前几个字、语速极快、不相干立刻跳走。
- **结论**：可访问性的核心不是"能不能读出来"，而是"能不能**快速跳过**"。
- **结果**：推导出一批具体写法（链接文字前置关键词、标题层级正确、
  提供跳转到主要内容），也印证了扫描理论的普适性。

### 案例 3: "增大字体"三秒测试
- **问题**：需要一个能立刻判断团队有没有在可访问性上投入的粗筛。
- **方法论的使用**：调浏览器的 Text Size，若页面字体纹丝不动，
  说明用了固定尺寸字体，通常也意味着这方面零投入。作者说
  "几乎我访问的每个网站都没有通过我的三秒钟可访问性测试"。
- **结论**：粗筛的价值在于成本极低、且高度相关。
- **结果**：**注意——作者自己就标注了这条的时代性**：多数浏览器已用 Zoom 取代 Text Size。
  当代等价替换见 E 步骤 5。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 收到无障碍/可访问性要求（政策、招标、信创、上架审核、企业客户合规条款），
   不知道从哪开始。
2. 跑了检查器，面对一屏红黄警告不知道哪些真要修。
3. 团队认为"做无障碍会牺牲设计感"或"我们用户里没有残障人士"。
4. 有视障/低视力/老年/运动障碍用户反馈用不了。
5. 要写链接文字、标题、图片说明、表单标签，想知道对读屏用户什么写法有效。
6. 想加一条低成本的自检进现有走查流程。
7. 场景性障碍：强光下看屏幕、单手抱孩子操作、嘈杂环境无法听音频、
   老人机与大字模式、无鼠标只能键盘。

### 语言信号（用户的话里出现这些就应激活）

- "无障碍 / 可访问性 / a11y / accessibility / WCAG / 信创无障碍"
- "屏幕阅读器 / 读屏 / VoiceOver / TalkBack / NVDA / 盲人用户"
- "alt 文本 / 图片描述 / 标题层级 / label / 对比度 / 键盘可达 / tab 顺序"
- "老年人看不清 / 字太小 / 放大后就乱了"
- "检查器报了一堆警告 / 要修到什么程度"

### 与相邻 skill 的区分

- 与 `dont-make-me-think-audit` 的区别：那个处理**所有人**的自明性问题；
  本 skill 处理**特定通道受限**用户的可达性。但注意二者有强依赖关系——
  本 skill 的第 1 步就是"先去做那个"。顺序不能反。
- 与 `billboard-scan-design` 的区别：那个为**视觉扫描**优化（层次、分区、留白）；
  本 skill 为**听觉扫描与键盘遍历**优化（前置关键词、标题层级、跳转链接）。
  同一个扫描理论的两个通道实现。
- 与 `frontend-dev` 的区别：那个是前端工程实现能力（框架、构建、组件）；
  本 skill 是**决定做什么、按什么顺序做**的优先级判断，只到"该改哪些 HTML 语义"为止，
  不涉及具体技术栈实现。实施阶段可转那个。
- 与 `ability-simplification` 的区别：那个降低"做一件事所需的能力门槛"（步骤、时间、
  脑力、金钱）；本 skill 处理的是**感知与操作通道的缺失**，不是难度问题——
  再简化的流程，图片没有 alt 也依然读不出来。

## E — 可执行步骤 (Execution)

1. **第 1 步：先做通用可用性清理（不可跳过）**
   - 先跑 `dont-make-me-think-audit` / `omit-needless-words` / `billboard-scan-design`，
     把"让所有人都困惑"的地方修掉：含混的按钮名、费解的错误提示、没有分区的页面。
   - 判据：如果一个明眼人在这里也要停下来想，读屏用户几乎必然失败。
   - 完成标准：主要任务路径上不存在"需要猜"的措辞与结构。

2. **第 2 步：建立使用直觉（20 分钟）**
   - 读 Theofanos & Redish 的观察报告（或等价的读屏用户观察记录/视频）。
   - 更好的替代：**自己打开系统自带读屏（iOS VoiceOver / Android TalkBack /
     Windows 讲述人 / macOS VoiceOver），闭屏完成一个自家产品的核心任务。**
     这是当代最低成本的"观察"，作者当年没有这个条件。
   - 完成标准：能说出"用耳朵扫描"意味着什么，并能指出自家产品哪三处会让读屏用户卡死。

3. **第 3 步：补系统知识（可延后，但要排期）**
   - 《A Web for Everyone》（中译《兼济天下：用户无障碍体验的可访问性设计》）
     或《Web Accessibility: Web Standards and Regulatory Compliance》。
   - 目标是掌握轮廓，不求全记。
   - 完成标准：知道有哪些类别的问题存在，遇到时知道去哪查。

4. **第 4 步：摘够得着的果子（动代码）**
   - ① **alt 文本**：装饰性图片用空 alt（`alt=""`）让读屏跳过；
     信息性图片写有帮助的描述性文字。
   - ② **正确的标题层级**：页面主标题 `<h1>`，主要区块 `<h2>`，子标题 `<h3>`，
     依次递减；视觉样式交给 CSS。标题是读屏用户的主要导航手段。
   - ③ **表单 label 关联**：用 `<label>` 把输入框与提示文字绑定，
     让用户知道该输入什么。
   - ④ **"跳转到主要内容"链接**：置于每页最前。否则用户每进一页都要先听完
     整套全局导航（20 秒到一两分钟）。
   - ⑤ **全键盘可达**：所有内容与操作不依赖鼠标；焦点顺序合理、焦点可见。
   - ⑥ **文本与背景明显对比**：不要深灰底上放浅灰字。
   - ⑦ **选用可访问性良好的模板/主题/组件库**（WordPress 主题、UI 组件库同理）。
   - 完成标准：七项逐条有结论（已做 / 不适用 / 排期），且 ①②③⑤ 全部完成。

5. **加一条粗筛进日常走查（三秒测试的当代替换）**
   - 原书版本（调 Text Size 看字体变不变）已随浏览器改用 Zoom 而失效。
   - 当代等价三选一：**① 系统字号调到最大**，看布局是否崩、文字是否被截断；
     **② 只用键盘 Tab 走一遍主流程**，看能否完成且焦点始终可见；
     **③ 用取色器测一次正文与背景对比度**。
   - 完成标准：三条中至少一条进入常规自查清单。

6. **对外沟通时先拆折中恐惧**
   - 遇到"做无障碍会牺牲设计"的反对，用有机玻璃盲文标志的分层思路回应：
     多数情况是**为不同通道各自提供完整信息**，而非把一份资源切成两半。
   - 完成标准：讨论从"要不要牺牲"转向"哪一层承载什么"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **需要正式合规达标与法律审计**（政府采购、无障碍认证、ADA/欧盟 EAA/
  国标 GB/T 37668 等）。本 skill 是**起步法而非达标法**，
  刻意省略了大量条款。此时必须回到完整标准与专业审计。
- **产品的核心障碍在于硬件或输入方式**（如需要适配开关控制、眼动、
  语音专用设备），超出本 skill 的射程。
- **问题其实是通用可用性问题**：转第 1 步引用的那些 skill，别绕远路。

### 作者在书中警告的失败模式

- **以检查器为起点**：长清单 + 模糊警告 = 新手劝退器。它适合当**收尾核对**，不适合当入口。
- **相信"Tang 式说法"**（做了无障碍所有人都受益）：作者认为这是招人烦的倒因为果，
  真正成立的是反方向——**先让普通人好用，残障用户才可能用得了**。
  倒过来做，会在一个含混的网站上贴满 alt 文本，然后发现依然没人能用。
- **折中恐惧**：把可访问性想象成必然的美学牺牲，从而在第一步就放弃。
- **把它当成开发人员的私事**：书中指出实际承担者是开发和设计，
  但他们往往不理解为什么要做——所以第 2 步（建立直觉）比任何规范都重要。

### 作者的盲点 / 时代局限

- **时代局限（本 skill 中最重）**：第 3 版正文写于 2013 年。
  - "三秒测试"依赖的浏览器 Text Size 已被 Zoom 取代（**作者本人已注明**），
    替换方案见 E 步骤 5。
  - 提到的建站工具（Dreamweaver）与标准称谓（Bobby 标准）已过时；
    今天是 WCAG 2.1/2.2、ARIA、以及各平台原生无障碍 API。
  - 全章围绕 **Web/HTML**，**完全未覆盖原生 App、小程序、
    Canvas/自绘 UI、视频字幕与音频描述、动效与前庭障碍
    （prefers-reduced-motion）、深色模式与对比度**等当代主战场。
    **凡涉及具体技术手段的条目，需在当代移动端与 App 语境下重新检验；
    "先修通用问题 → 建立使用直觉 → 摘最大果子"的优先级逻辑仍完全成立。**
  - 作者当年建议"找一两位盲人用户观察几小时"成本较高；
    今天系统自带读屏可让任何人在 20 分钟内自测，这一步应从"可选"升级为"必做"。
- **视角偏向视障**：全章以屏幕阅读器为中心，对**听障（字幕、纯视觉提示）、
  运动障碍（点击热区、时间限制、防误触）、认知障碍与阅读障碍
  （语言复杂度、记忆负荷）、癫痫（闪烁频率）**着墨极少。
  这些人群在真实用户中占比同样可观。
- **"七件事"是必要不充分**：全部做完不等于可用。特别是 SPA、
  动态内容更新、模态框焦点管理、自定义组件的语义——2013 年的清单不涉及，
  而它们是今天读屏失败的主要来源。
- **诊断非生成**：本 skill 给出优先级与检查项，不产出具体的无障碍设计方案与代码实现。
- **迁移力中等**：本 skill 的专门性强于本书族其他 skill。
  可迁移的部分是"面对压倒性合规清单时，如何用影响力排序找到起步点"这一元策略，
  以及场景性障碍（强光、单手、嘈杂环境、长辈机）的类比使用。

### 容易混淆的邻近方法论

- **WCAG 2.x / A-AA-AAA 分级**：完整的达标标准。本 skill 是它的**入口子集**，
  不是替代品。二者关系：先用本 skill 起步并建立能力，再用 WCAG 做完整覆盖。
- **包容性设计（Inclusive Design）**：更宽的框架，覆盖永久/临时/情境三类障碍
  （断臂、抱孩子、强光下）。本 skill 属于其中的执行子集。
- **适老化改造**：与本 skill 高度重叠（字号、对比度、点击热区），
  但额外强调认知负荷与流程简化，可与 `ability-simplification` 组合。
- **可用性测试**：`diy-usability-test` 的方法完全适用于招募残障参与者，
  且价值极高——但招募与设备准备需要额外准备，不属本 skill 的最小起步范围。
