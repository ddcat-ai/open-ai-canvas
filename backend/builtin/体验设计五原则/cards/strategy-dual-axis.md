## I — 方法论骨架 (Interpretation)

战略层是整个五层模型的**地基**,由两根轴组成:

- **内部轴——产品目标**: 企业想从产品得到什么。可能是商业目标(赚钱/省钱)、品牌识别(用户心中的形象),以及可追踪的成功标准。
- **外部轴——用户需求**: 用户想从产品得到什么。来自企业之外,需通过研究了解。

两根轴结合,成为范围、结构、框架、表现每一层决策的**基础**。失败最常见的原因不是技术也不是 UX,而是开始前没回答这两个基本问题。

关键动作是**明确(explicit)表达**: 模糊的战略(只可意会)会让不同人对"产品该怎么做"有不同想法。定义"成功的条件"而非"通向成功的路径",避免未充分了解问题就下结论——这能防止团队跑太快。

## A1 — 书中的应用 (Past Application)

### 案例 1: 网站失败源于没回答两个基本问题
- **问题**: 很多网站上线即失败。
- **方法论的使用**: 作者指出根因常是没人回答"我们要得到什么 / 用户要得到什么"。
- **结论**: 战略不明确,下层决策失去准星。
- **结果**: 成为全书主张"先定战略"的论据。

### 案例 2: 战略文档作为试金石
- **问题**: 战略常只存在于小群人脑中,易走样。
- **方法论的使用**: 作者主张写战略/愿景文档,不仅列目标,还分析目标间关系;文档要被团队频繁使用而非藏起来。
- **结论**: 明确的战略文档让所有参与者做正确决定。
- **结果**: 战略成为"设计流程的起点"且可演变。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
1. 启动新产品/新功能,没人说清"企业图什么、用户图什么"。
2. 团队对"项目目标"理解不一致,各做各的。
3. 写/重审战略文档、品牌定位、OKR 类产品目标。
4. 需求评审时发现需求无战略依据。

### 语言信号
- "我们到底为什么要做这个?"
- "用户到底要什么?"
- "战略目标不清楚 / 战略文档"
- "product objective / user need / 战略层"

### 与相邻 skill 的区分
- 与 `success-metrics` 的区别: 本 skill 定"目标与需求是什么"(双轴内容); success-metrics 是把这些目标变成"可追踪指标"。先有本 skill 的双轴,才有指标。
- 与 `user-segmentation-personas` 的区别: 本 skill 是双轴框架; personas 是"如何弄清外部轴(用户需求)"的具体技术。

## E — 可执行步骤 (Execution)

1. **分别列出两根轴**
   - 完成标准: 内部轴写出产品目标(商业/品牌),外部轴写出用户需求,各 3–5 条。
2. **逼出"明确"表达**
   - 完成标准: 把"只可意会"的目标改写成可判定语句; 定义"成功条件"而非"路径"。
   - 判停条件: 若出现"提升体验"等空话,返回重写具体。
3. **落成可复用战略文档**
   - 完成标准: 文档含目标间关系分析,且约定团队可频繁查阅(非封存)。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill
- 纯执行任务且需求已明确,无需重定战略。
- 不要把它当"写一堆漂亮的 PPT"——文档贵在明确与被使用,不在厚度。

### 作者在书中警告的失败模式
- 战略只可意会: 产品目标无法口头表达时,不同人对"如何完成"想法各异,项目失控。
- 管理层分不清"特性"与"战略": 常从特性倒推,需耐心引回战略目标(见范围层)。

### 作者的盲点 / 时代局限
- 假设战略可被清晰表达且稳定; 但很多产品目标本身模糊/争议,本书对高度不确定的探索型产品适配偏刚性(虽承认战略可演变)。

### 容易混淆的邻近方法论
- 不要把"用户需求调研"误认为本 skill 全部: 本 skill 是双轴框架,用户研究只是外部轴的一种输入技术(见 personas)。
