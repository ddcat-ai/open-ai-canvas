## I — 方法论骨架 (Interpretation)

很多体验决策是"不自觉地"产生的,被三种非战略来源劫持:

1. **design by default(由现状决定)**: 体验结构盲目跟随底层技术架构或企业内部组织结构。例: 把客户订单与消费信息分存两库(技术合理),于是在体验中也分开——但用户视角应合并。
2. **design by mimicry(由模仿决定)**: 照搬其他产品/刊物/软件的做法,不管是否适合你的用户或产品。
3. **design by fiat(由领导独断)**: 个人喜好代替战略。例: 某 VP 爱橙色→配色橙色主导; 研发领导爱下拉菜单→导航全变下拉。

**正面对抗**: 作者主张每个决定建立在"对背后议题的理解"上,先问**"你为什么要这么做?"**。不要以节省时间金钱敷衍 UX; 不要只在末尾加"用户接受度测试"(假设已藏进界面难暴露); 用户测试不能取代周密设计,也不能依赖用户自己阐明需求(要"比用户更准确理解需求")。

识别这三种来源,是把"不自觉决策"拉回"有意识、可论证决策"的前提。

## A1 — 书中的应用 (Past Application)

### 案例 1: 三种来源贯穿第8章
- **问题**: 体验决策常不知被什么驱动。
- **方法论的使用**: 作者命名 default/mimicry/fiat 三类,说明它们让战略被替代。
- **结论**: 命名即诊断起点。
- **结果**: 成为全书"应用"章的核心反框架(ce02)。

### 案例 2: 橙色配色由领导独断
- **问题**: 某 VP 喜好决定全站配色。
- **方法论的使用**: 作者以 fiat 为例,说明喜好代替战略目标。
- **结论**: 应拉回"为何",用战略目标而非个人偏好决策。
- **结果**: 说明如何对抗 fiat。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要 this skill?
1. 决策理由是"系统就这样分的""竞品都这么做""老板喜欢"。
2. 复盘发现产品偏离用户/战略。3. 想建立"决策须有战略依据"的团队规范。
4. 争论"要不要加 UX 评估/用户测试"。

### 语言信号
- "竞品都这么做,我们也做"
- "老板说用橙色"
- "系统分两库所以体验也分"
- "design by default / mimicry / fiat / 错误设计"

### 与相邻 skill 的区分
- 与 `bottom-up-chain-effects` 的区别: bottom-up 讲"层间应如何依赖建设"; 本 skill 讲"决策被哪些非战略来源带偏"。互补(都属第8章元原则)。
- 与 `strategy-dual-axis` 的区别: strategy 是"正确基座是什么"; 本 skill 是"偏离基座的三种错误来源"。

## E — 可执行步骤 (Execution)

1. **识别决策来源**
   - 完成标准: 对每个关键决策问"驱动它是战略/用户需求,还是 default/mimicry/fiat?"标出非战略来源。
2. **正面对抗:问"为什么"**
   - 完成标准: 对非战略决策,拉回战略层问"为何这样做",用战略目标替代现状/模仿/喜好。
   - 判停条件: 若只因"老板喜欢"且无战略依据,提出以战略目标重新论证。
3. **贯穿全程而非末尾测试**
   - 完成标准: 把 UX 作为全程决策基础,不在末尾才加"接受度测试"; 用户测试辅助而非替代设计。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill
- 已有明确战略/用户需求文档支撑、可追溯的决策,无需此诊断。
- 不要误把"合理借鉴竞品"当 mimicry——借鉴需论证适合自身,盲目照搬才是。

### 作者在书中警告的失败模式
- 三种错误来源使战略被替代,上线后用户痛恨产品(ce02)。
- 末尾"接受度测试": 假设藏进界面难暴露,发现问题也无力修复(ce04)。

### 作者的盲点 / 时代局限
- 对"企业政治压倒用户"的结构性无力着墨温和,主张"认同决策者需求、谈判"——现实中权力结构可能使战略让步,本书未深究。

### 容易混淆的邻近方法论
- 不要与"敏捷借鉴竞品"混淆: 借鉴+论证可行; mimicry 是"不顾适配照搬"。
