## I — 方法论骨架 (Interpretation)

五层不是"先做哪层"的时间表,而是一张**依赖网**:

- **下层决定上层**: 战略不清,范围就会飘;结构没定,框架就乱。任一层的决定会约束它上面所有层的可用选项。
- **连锁效应是双方向的**: 上层选了一个下层没兜住的选项(如表现层要一个底层架构不支持的炫酷交互),就得回头改下层;反过来,上层的新决策也可能**促成**对下层的第一次认真评估。
- **不要走极端**: 要求低层 100% 确定才能开始高层,会拖垮日程甚至产品成功;正确做法是"**任何一层的工作,不能在其下层的'工作完成之前'结束**"——不必等"完全确定"。作者比喻: 在知道房屋基本形状前,不能先盖屋顶。

这条规则的实战含义: 底层(战略/范围/结构)的任务看似"无可视化产出",却是上层的交付基础; 砍掉它们短期出活、长期制造债务(见 B 段)。

## A1 — 书中的应用 (Past Application)

### 案例 1: 不为房屋先加屋顶
- **问题**: 团队急于看到"成果"(界面/视觉)。
- **方法论的使用**: 作者用建筑比喻说明——框架层(屋顶)必须建在结构层(墙/地基)之上; 逼着先出顶层视觉,等于没地基先盖顶。
- **结论**: 任一层不能在其下层工作完成前结束。
- **结果**: 成为全书对"赶工"的约束原则。

### 案例 2: 砍掉底部层面制造新债务 (第8章)
- **问题**: 项目落后时,常先砍"无可视化产出"的战略/范围/结构任务。
- **方法论的使用**: 作者指出这些是被砍任务埋下债务——下一个大项目正是来修上一个的缺陷,陷入恶性循环。
- **结论**: 上层正确决策若建在底层错误上则毫无意义。
- **结果**: 解释了许多"漂亮但完全不可用"的失败网站。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
1. 争论"先画原型还是先写战略/需求文档"。
2. 项目反复返工,疑似底层没想清就动了上层。
3. 为赶进度想砍"战略/范围/结构"类前期任务。
4. 评审排期,发现上层依赖下层却并行失控。

### 语言信号
- "要不要先做个界面看看?"
- "战略文档太慢了,直接开干吧"
- "这个项目怎么一直在返工"
- "bottom-up / 连锁反应 / 层依赖"

### 与相邻 skill 的区分
- 与 `five-planes-model` 的区别: 五层是"坐标"(是什么层),本 skill 是"动力学"(层怎么互相决定、建设顺序)。定位用五层,排期/依赖用本 skill。
- 与 `design-anti-patterns` 的区别: 本 skill 讲"层间应如何依赖"; design-anti-patterns 讲"决策被哪些非战略来源带偏"(default/mimicry/fiat)。两者互补。

## E — 可执行步骤 (Execution)

1. **识别涉及的层与依赖方向**
   - 完成标准: 列出"X 层依赖 Y 层"的上下游关系。
2. **检查上层是否越界**
   - 完成标准: 若上层选项超出下层已定范围,标记"需重估下层"。
   - 判停条件: 若只是下层未"完全确定"但已"基本成形",允许上层启动(不阻塞)。
3. **排期约束输出**
   - 完成标准: 给出"任一层不得在其下层工作完成前结束"的排期原则,并标注哪些底层任务不可砍。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill
- 纯工程模块拆分(如后端服务划分)不在此模型内——这是 UX 决策层依赖,不是代码架构。
- 一次性、无后续迭代的临时物料(如活动海报)不必套用。

### 作者在书中警告的失败模式
- **砍底层制造债务**: 为赶进度砍战略/范围/结构任务,短期出活长期还债(ce05)。
- **上层错误削弱下层正确决策**: 视觉问题让用户秒退,永远发现不了你导航/交互的巧思。

### 作者的盲点 / 时代局限
- 对高度不确定的探索型产品(精益式),"战略尽早明确"偏刚性; 本书承认战略可演变,但排期上仍以底部为基础,对频繁 pivot 的适配有限。

### 容易混淆的邻近方法论
- 不要与"敏捷迭代=可以完全乱序"混淆: 本书允许双向连锁,但仍坚持"下层未完成前上层不结束"的约束,不是任意并行。
