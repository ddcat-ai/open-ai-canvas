## I — 方法论骨架 (Interpretation)

团队里关于"用户喜欢什么"的争论有一个特征：它**永远开不出结果**，而且每次复盘都觉得
"下次准备充分点就能吵明白"。不会的。Krug 的诊断是：这类争论是**信仰之争**，
它的结构决定了它不可能收敛。

两个原因：

**① 每个人都在拿自己当样本。** "我觉得下拉框挺好用的"——这句话的真实含义是
"我用着挺好"。而每个人的样本量都是 1，且这个 1 就是他自己。

**② 每个人被职位视角锁定。** 设计师看视觉一致性，开发看实现成本，
市场看转化和品牌，法务看风险，运营看能不能自己改。这些不是偏见，是他们的岗位要求
他们看的东西。争论表面上关于用户，实际上关于各自的职业世界观。所以谁也说服不了谁。

**关键洞察在于：这个争论的问题本身是错的。**

"大多数用户喜不喜欢下拉框？"——这个问题没有答案，因为没有"大多数用户"这个实体。
所有用户都是独一无二的，所有使用都是不一样的。

正确的问题形式是把它**降到具体上下文里，并改成关于体验而非偏好**：
"在这个页面、这个上下文、这几个措辞下，这个下拉框会不会让**大多数可能用户**产生
良好体验？"这个问题有答案，而且答案可以在一个上午、找三个人、看他们做一遍就得到。

所以本 skill 的核心动作有三步：**识别（这是信仰之争吗）→ 改写（把偏好命题改成可观察命题）
→ 移交（交给观察，不交给辩论）**。

还要拆掉三条常见的假出路：找专家意见、引用研究报告、发问卷/开焦点小组。
它们看起来客观，但回答的仍然是"平均人"——而平均人不存在。

## A1 — 书中的应用 (Past Application)

### 案例 1: 农场主与牧牛人
- **问题**：团队里不同角色对同一个设计决策持续对立。
- **方法论的使用**：Krug 借音乐剧《奥克拉荷马》的"农场主和牧牛人应该是朋友"作比——
  两方并非有人错了，而是各自的生存方式决定了他们看重不同的东西。
- **结论**：角色冲突是结构性的，不是态度问题。
- **结果**：不再试图"说服对方"，而是绕过争论去看真实用户。

### 案例 2: "因此我们不得不加上它"
- **问题**：某个元素被加进页面，理由是一连串内部推理。
- **方法论的使用**：作者引用团队原话并反讽"千真万确！"，指出这类推理链条完全建立在
  未经检验的用户假设上。
- **结论**：内部推理的自洽性不等于对用户成立。
- **结果**：把假设标注出来，等待被观察证伪。

### 案例 3: 越观察越发现用户不可归并
- **问题**：能不能通过更多研究找出"普通用户"？
- **方法论的使用**：作者说自己花大量时间观察真实用户，得到的是**相反**的结论——
  "你越是仔细观察用户，并倾听他们表述自己的意图和思考过程，就越能意识到
  他们对网页的个人反应和那么多不同的变量有关系"。
- **结论**：研究越深入，"普通用户"越站不住。
- **结果**：目标从"找出普通用户的偏好"改为"发现让大多数人卡住的具体障碍"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 评审会/需求会上为某个交互、文案、布局吵了几轮没结论。
2. 有人说"我觉得用户会……""我妈肯定看不懂""我朋友都是这么用的"。
3. 团队打算靠投票、职级、谁声音大来决定一个体验问题。
4. 有人提议"找个专家来拍板""发个问卷调研一下""开个焦点小组"。
5. 跨部门（产品/设计/开发/市场）对同一方案持相反立场且互相说服无效。
6. 需要向老板解释"为什么这个问题不能靠开会解决"。

### 语言信号（用户的话里出现这些就应激活）

- "大多数用户会 / 用户肯定喜欢 / 一般人都会"
- "我觉得用户 / 我朋友说 / 我妈肯定看不懂 / 反正我用着挺好"
- "要不投票吧 / 听老板的 / 找个专家来定"
- "发个问卷 / 做个调研 / 开个焦点小组"
- "average user / most users prefer / let's just vote / I think users will"

### 与相邻 skill 的区分

- 与 `diy-usability-test` 的区别：本 skill 是**诊断与改写**（识别信仰之争、把问题问对）；
  那个是**执行**（真的把三个人找来测一遍）。标准配合：先用本 skill 把争论改写成可测命题，
  再用它去测。单独用那个而不改写命题，测出来也裁决不了。
- 与 `premortem-doubt-injection` 的区别：那个针对**团队已经趋于一致**、需要注入怀疑的
  情形（事前验尸）；本 skill 针对**团队分歧不下**、需要拆掉错误前提的情形。方向相反。
- 与 `question-substitution-check` 的区别：那个查的是"难问题被悄悄换成了容易问题"
  （卡尼曼的替代）；本 skill 查的是"问题本身指向一个不存在的对象"。前者是偷换，后者是空指。
- 与 `expert-intuition-validity` 的区别：那个判断某个人的直觉**是否可信**；
  本 skill 主张即使可信也不该用它来裁决——因为这类问题应该由观察回答。
- 与 `nih-co-creation-buyin` 的区别：那个解决"对方不接受我的方案"；
  本 skill 解决"双方都不知道谁对"。

## E — 可执行步骤 (Execution)

1. **判定这是不是信仰之争**
   - 三条判据：① 争论对象是"用户喜不喜欢/会不会/懂不懂"；② 各方论据主要是个人经验
     或身边案例；③ 已经争过至少一轮且论据没有更新。
   - 判停条件：若争论对象是技术可行性、成本、排期、法务合规等**有客观答案**的问题，
     本 skill 不适用，立即说明并终止。

2. **把每个人的立场还原为"样本量 = 1 + 职位视角"**
   - 逐人写：他的真实论据是什么？他的岗位让他必须看重什么？
   - 完成标准：每个人的立场都被复述为"基于我自己的体验 + 我的岗位关心 X"，
     且当事人认可这个复述。这一步的目的是去人格化，不是揭短。

3. **宣布错误命题，写出正确命题**
   - 错误形式："大多数用户喜欢 A 还是 B？"
   - 正确形式："在【具体页面】的【具体上下文】里，用【这几个具体措辞】的 A，
     会不会让大多数可能用户顺利完成【具体任务】？"
   - 完成标准：新命题包含页面、上下文、措辞、任务四个具体要素，且**可被 3 人测试证伪**。

4. **拆掉三条假出路（如有人提出）**
   - 找专家 → 专家给的仍是一个人的判断，且他不了解你的上下文。
   - 引用研究 → 研究给的是平均值，平均人不存在；且研究的上下文与你不同。
   - 问卷/焦点小组 → 它们收集的是人们**说**的偏好，不是**做**的行为；
     适合最早期验证概念，不适合裁决界面。
   - 完成标准：每条被提出的假出路都有一句明确的反驳。

5. **移交观察**
   - 输出一份测试委托：测什么命题 / 用什么任务 / 找几个人（默认 3）/ 什么时候 /
     谁来主持 / 什么结果算 A 赢。
   - **必须预先约定判据**（在看结果之前），否则双方会各自解读录像。
   - 完成标准：判据被双方书面认可。转 `diy-usability-test` 执行。

6. **兜底：无法测试时的降级方案**
   - 若确实来不及测：选**可逆性更高、回滚成本更低**的那个方案先上，并记录待验证清单。
   - 完成标准：明确写下"这是一个未裁决的赌注"，避免它被当成已达成的共识。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **争论有客观答案**：技术可行性、性能、成本、排期、法律合规、安全风险。
  这些不是信仰之争，需要的是事实核查而不是用户观察。
- **纯资源分配冲突**（谁的需求先排期）：那是优先级与权力问题，用户观察裁决不了。
- **分歧只在数据解读上**：已有充分数据，双方对同一组数字有不同解释 → 需要的是
  分析方法论而非用户测试。
- **战略方向之争**（该不该做这个产品、要不要进这个市场）：可用性观察回答"能不能用"，
  不回答"该不该做"。
- **对方立场由 KPI 或已公开承诺锁定**：此时观察不会改变结论，见 `usability-buy-in` 的边界。

### 作者在书中警告的失败模式

- **试图找出"普通用户"**。作者明确说观察得越多，越会发现用户不可归并；
  继续寻找平均人是在找一个不存在的东西。
- **用专家意见/研究报告/问卷/焦点小组来终结界面争论**。它们回答的都是平均人的问题。
- **把"我用着挺好"当作证据**。这是样本量为 1 的自证。

### 作者的盲点 / 时代局限

- 第 3 版正文写于 2013 年，作者对**定量方法整体持回避态度**。今天 A/B 测试、
  分层埋点、行为分析已经普及，很多"A 还是 B"的争论确实可以用线上实验直接裁决
  （而且样本量足够大时，"大多数用户"在**行为频率**意义上是有效构念）。
  更准确的当代表述是：**偏好不可平均，行为可以统计**。
  凡涉及具体研究方法与工具的判断，需在当代语境下重新检验。
- 作者假设"观察结果会被团队接受"，但对**政治性阻力**只给出软性建议。
- 作者未处理 B 端多角色系统——那里"用户"本身就是几个诉求冲突的群体，
  裁决还涉及利益相关方权重问题。

### 容易混淆的邻近方法论

- **用户画像 / Persona**：Persona 是刻意构造的**典型代表**，用于对齐团队想象。
  它与"普通用户"的差别是：Persona 不宣称自己是平均值，只宣称自己是一个具体的人。
  用 Persona 对齐语言可以，用 Persona 裁决体验争论不行。
- **A/B 测试**：能裁决"哪个转化更高"，但不能告诉你"为什么"以及"用户卡在哪"。
  与本 skill + `diy-usability-test` 的组合互补：定量选方向，定性找原因。
