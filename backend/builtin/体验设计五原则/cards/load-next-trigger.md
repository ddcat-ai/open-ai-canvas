## I — 方法论骨架 (Interpretation)

投入阶段有三个作用：储存价值、改变态度、**加载下一个触发**。
第三个最容易被漏掉，而它正是闭环之所以是"环"的原因。

**核心区分：触发由谁发起**

| | 运营发起的触发 | 用户自己加载的触发 |
|---|---|---|
| 来源 | 排期、活动、召回策略 | 用户刚才的某个动作 |
| 合法性 | 需要理由，容易被视为打扰 | 天然合理——"是我自己要的" |
| 成本 | 每次都要花人力/预算 | 一次设计，长期自动运行 |
| 关闭风险 | 高（用户会关通知） | 低（关掉等于放弃自己的东西） |

> 判据一句话：**这条通知，能不能追溯到用户自己做过的某个动作？**
> 能 → 它是加载出来的触发；不能 → 它是运营推送。

**第二件工具：循环周期是可优化的杠杆**

多数团队只优化单次转化率，很少有人优化"循环转一圈要多久"。
但习惯的形成速度取决于**重复频率**，同样的转化率下，
把周期从 7 天压到 1 天，单位时间内的循环次数提升数倍。

度量方式：从"加载了一次触发"到"用户回访"的时长中位数。
压缩手段：改变提示的时间锚点（把"7 天后复习"改成"当晚睡前"）、
减少等待依赖（不必等他人回应即可产生反馈）、把大循环拆成小循环。

## A1 — 书中的应用 (Past Application)

### 案例 1: Any.do 的日历授权
- **问题**: 待办应用如何在不打扰的前提下让用户持续回来。
- **方法论的使用**: 用户授权日历（一次投入）后，
  每次会议结束时自动提示"要不要添加后续任务"——
  这条提示的合法性来自用户自己的日程，不是运营排期。
- **结论**: 一次授权可以持续生成无限次合法触发。
- **结果**: 触发与用户当下心境高度契合，回访自然发生。

### 案例 2: Snapchat 的消息往返
- **问题**: 如何让消息类产品自我循环。
- **方法论的使用**: 用户发出一张照片（投入）→ 对方收到并回复 →
  回复本身成为发送者的下一个触发。用户互为触发源。
- **结论**: 双向互动天然携带"加载下一个触发"，且周期极短（以分钟计）。
- **结果**: 在青少年群体中形成极高频的打开习惯。

### 案例 3: Tinder 的滑动与匹配
- **问题**: 如何让用户不断回来。
- **方法论的使用**: 每一次滑动（投入）都可能在未来产生一次匹配通知；
  匹配后聊天又生成新的通知。
- **结论**: 投入越多，未来被触发的概率越高——这是一个正反馈结构。
- **结果**: 滑动这一低成本动作撑起了持续的回访。

### 案例 4: Pinterest 的关注与转采
- **问题**: 内容平台如何让用户回来。
- **方法论的使用**: 用户关注了某个画板（投入），
  该画板的更新自动成为未来触发；用户的采集被他人转采，通知也回流给他。
- **结论**: 关注关系是一种可持续产生触发的储存价值。
- **结果**: 形成稳定的自然回访来源。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **用户完成核心动作后就消失了**，没有任何后续联系。
2. **回访完全依赖运营手动推送**，一停就没量。
3. **push 越发越多，打开率越来越低**——运营触发正在挤占自主型通道。
4. **闭环图画到第四步接不回第一步**（画不出闭环本身就是信号）。
5. **复访周期太长**（月活尚可、日活很差），需要压缩循环。
6. **已经做了投入设计**（用户在存东西），但这些沉淀没有产生任何提示。
7. **单人工具类产品**没有社交回路，需要设计自生触发。

### 语言信号 (用户的话里出现这些就应激活)

- "用户用完就走 / 一次性用户太多"
- "回访全靠我们推 / 不推就没人来"
- "推送发得越来越多，效果越来越差"
- "闭环最后一步怎么接回去"
- "怎么让用户自然想起来 / 自己回来"
- "复访间隔太长 / 月活还行日活很差"
- "close the loop" / "self-generated trigger" / "shorten the cycle"

### 与相邻 skill 的区分

- 与 `external-trigger-design` 的区别：那个覆盖**全部四类外部触发**的选型与时机
  （包含付费、回馈、人际、自主），是渠道层面的战略；
  本 skill 只处理其中一种特殊来源——**由用户自身投入自动生成的触发**。
  若问题是"该用哪条渠道、几点发"，转那个；
  若问题是"用户做完了但系统没生成任何后续"，用本 skill。
- 与 `investment-design` 的区别：那个管"让用户存什么、什么时候要、要多少"，
  本 skill 管"存完之后怎么把人叫回来"。
  本 skill 的输入是那个的输出，两者必须联用，否则闭环断裂（ce20）。
- 与 `hook-model-loop` 的区别：那个是全闭环分诊，
  本 skill 是分诊结论为"断在第四步接不回第一步"时的执行工具。
- 与 `variable-reward-design` 的区别：那个决定用户回来后得到什么，
  本 skill 决定用户为什么会回来。两者一前一后构成回访的完整理由。

## E — 可执行步骤 (Execution)

1. **列出用户的全部投入动作**
   - 从最近一次使用中盘点：他创建了什么、关注了谁、设置了什么、授权了什么。
   - 完成标准：至少 3 条具体动作。
   - 判停条件：一条都写不出 → 产品没有投入阶段，先转 `investment-design`。

2. **逐条问：这个动作能不能合法生成一次未来提示**
   - 合法 = 用户看到时会觉得"这是我自己要的"，而不是"你怎么又推我"。
   - 三种常见生成方式：
     - **他人回应型**：我发了 → 别人回了 → 通知我（消息、评论、匹配）。
     - **时间到期型**：我存了/设了 → 到点了 → 提醒我（复习卡、日程、订阅更新）。
     - **状态变化型**：我关注了 → 它变了 → 告诉我（价格、库存、作者更新、数据异动）。
   - 完成标准：每条投入动作标注可用的生成方式，或标注"不可生成"。

3. **为"不可生成"的投入补设计**
   - 常见解法：加一个用户自愿设定的时间锚点（"3 天后提醒我看这条"）、
     把单人动作接入他人（把笔记分享给同伴）、把静态沉淀接入变化源（关注主题）。
   - 完成标准：至少让 1 条原本"不可生成"的投入变成可生成。

4. **检查合法性与自主权**
   - 每条自动触发都要能回答："用户什么时候同意了这件事？"
   - 提供关闭入口，且关闭粒度要细（能关这一类而不必关全部）。
   - 判停条件：若找不到用户的同意点 → 这不是加载触发，是伪装成通知的运营推送，
     转 `external-trigger-design` 按自主型通道预算管理。

5. **度量当前循环周期**
   - 定义："加载一次触发 → 用户回访"的时长中位数（不要用均值）。
   - 完成标准：拿到一个具体数字，并按投入类型分组（不同触发的周期差别很大）。
   - 判停条件：若无法度量 → 先补埋点，这是本 skill 的核心指标。

6. **压缩周期**
   - 换时间锚点：把"7 天后"改为"当晚"，把"月度报告"改为"每次使用后"。
   - 去掉等待依赖：不必等他人回应才有反馈（先给系统级反馈，再给他人反馈）。
   - 拆大循环为小循环：把一个长任务切成多个可完成的小段，每段生成一次触发。
   - 完成标准：给出 1–3 个压缩动作及预期新周期。
   - 纪律：压缩周期 ≠ 增加发送量。若压缩的办法是"多发几条"，
     那是在消耗通道，不是提速循环（会引发 ce18）。

7. **验证闭环闭合**
   - 画出闭环图，确认第四步有一条实线指回第一步。
   - 完成标准：能说出一条完整链路：
     "用户做了 A（投入）→ 系统在 B 时刻生成 C（触发）→ 用户回到 D（行动）。"
   - 判停条件：画不出这条链路 → 闭环仍未闭合，回步骤 2。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **用户还没有任何投入行为**——无米之炊，先做 `investment-design`。
- **产品是真正的一次性工具**（查快递、转格式、办一次手续）——
  强行制造回访理由等于骚扰。
- **低频品类**——即使加载了触发，下一次循环也在半年后，收益极低（ce10）。
- **内部触发未知**——不知道用户在什么情绪下需要你，
  加载的触发也会落在错误的时刻（转 `internal-trigger-mining`）。
- **想用它来提高发送量**——本 skill 的目的是让触发**更合法**，不是更频繁。

### 作者在书中警告的失败模式

- **ce20 — 加载下一个触发缺失**（本 skill 的正对靶子）：
  用户投入了，但系统没把投入转化为未来触发，闭环变成单次直线。
  警告信号：用户行为不产生任何后续通知；回访完全依赖运营手动推送；
  闭环图上第四步指不回第一步。
- **ce18 — 触发时机与情绪脱节**：即便触发是自动生成的，
  若投递时刻不对（用户在开会/在睡觉）依然会被关闭。加载 ≠ 立即发送。
- **ce05 — 只做外部触发**：本 skill 是摆脱买量依赖的关键一环，
  但它不能替代内部触发的建立。
- **ce02 — 未经同意的自动通知**：把"用户做过某个动作"曲解为"同意接收一切相关推送"，
  会触发逆反，转 `autonomy-reactance`。

### 作者的盲点 / 时代局限

- 书中默认"加载的触发几乎必然送达"。今天系统级通知管控
  （通知摘要、分级授权、静默投递）使这一假设不再成立——
  即便是合法的自生触发，也要争夺有限的通知配额。
- **周期压缩没有下限讨论**：书中鼓励缩短循环，但未指出过短的循环
  会让用户感到被追赶（每次操作都立刻收到提示 = 骚扰）。
  实践中应设置合并与静默窗口，书中完全未涉及。
- 未讨论**多用户产品的触发放大**：一个用户的动作可能同时触发数十人，
  规模化后的总噪声是设计时看不见的（群消息即典型），需要有全局节流机制。
- 案例几乎全部来自社交/双向互动产品，
  **单人工具类**如何加载触发着墨很少——本 skill 步骤 3 是对这一空白的补充外推。

### 容易混淆的邻近方法论

- **生命周期营销的自动化流程（Marketing Automation / Drip Campaign）**：
  也是自动发送，但触发条件通常是"注册后第 N 天"这类时间轴，
  本质仍是运营发起；本 skill 要求触发源必须是**用户自己的具体动作**。
- **事件驱动通知（Event-driven Notification）**：技术实现高度相同，
  本 skill 补充的是"合法性判据"与"循环周期作为优化目标"这两层设计意图。
- **召回策略 / 流失用户唤醒**：面向已经离开的用户，属于补救；
  本 skill 面向仍在使用的用户，属于预防——两者时机与手段都不同。
- **Aha 时刻 / 激活指标**：关注首次价值体验；
  本 skill 关注的是第 N 次到第 N+1 次之间的桥梁。
