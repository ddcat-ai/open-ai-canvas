## I — 方法论骨架 (Interpretation)

这条定律把"好不好用"从一个审美/口味问题，换成了一个**可数的东西**：使用者在这个界面上
脑子里冒出了几个问号。

问号不是错误，界面不会报错，用户也不会投诉。它只是一次几百毫秒的停顿。但停顿会累积成
挫败，挫败会变成放弃。所以审查的对象不是"哪里做错了"，而是"哪里让人多想了一下"。

质量分三档，只有前两档及格：
- **不言而喻（self-evident）**：看一眼就懂，不需要任何解释。
- **自我解释（self-explanatory）**：需要一点推断，但推断毫不费力。
- **需要说明**：失败。加一段说明文字不能把它救回及格，只是把失败埋起来。

关键的方法论动作是**换判定人**。你自己是这个界面的作者，你永远不会在自己的界面上产生
问号。Krug 给了一个可操作的替身：你隔壁的邻居——对你的主题毫无兴趣、技术也不熟练。
判定标准是她能不能一眼说出"噢，这是……"。

还有一条容易被忽略的推论：认知负荷和功能多少无关。一个只有三个按钮的页面照样可以让人
满脑问号（三个按钮都不知道该点哪个）。所以"精简功能"不等于"降低认知负荷"，
本 skill 处理的是后者。

## A1 — 书中的应用 (Past Application)

### 案例 1: 隔壁邻居基准
- **问题**：团队都觉得自己的主页"很清楚"，因为他们知道每个词是什么意思。
- **方法论的使用**：Krug 把判定权交给一个虚拟的第三方——"你隔壁的邻居，她对你的网站
  主题毫无兴趣，也几乎不知道使用后退按钮"。
- **结论**：自明性不是作者说了算的属性，必须由非利益相关的普通人判定。
- **结果**：把"这够清楚了吧"这种无法证伪的争论，换成了一个可以真的去做的动作——
  找个外人看一眼。

### 案例 2: 问号清单
- **问题**：用户说不清"哪里不好用"，只说"感觉很别扭"。
- **方法论的使用**：Krug 把模糊的别扭感拆成一组具体问号：这里叫什么？我该从哪儿开始？
  他们把 X 放哪儿了？这个能点吗？这页上最重要的是什么？为什么他们要这么叫它？
- **结论**：模糊的体验问题总能被还原成有限的几个具体问号。
- **结果**：评审从"提意见"变成"逐条定位"，产出的是可修的清单而不是感受。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 手上有一个界面/页面/表单/文档要评审，想知道"哪里会卡住使用者"。
2. 数据或客服反馈显示某一步流失高、重复提问多，但不知道原因在哪。
3. 团队在为"要不要加一段说明文字"争论。
4. 要给别人写一份说明书、README、操作指引、错误提示，希望对方不用来问自己。
5. 内部工具/后台系统被同事吐槽"用不明白"。

### 语言信号（用户的话里出现这些就应激活）

- "用户看不懂 / 这里为什么没人点 / 一眼看不出来"
- "要不要加个说明 / 加个引导 / 写个提示"
- "这个按钮是干嘛的 / 这能点吗 / 入口在哪"
- "帮我看看这个页面（原型/表单/文档）有什么问题"
- "confusing / not obvious / users can't find / don't make me think / cognitive load"

### 与相邻 skill 的区分

- 与 `ability-simplification` 的区别：那个 skill 解决"用户做不到/嫌麻烦"——降低**执行成本**
  （步骤、门槛、体力）；本 skill 解决"用户没看懂"——降低**理解成本**。用户能看懂但懒得做 → 用前者；
  用户愿意做但不知道怎么做 → 用本 skill。
- 与 `bmat-behavior-diagnosis` 的区别：B=MAT 是行为未发生时的**归因分诊**（动机/能力/触发三选一）。
  它会告诉你"问题出在能力上"；本 skill 是能力/理解这一支的**具体查错工具**。先用它分诊，再用本 skill 落地。
- 与 `frontend-dev` 的区别：那是工程实现层（组件、样式、构建）；本 skill 完全不碰代码，只判断认知。
- 与 `omit-needless-words` 的区别：那个专治"文字太多"；本 skill 覆盖命名、布局、可点性、
  层次等全部问号来源，文字只是其中一类。

## E — 可执行步骤 (Execution)

1. **确定审查对象与"隔壁邻居"画像**
   - 拿到具体对象（截图、URL、原型、文档、命令行输出均可）。
   - 明确写下判定人：一个对该主题不感兴趣、不熟练、没有背景知识的普通人。
   - 完成标准：能一句话说出"我现在是以谁的眼睛在看"。

2. **一瞥（3–5 秒）后立刻记录第一印象**
   - 不许细读。记录：这是什么？我能在这做什么？最显眼的是什么？
   - 完成标准：三个答案都写下来了（写不出来本身就是发现）。

3. **逐处扫描六类问号，定位到具体元素**
   - ① 命名：这个词是什么意思？（行话、自造词、部门内部叫法）
   - ② 入口：我该从哪儿开始？（有没有一个明显的起点）
   - ③ 分类：X 会在哪一栏里？（分类是否互斥、是否符合用户心里的分法）
   - ④ 可点性：这个能点吗？（形状/颜色/位置三重线索是否到位）
   - ⑤ 层次：这页上最重要的是什么？（视觉突出是否对应实际重要性）
   - ⑥ 术语一致：同一个东西在不同地方是不是叫了不同的名字？
   - 完成标准：每个问号都指向一个具体元素，而不是"整体感觉不好"。

4. **对每个问号先问"能不能靠拿掉/改名解决"，最后才考虑加说明**
   - 优先级：改名 > 挪位置 > 改视觉 > 删掉某物 > 加说明。
   - 判停条件：若某处唯一可行解是"加一段说明"，标记为**设计失败点**，
     记入待重做清单，不当作已解决。

5. **排序并只交付前三条**
   - 按"影响人数 × 卡住程度 ÷ 修复成本"排序。
   - 完成标准：输出一张 ≤3 行的表（位置 / 问号 / 建议动作 / 预计效果），
     其余问号列在附录不占主表。

6. **给出验证方式**
   - 建议用 `diy-usability-test` 找 1–3 个真人验证，或至少找一个"隔壁邻居"看 5 秒。
   - 完成标准：明确写出下一步由谁、看什么、怎么判断修好了。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **需要从零生成设计方案时**。本 skill 只做诊断与裁剪，不产出创意方案（作者本人也不提供）。
- **专家/生产力工具的核心工作区**（IDE、Vim、Excel 公式栏、Photoshop、Figma、专业 CLI）。
  这类产品的价值恰恰来自用户愿意投入学习换取能力上限，把它们"做到不用思考"会砍掉效率天花板。
  正确做法是分层：新手路径遵循第一定律，专家路径提供密度与快捷方式。
- **高涉入决策场景**（购房、保险、医疗、大额 B 端采购、法律条款）。用户会真的逐字阅读，
  信息完整性与合规优先于简洁性。
- **需要刻意制造摩擦的地方**（删除确认、转账二次验证、风控问询、冥想/戒断类产品）。
  摩擦本身就是设计目标。
- **无目的消费型产品**（信息流、短视频、推荐流）。全书假设"用户带着明确任务而来"，
  对"滑着玩"的场景解释力很弱，此时主要杠杆是动机而非认知负荷。

### 作者在书中警告的失败模式

- **用"加说明"来治困惑**。作者的判断是：说明文字绝大多数人根本不读，加说明通常只是
  把设计失败埋得更深；正确动作往往是重做那个元素，或干脆拿掉。
- **用自己当判定人**。团队成员对自己的产品永远不会产生问号，这使得内部评审系统性失真。

### 作者的盲点 / 时代局限

- 本书第 3 版正文写于 2013 年。书中涉及具体浏览器行为、控件样式、设备形态的判断
  （如扁平化是"最新潮流"、响应式"很烦琐"）**均需在当代移动端与 App/小程序语境下重新检验**；
  但"消灭问号"这一认知层原则不受影响。
- 语境是英文桌面 Web。中文无空格分词、微信生态的返回/授权惯例等，需要本地替换后再套用。
- 作者只教发现问题，不教生成方案（他甚至主张"抵制添加的冲动"）。

### 容易混淆的邻近方法论

- **尼尔森十大启发式**：更全面的专家评审清单；本 skill 是它的极简版，只保留"认知负荷"一维，
  优点是快、门槛低、不需要专家。
- **Fogg B=MAT**：见 A2，分诊 vs 查错的关系。
- **信息架构重构**：如果问号集中在"分类"一项且遍布全站，说明是 IA 问题，
  本 skill 只能标记，需转专门方法（并参考 `trunk-test-navigation`）。
