# Open AI Canvas UI Design System

本文件是 `open-ai-canvas` 的 UI 设计总纲，面向 Codex、AI Agent 和项目协作者。它定义产品视觉方向、布局原则、组件语言、交互边界和评审标准，不替代具体页面的专项设计文档。

发生冲突时按以下优先级处理：

1. 用户对当前任务的明确要求；
2. `AGENTS.md` 中的产品、工程和安全约束；
3. 本文件的产品级设计原则；
4. `docs/design/` 下对应领域的专项设计合同；
5. 现有组件和页面的局部实现。

专项文档可以细化本文件，但不能在未经过设计评审时改变产品定位、核心工作流或状态语义。

## 1. 产品视觉定位

`open-ai-canvas` 是面向 AI 影视创作的专业生产工作台，不是聊天机器人、模型演示站或通用 SaaS 后台。

产品关键词：

- **Professional**：界面应支持持续、精确和高频操作，而不只是首次使用时容易理解。
- **Creative**：素材和创作结果优先于系统配置，用户始终能看到正在制作的内容。
- **Spatial**：画布、节点、连接、时间线和空间关系是主要信息组织方式。
- **AI Native**：AI 是可观察、可控制、可恢复的生产能力，而不是不可解释的一次性按钮。

默认视觉方向是深色、高信息密度、低干扰的专业创作环境。浅色主题必须保持同等层级和可读性，不能成为降级版本。

## 2. 核心设计原则

### 2.1 Canvas First

画布和创作内容永远是主角。工具栏、检查器、素材面板和 AI 面板用于辅助当前创作，不应长期遮挡主要工作区域。

- 高频操作靠近对象或画布提供。
- 低频配置采用可折叠面板、Popover 或设置入口。
- 不为了容纳控制项持续压缩画布。
- 不把画布操作改造成多级表单或页面跳转。

### 2.2 Context Preservation

用户完成操作时应保留当前对象、空间位置、选择状态和任务上下文。

- 点击节点后优先在 Inspector 或就近面板中编辑，而不是打开新页面。
- 临时操作结束后返回原来的画布位置和选中对象。
- 跨页面只用于真正独立的工作阶段，例如项目管理、完整剪辑和系统设置。
- Modal 只承载需要集中注意、明确确认或无法在原位置安全完成的任务。

### 2.3 Workflow Before Features

功能必须落入清晰的生产流程：

`故事构思 -> 分镜设计 -> 角色与场景资产 -> 图片生成 -> 视频生成 -> 剪辑与导出`

新增入口前先确认用户从哪里进入、输入来自哪里、结果落到哪里、失败后如何继续。不能只增加孤立按钮或没有下游出口的能力。

### 2.4 AI Transparency

AI 任务必须让用户知道系统正在做什么、使用什么输入以及接下来能做什么。

产品层统一表达以下状态：

`准备 -> 提交 -> 排队 -> 处理中 -> 完成`

异常路径必须明确表达：

`失败 -> 查看原因 -> 重试或调整`

需要恢复的本地或后台任务应表达：

`连接中断 -> 后台继续或等待恢复 -> 状态同步`

- 不使用永久旋转但没有说明的加载状态。
- 不把“本地缓存成功”显示成“服务端保存成功”。
- 不伪造取消、完成、额度或模型可用状态。
- AI 生成结果必须保留来源、版本或任务追踪入口。

### 2.5 Progressive Disclosure

默认显示当前步骤所需的核心控制，专业参数按需展开。

- 主操作必须清晰且唯一。
- 次要动作进入工具栏、上下文菜单或折叠区域。
- 高级参数不能压过提示词、素材和结果预览。
- 隐藏不等于不可发现：入口需要稳定位置、文字或可理解的图标。

### 2.6 Reversible and Safe

创作操作应尽可能可撤销、可恢复、可比较。

- 画布节点、连接和时间线修改遵守既有历史与命令协议。
- 删除、覆盖、扣费和批量操作必须说明影响范围。
- 生成结果优先产生新版本，不静默覆盖可用内容。
- 自动化操作完成后，应让用户看到实际改变并能继续编辑。

## 3. Layout System

专业工作区采用稳定的三段式空间模型：

```text
┌──────────────┬─────────────────────────────┬──────────────────┐
│ Navigation   │ Creative Stage              │ Context Panel    │
│              │                             │                  │
│ 项目与入口    │ Canvas / Storyboard / Preview│ Inspector / Agent│
│ 素材与工具    │ 当前创作内容                 │ 参数与任务状态     │
├──────────────┴─────────────────────────────┴──────────────────┤
│ Optional Timeline / Task Dock                                  │
└────────────────────────────────────────────────────────────────┘
```

### 3.1 Navigation

- 提供稳定的产品入口和项目范围切换。
- 不承担当前节点的大量参数编辑。
- 折叠后仍保留恢复入口和当前位置语义。

### 3.2 Creative Stage

- 占据页面主要面积，是视觉层级最高的区域。
- 根据工作阶段承载无限画布、分镜工作台、预览监视器或时间线。
- 空态应引导用户开始生产任务，而不是展示营销卡片集合。

### 3.3 Context Panel

- Inspector、Prompt、Asset、Character 和 Agent 面板围绕当前选择工作。
- 面板开合不能改变底层数据，也不能让用户丢失画布位置。
- 同一时刻只突出与当前任务最相关的上下文。

### 3.4 Timeline and Task Dock

- 时间线用于时间关系、片段编排和播放控制。
- 任务 Dock 用于持续观察生成、转写和导出任务。
- 二者不应被误做成普通页面底部卡片列表。

工作区外壳的具体尺寸、折叠和响应式合同见 [工作区外壳设计](design/workspace-shell-design.mdx)。

## 4. Design Token System

全站遵循三层 token：

```text
Primitive -> Semantic -> Component
```

### 4.1 Primitive

保存无业务语义的基础值，例如颜色阶、尺寸、圆角、透明度和动效时长。业务组件不应直接依赖 Primitive token。

### 4.2 Semantic

表达用途，例如：

- `background`：工作环境底层；
- `surface`：内容或工具表面；
- `foreground`：主要文字和图形；
- `muted`：辅助信息；
- `border`：结构边界；
- `accent`：主操作和当前焦点；
- `success`、`warning`、`danger`、`info`：状态语义。

### 4.3 Component

表达具体组件合同，例如 Node、Panel、Dock、Input、Overlay 和 Timeline 的表面、边界、状态、尺寸与阴影。

要求：

- 业务组件优先消费 Semantic 或 Component token。
- 明暗主题必须成对定义。
- 皮肤通过 token 映射实现，页面不能按皮肤 ID 编写条件样式。
- Ant Design 与自研组件必须从同一语义层获得颜色和交互状态。
- 新增颜色、圆角、阴影、层级或动效前，先检查现有 token 是否已覆盖。
- 不在 JSX inline style 或局部 CSS 中散落可复用的视觉字面值。

具体皮肤模型和运行时适配见 [站点外观与皮肤主题](design/site-appearance-and-skins.mdx)。

## 5. Component Rules

### 5.1 Node

节点统一由以下区域组成：

```text
Header -> Preview or Content -> Status -> Contextual Actions
```

- Header 表达节点类型、名称和主要状态。
- Preview 优先展示创作结果，不增加无意义装饰层。
- Status 表达模型、任务、版本、规格或资源状态。
- Actions 根据选中或悬停出现，避免默认堆满按钮。
- 节点类型通过图标、标签和内容共同表达，不能只依赖颜色。
- 选中、关联、连接目标、生成中、失败和禁用必须可区分。
- 节点视觉修改不得改变节点 ID、坐标、连接、原始媒体比例或任务语义。

节点和连接的专项视觉合同见 [画布节点可读性设计](design/canvas-node-visual-contrast.mdx)。

### 5.2 Panel

面板统一由以下区域组成：

```text
Title -> Optional Toolbar -> Content -> Optional Footer
```

- Title 说明当前对象或任务，不使用泛化标题。
- Toolbar 只保留高频且与上下文相关的动作。
- Content 保持可滚动，滚动不能泄漏成画布缩放。
- Footer 只放持续可见的主操作或状态，不复制顶部工具栏。
- Inspector 修改应实时反馈或明确要求保存，不能混用两种模式而没有提示。

### 5.3 Toolbar and Dock

- 工具按创建、选择、视图、生成和辅助能力分组。
- 持续状态与一次性命令必须使用不同反馈。
- 常用命令保持固定位置，不能随节点类型无规律跳动。
- 图标按钮必须提供可访问名称；仅在行业语义足够稳定时省略常驻文字。
- 画布顶部和底部浮动控件的具体合同见 [画布浮动控件设计](design/canvas-floating-controls.mdx)。

### 5.4 Overlay

- Popover：少量就地选择或轻量设置。
- Drawer/Inspector：持续编辑当前上下文。
- Modal：阻塞确认、集中式复杂任务或媒体编辑。
- Full-screen Workbench：独立且包含多个连续步骤的生产流程。
- Toast：短暂结果反馈，不承载需要用户记住的错误细节。

禁止为同一操作叠加多层 Modal。浮层必须处理焦点、Escape、点击外部、滚轮和画布 pointer 边界。

### 5.5 AI Task Presentation

任务显示至少应回答：

1. 正在执行什么；
2. 当前处于哪个阶段；
3. 使用了哪些输入或模型；
4. 是否仍会在后台继续；
5. 失败后用户可以采取什么行动；
6. 完成结果保存到了哪里。

## 6. Typography, Density and Iconography

- 信息密度服务于专业效率，不等于缩小所有文字和点击区域。
- 标题、正文、标签、数值和辅助说明使用稳定层级。
- 参数、时间码、尺寸和额度使用便于比较的数字表现。
- 图标保持统一来源、尺寸和描边；品牌或模型图标使用真实资产，不用通用占位图标长期替代。
- 文字能准确说明操作时，不为了“简洁”改成含义不明的单图标。
- 页面不通过大量卡片、渐变和装饰性标题制造层级。

## 7. Motion

动效应快速、有目的并能解释状态变化。

允许的目的：

- 表达面板出现、消失和空间来源；
- 保持节点移动、展开和批量结果的连续性；
- 表达任务进行、成功、失败和恢复；
- 帮助用户理解焦点或选择发生了变化。

禁止：

- 与操作无关的循环装饰动画；
- 导致画布、面板或工具位置漂移的入场动画；
- 用动画掩盖真实等待时间；
- 忽略 `prefers-reduced-motion`。

## 8. Accessibility and Responsive Behavior

- 所有主要操作必须可通过键盘到达，并保留 `:focus-visible`。
- 图标按钮、切换、折叠和拖拽替代操作需要正确的可访问名称或状态属性。
- 状态不能只通过颜色表达。
- 深色和浅色主题都必须满足文字、节点边界和交互状态的基本可辨识度。
- 窄视口优先保留创作内容和主操作，次要面板折叠或转为临时层。
- 触摸交互需要区分平移、缩放、选择、拖拽和内部滚动。

## 9. Prohibited Patterns

未经设计评审，不得引入以下模式：

- 普通 SaaS Dashboard 风格作为主要创作界面；
- 为展示功能而堆叠大量同质卡片；
- 节点操作频繁跳转到独立页面；
- 多层嵌套 Modal；
- 把 AI 交互退化为只有聊天窗口的产品形态；
- 隐藏任务失败、保存位置、额度消耗或后台继续状态；
- 用纯视觉修改改变业务语义；
- 为单个页面建立平行的颜色、按钮、表单或浮层体系；
- 因 UI 重构改写 Canvas Store、节点 ID、连接系统或时间线命令协议。

## 10. UI Change Review

重要页面或组件进入实现前，必须明确：

- 用户目标与当前工作阶段；
- 主操作、次要操作和下一步；
- 数据来源、保存位置和错误路径；
- 对 Canvas、项目、任务、素材和插件边界的影响；
- 是否复用现有组件与 token。

实现完成后至少检查：

- 页面截图与主要交互说明；
- 深色、浅色、空态、加载、成功、失败和禁用状态；
- 键盘焦点、滚动、浮层、窄屏和减少动画偏好；
- 是否降低操作成本并保留创作上下文；
- 是否产生重复组件、重复 CSS 或新的视觉字面值；
- 是否修改了任务之外的交互逻辑。

代码完成不代表产品验收完成。重要 UI 需要经过设计评审后才能视为最终形态。
