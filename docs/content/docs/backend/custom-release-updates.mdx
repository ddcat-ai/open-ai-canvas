# 定制版本与更新保护

Host Updater 部署的是完整发行镜像，不合并本地源码。自定义修复必须保存到自己的 Git 分支或 Fork，经过验证后构建并发布自己的镜像；不能靠容器内修改或数据库备份保留代码。

## 默认禁止来源不明的覆盖

部署 `.env` 中的以下字段由更新器读取，不是浏览器端开关：

| 字段 | 含义 |
| --- | --- |
| `CANVAS_UPDATE_POLICY` | `manual` 禁止更新和人工回退；只有 `managed` 才进入来源核验。缺失或其他值同样禁止覆盖 |
| `CANVAS_RELEASE_REPOSITORY` | 当前发行仓库，必须与 Host Updater 的 `CANVAS_UPDATER_REPOSITORY` 完全一致 |
| `CANVAS_RELEASE_COMPOSE_SHA256` | 当前受管 Compose 的 SHA-256，文件发生修改后禁止替换 |
| `CANVAS_BACKEND_IMAGE`、`CANVAS_WEB_IMAGE`、`CANVAS_YINGCE_AGENT_IMAGE` | 三个服务必须固定为发行方对应 GHCR 仓库的 digest |

源码开发默认使用 `manual`。安装脚本仅为同一官方 Release 的镜像与 Compose 自动登记 `managed`；其他来源保持手动维护。旧部署缺少字段时不会自动推断为官方版，仍可检查新版本，但不能执行覆盖更新。

后台“定制部署保护”会显示本地策略、发行来源和 Compose 校验失败的原因。即使绕过页面直接调用更新 API，更新器也会拒绝。运行时核验在开始更新、预检及停服前再次执行，包括：

- 容器实际使用的镜像引用与登记的 digest 一致；镜像本身具备对应仓库的 RepoDigest，本地构建或仅重新打标签不能代替此校验。
- 容器来自受管 Compose，没有叠加其他 Compose 文件。
- 程序目录没有被额外挂载覆盖，容器可写层的 `/app`、`/usr/local/bin`、`/opt/canvas-release` 没有被改动。
- Docker 信息不可读、服务未唯一运行或来源信息异常时拒绝更新。

更新成功切换 Compose 后刷新校验值；更新器自身失败触发的自动回退使用此次保存的旧环境与编排。人工回退也需要通过保护检查，避免用回退入口覆盖定制代码。若服务损坏导致无法核验运行容器，应由管理员按备份手工恢复，不绕过检查。

## 自有发行流程

1. 将修复提交到自己的仓库，并记录所基于的上游版本。
2. 在开发分支合并上游更新、解决冲突并运行相关验证。
3. 发布自己的 Web、Backend、Agent 镜像和 Release，固定镜像 digest；Host Updater 当前要求镜像命名为 `ghcr.io/<owner>/open-ai-canvas-{backend,web,yingce-agent}`。
4. Release 需要提供匹配的 Compose 与更新器附件。将更新器仓库配置为自己的发行仓库，不能继续指向官方仓库。
5. 完成镜像来源、Compose、数据库和数据备份核验后，再由维护者登记受管策略、发行仓库及当前 Compose 校验值。不要仅把 `manual` 改成 `managed`。

缺少发行流水线时，保留 `manual`，使用自己的源码构建部署。Host Updater 不承担源码合并、冲突解决或自定义功能回归验证。

## 生效与保护范围

必须安装包含本保护逻辑的 **Host Updater 二进制**；仅更新业务 Backend、Web 或新增 `.env` 字段，无法约束旧更新器。升级旧更新器之前应停用其更新入口，先备份并核验部署。

这些检查用于防止误操作，不是对拥有宿主机权限的管理员的安全隔离。数据卷中的插件、前端资源和配置不属于容器可写层检查范围，仍需独立备份与版本管理；来源核验也不等于镜像签名验证。自定义数据结构仍需迁移与回归测试。
