# Figma、飞书文档与影策实时协作对照

上游移植说明：本文保留原协作方案与调研过程；当前代码入口为 internal/canvas 领域层和 internal/app 组合根，API 客户端为 http，迁移接续 v30/v31。实际交付合同、跨账号媒体权限限制与本次验证见 [共享协作画布](./canvas-collaboration) 和 [待测试](../progress/pending-test)。原分支的测试数量/浏览器记录不等于本次上游验收。

## 结论与证据范围

建议采用 Figma 的“本地立即显示、服务端确定顺序、操作增量广播”作为画布协作的基础；界面参考文档产品，把在线成员、输入状态和同步状态放在前面，把历史和独立方案放到用户主动打开的协作面板。

**实时传输、并发合并、持久化是三个不同问题。** WebSocket 解决及时送达；字段和结构规则解决同时修改时保留什么；操作回执、数据库事务和本地队列解决断线后能否可靠恢复。仅把轮询改成 WebSocket，不能自动解决数据覆盖。

本报告使用以下证据边界：

- Figma：完整阅读 Evan Wallace 于 **2019-10-16** 发布的官方架构文章。以下算法描述对应该文章，不能据此断言 2026 年所有 Figma 产品和文本编辑仍完全相同。
- 飞书：核对官方文档产品页、官方 Go SDK 的 Docx 批量更新协议和示例。本轮取得的资料未确认浏览器内部采用 OT、CRDT 或混合算法，也没有确认其内部实时传输协议。
- 影策：依据当前本地 React/Go 实现和专项测试。没有用两个真实账号测得端到端延迟，也没有把本轮改动部署到线上。
- 100～300ms 等数字是我们的候选验收目标，不是 Figma、飞书的公开 SLA，也不是本轮实测结果。

## 一、Figma 怎样同步

### 1. 打开时快照，编辑时操作

公开设计使用中心化客户端/服务端架构，浏览器通过 WebSocket 连接多人服务。文章当时的部署方式是每份协作文档对应一个进程，编辑同一文件的人连接到同一文档进程。

打开文件先下载内容，之后双向传输更新。离线时继续本地编辑；重连时重新下载最新文件，把离线编辑应用到最新状态上，再恢复同步。

评论、用户、团队、项目等元数据使用另一套基于 PostgreSQL 的系统。文章明确区分了它们与文档编辑同步：不同业务不必挤在一条高频内容通道里。

**我们应借鉴：** 画布操作走低延迟通道，媒体上传、生成任务、账务和版本快照走各自流程；大视频上传不应阻塞另一个画布的位置更新。

### 2. 按“对象 ID + 属性”确定最终值

可把公开模型理解为：

```text
对象 ID
  ├─ 位置
  ├─ 尺寸
  ├─ 颜色
  └─ 文字属性
```

不同对象，或同一对象的不同属性，可以各自更新。同一对象同一属性同时被修改，最终采用服务端最后收到的值。顺序由服务端决定，不依赖两个用户电脑上的时钟。

文章直接给出文本例子：原文 B，A 改成 AB，B 改成 BC，最终是 AB 或 BC，不会自动得到 ABC。该公开设计没有为此实现逐字文本合并。

这借用了 CRDT 的部分思想，但不是直接使用完整的去中心化 CRDT，也不是把传统文本 OT 套到所有图形属性上。

**对影策的取舍：**

- 位置、尺寸等视觉属性可以评估按服务端顺序确认，配合拖动占用提示；这属于下一阶段策略调整。
- 提示词、模型配置和生成输出不能照搬静默覆盖。提示词看似只差几个字，却可能改变生成含义和费用，应保留双方并在必要时确认。
- 当前影策位置也执行基线冲突检查，尚未改成 Figma 式同属性最后写入生效。

### 3. 本地先显示，防止远端消息导致跳动

假设节点位置原本是 0：

1. 我拖到 100，屏幕立即显示 100，提交尚未确认。
2. 此时收到别人较早提交的位置 50。
3. 如果立刻显示 50，稍后我的提交确认又显示 100，节点就会闪回。
4. Figma 公开方案暂时忽略与本地未确认属性冲突的远端值，使显示符合“本地操作最终可能被确认”的预测。

这里不代表永久丢弃远端数据。应区分“服务端已确认的真实状态”与“叠加本地待确认编辑后的显示状态”，并在确认或拒绝时收敛。

影策本轮已让普通远端增量在当前画布内应用，保留未提交的独立字段修改；但有持久化发送队列时，当前仍先完成该队列的回执恢复，再接纳远端状态。高并发时进一步穿插远端增量，仍需精细化队列设计。

### 4. 删除、树结构与排序有专门规则

Figma 的公开设计中，创建和删除是明确操作；给一个不存在的 ID 写属性不能让它自动复活。ID 可在客户端生成，以支持离线创建。

父子关系放在子对象上，移动到另一个父级时保持对象身份。服务端拒绝形成环的父级更新。例如 A 成为 B 的子项，同时 B 成为 A 的子项，最终不能形成环。

子项顺序采用 fractional indexing；**父级和父级内的排序值必须作为一个整体更新**，不能分别合并后拼成不合法状态。文章也坦承客户端可能短暂出现循环，直到服务端拒绝操作后恢复。

影策既有分组关系又有工作流连线，两者不一定遵循同样约束。需要分别定义是否允许多父级、环路、失效依赖，不能把所有线都当作 Figma 图层树。

删除后的数据保留策略也不同：该文章将删除对象的数据保留在执行删除的客户端撤销缓冲中。影策需要服务端历史恢复、生成结果溯源和跨设备找回，应保留自己的历史与生命周期记录。

### 5. 协作撤销不能直接恢复旧画布

Figma 文章提出：撤销会调整重做历史，重做也会调整撤销历史，避免把其他人的后续编辑覆盖掉。

影策本轮只做了保守保护：远端变化不进入我的撤销历史；与远端修改重叠的旧撤销项被移除，避免本地 Ctrl+Z 覆盖他人内容。**这还不是完整的协作撤销。** 后续需要提交带条件的反向操作，保留无关字段的撤销能力。

## 二、飞书哪些机制有官方依据

### 1. 产品层：多人实时编辑是日常能力

飞书文档官方产品页明确描述多人实时编辑和数据实时多端同步。值得借鉴的是用户任务层级：打开即可共同编辑，版本编号和请求协议不成为日常编辑步骤。

我们的体验建议是：顶部头像表示谁在线，节点边框和光标表示谁在处理哪里，轻量状态表示是否已同步；只有确实需要用户决定时才弹出冲突。

上述交互建议不等于本轮实测了飞书每一种冲突情形。本轮没有操作飞书账号验证删除、恢复和断网的全部行为。

### 2. 开放协议：块、版本、幂等和批量

官方 SDK 的批量更新接口为：

```text
PATCH /open-apis/docx/v1/documents/:document_id/blocks/batch_update
```

| 官方 SDK 字段或约束 | 可以确认的含义 | 对影策的启发 |
| --- | --- | --- |
| document_id、Block ID | 文档和块有稳定身份 | 画布、节点、连线分别有稳定 ID |
| document_revision_id | 指定要操作的文档版本；-1 表示最新；新文档从 1 开始 | 版本用于校验和恢复游标，不必显示给普通用户 |
| client_token | 非空时用于幂等更新，响应也带回该标识 | 网络重试必须复用同一 opId 和内容 |
| Requests 批量更新 | 一次请求包含多个块更新 | 可以减少 N 个顺序网络往返 |
| 同批不能重复 Block ID | 同一批次内不能多次更新同一块 | 批次需有确定顺序和清晰边界 |
| 响应的 document_revision_id | 返回更新成功后的版本 | 以服务端确认结果推进基线 |

不能从这些 API 推导出浏览器内部协同编辑算法，也不能推导批量请求一定具有我们希望的全部事务语义。实现影策批量协议时仍需自行规定“整体成功或失败”、幂等和冲突响应。

**不要把 -1 最新版本理解为解决冲突。** 在最新版本上执行旧页面构造的整份覆盖，仍可能抹掉他人内容。版本、操作基线和合并规则需要一起工作。

### 3. 尚不能确认的内部细节

本轮官方资料不足以确认飞书的逐字冲突算法、服务端排序方式、浏览器 WebSocket 消息结构、离线重放策略、冲突时的删除优先级和延迟 SLA。

因此本报告不写“飞书就是 OT”或“飞书就是 CRDT”。如果未来产品确实需要同一长文本逐字协作，应独立评估 OT 或文本 CRDT，而不是根据未经核实的厂商架构选型。

## 三、与影策的实际差异

| 维度 | Figma 官方公开设计 | 飞书本轮可确认依据 | 影策当前本地代码 |
| --- | --- | --- | --- |
| 传输 | 快照 + 双向 WebSocket 更新 | 产品支持多人实时编辑；内部协议未确认 | REST 提交 + WebSocket 已提交增量；5 秒补偿拉取 |
| 修改单位 | 对象属性 | 公开 API 使用文档块 | 节点顶层字段；metadata 仍整体校验；连线部分路径仍比较全集 |
| 同字段冲突 | 服务端最后收到的值生效 | 浏览器内部算法未确认 | 基线/我的/最新比较；冲突保留草稿 |
| 本地显示 | 立即显示；保护未确认属性，减少闪回 | 产品体验可参考 | 原地应用增量；独立编辑自动重放；发送队列期间保守等待 |
| 重试 | 文中描述离线重连重放 | client_token 幂等更新 | opId 与完整请求先落本地；丢回执后复用原请求 |
| 删除 | 显式删除，不靠属性写入复活 | 本轮资料不足 | 生命周期 incarnation；结构事务；旧修改拒绝 |
| 临时在线状态 | 产品具备实时协作状态 | 产品体验可参考，内部协议未确认 | 光标/输入状态独立；HTTP 心跳和轮询，Redis 可共享 presence |
| 多实例内容广播 | 当时按文档进程组织连接 | 本轮资料不足 | 内容 Hub 仍是实例内存，尚无跨实例广播 |
| 撤销 | 协作撤销/重做历史互相调整 | 本轮资料不足 | 远端更新不进入本地历史，冲突的旧撤销项保守失效 |
| 分支/恢复 | 本轮引用文章未论述分支合并 | 不从 Docx API 推断分支能力 | 已有独立方案、三方预览与恢复；仍须业务场景验收 |

## 四、本轮已改动的同步链路

```text
编辑器立即显示
  → 内容进入本地保存
  → 150ms 防抖，连续输入最多等待 500ms 调度
  → 保存按账号/画布隔离的确切待提交请求
  → REST 提交，服务端事务校验并生成回执
  → 事务成功后 WebSocket 广播规范化增量
  → 接收端更新已确认状态，叠加自己的独立编辑
  → 当前画布原地显示，不重新加载编辑器
```

500ms 是调度等待上限，不包含先前请求、媒体上传、数据库锁等待和网络时间。当前仍有全局同步串行区，不能将其宣传为端到端耗时上限。

| 原问题 | 本轮处理 |
| --- | --- |
| 前后端有 WebSocket，但页面代理未转发升级 | Vite 与 Nginx 增加协作专用代理规则；Vite 实际握手/消息转发测试通过 |
| 要等下一次轮询才能看到更新 | 提交成功立即推送可应用增量；轮询只做补偿 |
| 收到通知就重新读取整张画布 | 连续 revision 直接应用；缺口或恢复才补拉 |
| 整页重新加载打断编辑和视口 | 更新节点、连线和内容，保留本地视口 |
| 别人移动节点导致我的文字进入冲突 | 比较共同起点，合并独立字段 |
| 无变化的轮询把本地状态误标成已保存 | 无变化时不改内容、不改同步状态 |
| 回执丢失后重建操作可能重复新增 | 本地持久化原 opId、基线和请求体；重试不换身份 |
| 一批操作部分成功后不知从哪里恢复 | 逐次保存已确认回执和剩余队列 |
| 保存确认时覆盖刚输入的内容 | 回执之上重放发送期间的新编辑；冲突保持可见 |
| 点击重试却加载最新内容 | 重试只重发待保存内容；加载最新是独立的明确动作 |
| 普通协作更新不断通知 | 正常更新静默应用，真正冲突才需要用户处理 |
| 慢客户端丢消息后无提示 | Hub 队列溢出保证留下 resync 标记 |
| 广播内容与落库内容不同 | 增量来自服务端提交结果，包含规范化属性和生命周期标记 |

接口仍使用现有登录 Cookie。WebSocket 升级前校验登录与画布权限，复用应用 CORS 决策校验 Origin；发内容前再次检查访问资格。恢复快照不作为增量直接散发，客户端通过有权限校验的接口重新读取。

本轮没有增加数据库结构迁移。新队列位于当前账号隔离的本地 IndexedDB；服务端仍复用已有操作回执表。

### 当前边界

- 同一节点的位置与提示词可独立处理；metadata 内不同配置尚未普遍拆开。
- 真冲突目前暂停该画布自动提交，尚未做到只暂停冲突操作及其依赖。
- 一次保存仍可能顺序发送多个 REST 请求。
- 复制的新节点及相互连线可以组成原子创建操作；不能把“整个自动保存产生的多个请求”宣传为一个事务。
- presence 仍是 HTTP 心跳/轮询，没有迁到 WebSocket。
- 内容广播尚未接入 Redis；配置了 Redis presence 不代表跨实例内容推送已经完成。
- 全部任务、Agent、历史恢复、方案合并写入路径还需统一验收，不以普通节点测试替代。
- 本地磁盘满、浏览器清理数据等故障不能保证草稿一定持久化；保存失败时保留内存内容并明确提示。

## 五、下一步按收益排序

| 优先级 | 改造 | 为什么需要 | 完成标准 |
| --- | --- | --- | --- |
| 第一批 | presence 走实时连接 | 光标/输入状态还受轮询限制 | 在线光标平滑；掉线超时消失；不增加内容版本 |
| 第一批 | 按画布调度同步 | 当前一份素材上传或长请求可阻塞其他画布 | 不同画布独立推进；同画布严格有序 |
| 第一批 | 操作批次协议 | N 个顺序请求会叠加网络往返 | 一批有一个稳定身份；明确原子边界；失败可重试 |
| 第一批 | 逻辑字段组、连线按 ID 操作 | metadata 和连线全集扩大冲突范围 | 不同业务字段与独立连线能自动合并；关联字段一起校验 |
| 第一批 | 冲突只阻塞相关操作 | 一个提示词冲突会暂停整张画布 | 独立节点继续同步；依赖操作及原子批次整体暂停 |
| 多实例前 | Redis/文档房间路由 + 可靠补偿 | 内存 Hub 无法通知另一实例 | 跨实例、进程重启、提交后广播前崩溃均能恢复 |
| 大画布前 | 小回执、压缩快照、节点状态批处理 | 每个操作仍可能保存完整文档并遍历节点 | 数据量和 SQL 次数随改动量下降；历史仍可恢复 |
| 第一批验收 | 所有内容写入统一走协作规则 | 旧任务完成、恢复或合并可能绕开前端路径 | 输入变化、节点删除、恢复后旧任务均不覆盖新结果 |
| 后续 | 条件反向操作实现协作撤销 | 当前保守丢弃重叠撤销项不够好用 | 撤销我的字段，不覆盖他人后续修改 |

建议的 presence 发送上限可先试 20Hz：只发最近光标位置，拖动过程发临时预览，松手才提交持久化位置。此频率是设计起点，需要按人数、节点规模和设备测量调整；广播前必须校验权限和消息大小，不能每帧写 PostgreSQL。

批量提交可以先保留 HTTP，再考虑 WebSocket 写入。HTTP 与 WebSocket 都能传小操作；**消息粒度、排队、数据库成本和渲染，比单纯更换提交协议更决定体验。**

跨实例 Redis Pub/Sub 不能单独保证消息不丢。应由 PostgreSQL 操作记录作为补偿来源；需要更严格保障时，在同一事务记录 outbox，再异步发布，解决“数据库提交后进程退出、通知没发出”的窗口。

## 六、用户真正会遇到的情况

以下为目标交互；标注待完善的条目不能视为全部已经交付。

| 情况 | 系统规则 | 用户体验 |
| --- | --- | --- |
| 不同节点同时修改 | 各自保留 | 无提示，内容自然出现 |
| 同一节点移动与改提示词 | 不同字段合并 | 位置和文字都保留 |
| 同一提示词改成相同内容 | 视为一致 | 无需选择 |
| 同一提示词改成不同内容 | 保留双方，不静默覆盖 | 当前画布提示“这段内容也被某人修改”，只处理该项 |
| 先删除，再收到旧编辑 | 拒绝旧生命周期的编辑 | 保留我的内容，可另存新节点 |
| 先修改，再收到基于旧内容的删除 | 重新确认删除 | 明确展示节点刚被修改 |
| 新增子节点/连线先成功，删除后到 | 删除校验所见关系，不能顺手删掉未知关系 | 展示新增关联，确认后再删 |
| 删除先成功，子节点/连线后到 | 指向已不存在节点的结构写入失败 | 子节点草稿保留，选择新的连接位置 |
| 删除后明确恢复 | 新公共操作、更新生命周期；旧请求不能借恢复复活 | 相关成员看到“某人恢复了某节点”，可查看活动 |
| 方案合并存在冲突 | 主画布保持原状，先比较后确认 | 在当前画布弹窗中列出少量冲突，其他差异自动合并 |
| 预览合并后目标又被改 | 拒绝过期确认，重新计算差异 | 保留选择，提示重新核对最新内容 |
| 回执丢失后重试 | 同一操作返回既有结果 | 不重复复制节点，不重复推进内容版本 |
| 断网编辑 | 明确标注本机未同步，恢复后校验和重试 | 不把本地缓存说成云端已保存 |

删除与恢复的身份通知、依赖链阻塞、关系端点生命周期、全部任务写入和多层方案合并还需独立验收。不能仅靠“有 incarnation 字段”就认为所有结构路径都安全。

方案入口继续使用“创建独立方案”“返回主画布”“合并到主画布”等业务语言。Git 式分支适合长期创意试验，不应让每次共同编辑都变成手工提交、拉取和合并。

## 七、怎样确认达到毫秒级

建议测三个独立指标：

1. **本机反馈**：输入/拖动到本机可见，争取在一帧内完成。
2. **服务端确认**：操作进入队列到提交成功，反映保存可靠性和数据库耗时。
3. **另一成员可见**：A 的操作形成到 B 实际渲染，包含防抖、网络、排队、提交、广播和渲染。

```text
远端可见延迟 =
  客户端合并等待 + 上行网络 + 服务端排队/数据库提交
  + 广播/下行网络 + 客户端合并/绘制
```

候选目标为普通在线编辑远端可见 P50 100～300ms、P95 小于 500ms；必须明确测试的网络 RTT、地区、设备、节点数和用户数。含150ms防抖的内容操作和20Hz临时光标不能混在同一份统计中。

验收矩阵应包含 2/5/20 人、100/1000 节点、前后台切换、100ms/300ms 网络延迟、断线、重复提交、乱序、消息缺口、磁盘失败、撤权、节点删除/恢复、批量复制和并发方案合并。观察 P95/P99、错误率、消息大小、SQL 次数和浏览器长任务，不只看平均时间。

## 八、原实现验证与剩余验证

原分支记录：前端协作合并、增量应用、保存版本与队列专项测试共 39 项通过；覆盖部分成功、丢回执重放、保存期间新编辑、草稿写入失败和账号隔离。另有 1 项真实 Vite 代理测试通过，验证临时回显服务的 WebSocket 升级和消息转发，不接入业务数据库。前端 TypeScript 检查和 Go 协作 service/handler 专项测试通过，后者覆盖广播、回放一致性、拒绝写入不广播、生命周期标记、Origin 校验和 Hub 队列溢出。

尚未完成两个真实浏览器账号的本轮 UI 验收、生产 PostgreSQL 并发/延迟压测、Nginx 容器与外层代理运行验收、跨实例广播和全部业务写入集成验证。后端全包测试此前另有模型能力测试失败，不能把专项通过写成全仓通过。

本轮没有部署、迁移生产数据库或改变本地运行时的数据库配置。现有后端单元测试的内存数据库只用于隔离测试，不代表把实际开发服务换成 SQLite。
