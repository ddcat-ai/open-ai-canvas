# 浏览器 Agent 改造计划审计

审计对象：`browser-agent-worker.md`，基线 `eff6905a`。审计结论：方向可行，但当前计划尚不足以直接指导完整实现；4 项 P1 合同缺口应在首期设计中明确，另有 1 项 P2 兼容性缺口。以下是计划风险，并非已经上线的浏览器实现缺陷。

修订状态：上述问题已纳入[实现方案](browser-agent-worker.md)，实现采用后端授权单步与原生浏览器 Worker，并保留服务端执行及默认关闭的开关。本文保留初审记录，原方案行号对应修订前版本；验证范围以实现方案和交付报告为准。

## 1. [P1] 异步模型接口缺少脱离浏览器的结果收尾责任

计划位置：原方案第 68 行的 `runtime/model`，第 70 行 `runtime/settle`，第 84 行页面关闭行为。

当前 `cloud_agent_pi_model.go` 的 `runCloudAgentModelStep` 在任务入队后调用 `waitCloudAgentTask`，随后解析结果、校验工具调用并调用 `finishCloudAgentPiModelStep` 或 invalid-calls 分支写回运行。当前 coordinator 在 session 返回后调用 `completeCloudAgentPiRun`。这些收尾逻辑不能因为 HTTP 改为立即返回 taskId 而消失。

触发：任务入队后浏览器关闭，文本模型任务成功，但没有执行端继续原等待函数或请求 settle。后果可能是 ActiveTaskID 没清理、Calls 未保存、最终回复未结算，或恢复端把已经结束的一步当成未结束。

修正要求：把单个已接受步骤的结果归档作为服务端任务完成处理/恢复核对的一部分，幂等完成 canonical 消息、调用批次、回执和最终状态。浏览器只决定下一步何时发起；服务器仍处理已接受任务的完成，不因此启动新一轮 Agent 循环。`settle` 只能触发核对，不能是唯一收尾路径。不得靠不受持久队列管理的 HTTP 后台 goroutine 保证完成。

验收：分别在入队后、结果持久化后但回执前、最终回答写入后但 settle 前关闭页面；任务完成状态和结果可查询，重开不重新收费或重复回答。

## 2. [P1] “加载历史后续跑”遗漏 assistant 工具批次的恢复算法

计划位置：原方案第 67、83、86 行，以及第 112 行首期刷新恢复。

固定版本 `pi-agent-core@1.5.2` 的 `Agent.continue()` 在历史末尾为 assistant 且没有插话队列时直接抛出 `Cannot continue from message role: assistant`。本地固定版本源码与 Context7 对应文档均可确认。当前 Go 工具执行器则按 `state.Calls[state.CallIndex]` 顺序匹配，并优先重放已有工具回执。

触发：模型已生成 3 个工具调用，刷新发生在尚未执行任何工具、执行到第 2 个、或等待审批期间。只还原消息再调用 continue 无法完成剩余工具；重新请求模型会改变调用并可能产生额外付费。

修正要求：定义持久恢复阶段和服务端返回的待办操作。先按原 assistant 批次顺序核对已完成回执、等待已有任务、处理审批，再通过同一受控工具执行入口完成剩余调用；不把不完整批次直接交给 SDK continue。仅当原批次所需 toolResult 全部齐全并恢复原生 reasoning 字段时进入下一模型请求。最终 assistant 已结束则收尾，不 continue。不得伪造“成功”工具结果来绕过 SDK 限制。

验收：工具批次每个切点断开重连，断言原调用 ID 和结果顺序不变、每个副作用一次、没有额外模型请求。首个只读闭环也要覆盖该路径。

## 3. [P1] 步骤幂等与 epoch 仅有原则，缺少可执行的唯一性合同

计划位置：原方案第 61、64–75 行。

当前运行 Revision CAS 和工具回执可复用，但“带步骤 ID”本身不能防止恢复后重新生成一个 ID，再次发起同一模型请求。当前 `runCloudAgentModelStep` 用 ActiveTaskID 接管在途任务；已完成并清除 ActiveTaskID 后的重试还需可定位的持久回执。模型有限纠偏/重试也必须区分逻辑步骤与实际付费 attempt。

触发：模型完成且服务端清除活动任务后，HTTP 响应丢失；新标签接管后创建新步骤 ID。另一个竞争窗口是旧 epoch 在 handler 校验通过后，新 owner 接管，而旧请求才进入任务创建事务。

修正要求：由服务端按持久 turn/next-action 标识签发逻辑 stepId；相同逻辑步骤、不同网络重试和 owner 都查回同一记录。服务端掌握付费 attempt 序号和有限重试策略，Worker 不叠加自动重试。唯一约束/条件写应阻止同一 next-action 创建两次，输入摘要不一致返回冲突。epoch、允许的 phase/revision 和步骤预占应在同一受保护事务中核对。

已被服务端接受的旧 epoch 任务可以按原 task/step 身份写入完成回执；失效的是旧浏览器发起新步骤的权利。不能因 epoch 更新拒绝真实任务结果，也不能让旧结果覆盖新阶段。复用现有 receipt/任务创建事务，避免再建一套泛化工作流引擎。

验收：同一请求延迟到接管后才入库、结果已入库但响应丢失、恢复后换 owner、模型纠偏重试，均不产生未经授权的新任务或多份结果。

## 4. [P1] waiting_browser 混合连接状态与业务状态，会冲掉审批或输入等待

计划位置：原方案第 84、86、92 行。

代码不仅有 `waiting_approval`，还有 `waiting_user`：`cloud_agent_pi_coordinator.go` 的 `cloudAgentRunPausedForInput` / `completeCloudAgentPiRun` 明确同时处理两者。模型调度器通过 `run.Status == waiting_approval` 加 Approval 字段阻止审批期间的新步骤。

触发：待审批或表单等待输入时 lease 到期，失联处理器统一写 `waiting_browser`。这可能隐藏真实用户动作，甚至使依赖原 status 的模型门禁失效。重新打开后也无法仅凭 waiting_browser 判断应等待审批还是续跑。

修正要求：首版优先保留现有业务 status，执行端连接状态由 owner/lease 派生；UI 以单独字段展示“浏览器未连接”。保持待审批、待输入、媒体等待、终态的优先级。若仍新增持久 waiting_browser，必须保存恢复 phase 并给出完整状态转移表，禁止无条件覆盖。服务端门禁还应检查真实待处理审批/工具阶段，不能只靠单个展示状态。

验收：分别在待审批、待用户输入、媒体执行、取消完成时令 lease 过期；原业务状态不丢失，重新连接后显示正确动作，不能发起不允许的模型步骤。

## 5. [P2] 协议版本和上下文能力后置，会让分阶段发布缺少保护

计划位置：原方案第 55、112–115 行。

方案把 reasoning、压缩/检查点和版本恢复放在第三阶段，但第二阶段已包含完整写工具和业务能力。首期可用的小会话探针并不能保证长上下文或老页面连接新后端的行为。当前 SDK 的完整 session 能力与底层 core 已有明确差异。

修正要求：claim/state 首期就返回 runtimeProtocolVersion、checkpointVersion 和服务端认可的能力集合。旧网页遇到不支持的协议时停止领取新步骤并提示刷新；已提交任务继续服务端归档。短期不做多版本兼容框架。无压缩支持时仅允许内部验证，并由服务端在上下文预算前拒绝下一步；不得静默截断历史。reasoning 原生字段保真、单步限额、审批门禁和取消不得后置到公开写工具之后。

验收：旧标签页跨发布、版本不支持、检查点格式不同、接近上下文上限时，均能安全停止或恢复，不丢工具回执、不重新收费。

## 日志上报专项结论

原方案已经覆盖自动上报、脱敏、离线补传、账号隔离、限量、确认后删队列及防递归，方向合理，无需另建监控平台。

实施时补三项明确验收条件：

- Worker 加载失败可能还没有 runId/stepId，允许这些字段缺省，以 eventId、用户 scope 和 buildCommit 定位；否则最需要诊断的启动失败会被接收器拒绝。
- 调用日志接口使用发起时的用户 scope 并带现有 expected-user 校验；单纯检查当前登录态无法排除请求在切换账号时跨 scope 落库。
- eventId 精确去重与同类故障聚合分别处理；接收 ACK 对应实际持久化的 ID。聚合不能让还未确认的新事件被本地提前删除，服务端还需限制去重记录保留量。

## 调整后的实施顺序

1. 先明确上述四个 P1 合同、版本字段和失败日志最小结构；沿用现有任务/回执事务，避免先铺新框架。
2. 首个闭环验证真实 Worker、一个只读工具、多工具批次切点、刷新与双标签接管，并将失败日志实际写入后端。静态 bundle 与 Bun mock 仅作前置证据。
3. 对齐审批、待用户输入、媒体任务、reasoning、取消和必要上下文策略，再开放写工具与普通用户。
4. 验证发布兼容与故障恢复，再切换默认执行模式和删除生产 Node 依赖。

本次为源码与计划审查，未修改产品实现、未运行数据库/浏览器/生产故障测试。现有打包与模拟闭环通过不能作为上述故障场景已通过的证据。
